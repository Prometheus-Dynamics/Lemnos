# Changelog

All notable changes to this workspace should be documented in this file.

The format is based on Keep a Changelog and this project follows Semantic Versioning.

## [Unreleased]

### Removed

- The crates.io packaging check (`ci.sh package-surface` and its CI job). Lemnos is used as a git dependency and is not published to crates.io; lemnosd's `orion` feature depends on Orion through git, which `cargo package` cannot resolve.

### Added

- Trailing `*` wildcards in client names: a board device's `writers` and the board-level `raw_clients` admit every client whose name starts with the prefix (`writers = ["orion:*"]` admits the Orion bridge's `orion:<requested_by>` connections; `*` alone admits any client). Entries without `*` still match exactly, and a `*` anywhere but the end is a board validation error (`docs/board-definition.md`, `docs/system-service.md`).
- `lemnos-orion`, lemnosd's devices as Orion resources (`docs/orion.md`, the contract; feature `orion` of `lemnosd`, unit `packaging/systemd/lemnos-orion.service`, optional Gaia layer `packaging/gaia/lemnos-orion.toml`). A lemnosd client (`orion`) and an Orion provider (`lemnos-orion`, provider `lemnos`): one resource `lemnos.<board>.<device>` of type `lemnos.device` per device, with labels for class, model, driver, units and control ranges; status (`status`, `reason`, `read_us`, channel values and `control.<name>` as F64) at most `LEMNOS_ORION_RATE_HZ` (default 2) per device with per-quantity deadbands, a 30 s heartbeat and a 90 s TTL; actions `set`, `restore`, `release` and `read` on each resource, each caller on its own lemnosd connection (`orion:<requested_by>`). Pinned to Orion `4fadba9`.
- Raw bus and line access through `lemnosd`, so it stays the one owner of the hardware (`docs/system-service.md`, "Raw bus and line access"): GPIO line claims (by chip and offset, board `[[lines]]` name or kernel line name; direction, bias, drive, active-low, edges with debounce; read, write, edge events), PWM claims (by chip and channel or board `[[pwms]]` name; period, duty, polarity, enable), I2C transactions (combined write-then-read, register helpers, optional locks) and SPI transactions (full duplex, mode, speed and word size). Board devices' addresses, chip selects and lines are refused (`Refusal::Owned`), I2C/SPI ones brokered for clients a device lists in `raw`; unowned ones are claimed per connection (`Refusal::Claimed`); board-level `raw_clients` limits who may. Claims end with the connection: lines go to the claim's `on_release`, the board's `safe`, else high impedance; PWM is disabled. One definition for every layer: `lemnos_hal::raw` (`LineConfig`, `RawLine`, `PwmConfig`, `RawPwm`, `SpiConfig`, `RawSpi`, `SafeState`), implemented by `lemnos-linux` (`GpioLine`, `Spidev`), the new `lemnos_drivers_linux::SysfsPwm`, and `lemnos-hal` mocks (`MockLine`, `MockPwm`, `MockRawSpi`); `lemnos_board::raw` (resources, `DynLine`/`DynPwm`/`DynSpi`) and new `Buses` methods (`line`, `pwm`, `spi`, `line_chip_id`, `find_line`). Client API: `DeviceClient::{claim_line, claim_line_with, claim_pwm, i2c, spi, unclaim}` with `Line`, `Pwm`, `I2cDevice`, `SpiDevice`; `lemnos-ctl gpio|pwm|i2c|spi`.
- Control writes end with the writer's connection: a fan goes back to the kernel governor, other controls to their value from before the first write (no more marker files in clients). `DeviceClient::restore` / `Request::Restore` / `lemnos-ctl restore` undo writes explicitly; clients that keep their intents are exempt, so `lemnos-ctl set` persists.
- `lemnosd` feature `mock`: `lemnosd::mock::MockLemnosd` runs the real service over `MockHardware` and a fake sysfs, for client tests.
- `lemnos-ipc`: `ClientOptions::wait` (retry the first connection until `lemnosd` is up; with `reconnecting` and no wait, a failed first connection is a `Disconnected` event); `ClientOptions::events` and `LedClient::next_event`; re-exports of `DeviceClass`, `Quantity`, `Unit`, `Axis`, `DeviceStatus`, `NO_VALUE`, `ErrorKind` and `lemnos_hal::raw`.
- Sizes (x86_64, service profile): `lemnosd` 822 KB to 905 KB and `lemnos-ctl` 742 KB to 798 KB for raw access (spidev, sysfs PWM, the claim table, the new requests and commands).
- `packaging/buildroot/lemnos-users.table` (the `lemnos` user for `BR2_ROOTFS_USERS_TABLES`, as Buildroot does not run sysusers into the target); `lemnos` joins `spi`; udev rules for raw PWM in `packaging/README.md`.
- `lemnos_hal::asynch::Blocking`: a blocking register map (`RegisterBus`), I2C bus, SPI device or delay used through the async traits (`asynch::RegisterBus`, embedded-hal-async `I2c`, `SpiDevice`, `DelayNs`), so async driver code (Styx's sensor core) runs over blocking buses.
- `lemnos_hal::mock::MockI2c`: clones share the bus (a mutex with `std`, `Send + Sync`; a `RefCell` without), `with_pending_polls`/`set_pending_polls` make async transfers return `Pending` first, `set_dead(address, dead)` makes a target stop acknowledging, and `value` reads a multi-byte register. `target` and `transfers` now return snapshots, and `clear_log`/`fail_next` take `&self`.
- `lemnos-drivers-vcm`: `VcmChip::Custom` (no built-in format: `builtin_format` is `None`, `format` is `VcmFormat::UNSET`, which `check` rejects with `FormatError::Unset`), `VcmChip::BUILTIN` and `name`; feature `alloc` adds `OwnedVcmFormat` (owned power sequences, lent as a `VcmFormat` through `refs`/`with_format`, at most `MAX_VCM_WRITES` each); feature `serde` (de)serializes `VcmChip` by its description name and, with `alloc`, `OwnedVcmFormat` (defaults `bytes = 2`, `bits = 10`).
- `lemnos-device` (`no_std`, no allocation): the compact device model from `docs/compact-model.md`. `DeviceClass`, `Quantity` with one canonical `Unit` each, fixed-point `Channel`s (`raw × 10^exponent`, `NO_VALUE` for no reading), `ControlInfo`, `DeviceInfo`; the `Device`, `Sensor` and `Control` traits (blocking and `asynch`); object-safe `DynSensor`/`DynControl`/`DynSensorControl`, `DeviceRef` and (feature `alloc`) `BoxedDevice`; `kernel::KernelBinding`, a data description of how a chip maps onto its mainline IIO/hwmon driver; `fixed::rescale`.
- The BMI088, BMM150, INA2xx and VCM drivers implement the device model (blocking and async): `Imu` with acceleration (mm/s²) and angular rate (µrad/s), `Magnetometer` in nT, `PowerMonitor` with bus/shunt voltage, current, power and (INA238) die temperature, and `Lens` with a `position` control. Each publishes its `DeviceInfo` and kernel binding (`lemnos_drivers_bmi088::{INFO, KERNEL}`, `Model::info`/`Model::kernel`, ...). `Bmi088::with_config` and `Bmm150::with_config` set what the device model's `init` applies; The conversions (`Config::channels`, `MagneticFieldFixed::channels`, `ReadingFixed::channels`) use no 64-bit division.
- `lemnos-lite` (`no_std`, no allocation): `Devices`, a static table of `dyn` devices with per-device `DeviceStatus`, last error kind, reads and control writes by index or name, and `poll` with per-device periods that re-initializes devices that are not up. Example: `linux_sensors` (BMI088 + BMM150 + INA238 on `/dev/i2c-N`).
- The generic runtime adapter (`lemnos_driver_sdk::l1`): `L1BoundDevice` binds any `lemnos-device` device (channels become telemetry in SI units keyed by channel name, controls become `<control>.set`/`<control>.get` interactions, `device.read`), `L1Driver` binds descriptors through a factory, `describe` adds class, model and units to descriptors.
- `lemnos-board`: versioned board definitions (`format = "lemnos.board"`, TOML or JSON, JSON Schema in `docs/schemas/`), strict validation, and `DriverRegistry` factories for `bmi088`, `bmm150`, `ina226`, `ina238`, `ina260`, `vcm`, `hwmon-fan` and `thermal-zone` with `auto`/`userspace`/`kernel` backends; `LinuxBuses` (feature `linux`); `examples/raze.toml` and a `validate` example. See `docs/board-definition.md`.
- Facade feature `board`: `lemnos::board::BoardSetup` (probe and drivers for a board definition) and `LemnosBuilder::with_board`, which also adds the board's drivers to the bind policy. `LinuxBackend::with_probe` runs extra probes (such as a board's) in every Linux refresh.
- `lemnos-drivers-linux`: `HwmonFan` and `ThermalZone` as device-model devices, and `KernelDevice`, a generic binding that serves a chip through its mainline IIO/hwmon driver from the chip crate's `KernelBinding`.
- The Linux backend discovers thermal zones (`ThermalDiscoveryProbe`, `linux.thermal.<zone>`), and the built-in drivers bind them (`lemnos.linux.thermal-zone`) as temperature sensors. Hwmon fan and thermal descriptors carry a `device.class` label.
- `lemnos_bus::hal::OwnedI2cBus` (an owned controller session as an embedded-hal bus), `lemnos_hal::erased::Kind` (a bus or pin with its errors reduced to `ErrorKind`), `DriverError::Device` (a device-model driver's failure with its `ErrorKind`).
- `lemnosd`, the board's hardware service (phase 4, `docs/system-service.md`): one single-threaded `poll` loop hosts a board definition's devices and serves clients over `/run/lemnos/lemnosd.sock`: device lists in the compact model, reads and subscriptions, control writes under each device's `writers` policy, LED intents and events. Devices that fail stay `missing` and are retried; fans with a `restore_mode` go back to the kernel on stop, on panic (hook) and after a crash (`ExecStopPost=lemnos-ctl fan restore --all`). systemd `Type=notify` with a watchdog. It shows the device package's updates (`/run/pd-device/update.json` and the copy progress) on the status light with no updater changes. `lemnos-ctl` is its command-line client.
- `lemnos-ipc`: the socket protocol (length-prefixed little-endian frames) and `DeviceClient`/`LedClient` in the style of Styx's `FrameClient`/`ControlClient` (typed reads, subscriptions, controls answered with the applied value or a `Refusal`, LED intents, `ClientEvent::Connected`/`Disconnected`, background reconnection that restores subscriptions and held intents).
- `lemnos-light` (`no_std`, no allocation): fixed-point easing (linear, ease-in/out/in-out, sine, cubic Bézier), effects (`Solid`, hard `Blink`, eased `Breathe`), gauges with sub-LED precision and eased advance, spinners, built-in system animations (updating with phases, booting, rebooting, update failed, rolled back), an `Animator` that fades between looks and returns frames only while something moves, and an `Arbiter` (`Locate` > `System` > `Alert` > `Status` > `App`, then priority and recency). `Defaults` come from the board definition.
- `lemnos-drivers-ws2812` (`no_std`): WS2812/SK6812 strip geometry (count, index offset, direction), RGB/RGBW wire formats, brightness, and encoders for the RP1 `ws2812-pio` device (4 bytes per LED) and for SPI. `lemnos_drivers_linux::Ws2812Pio` is the device-model light over `/dev/ledsN`.
- `lemnos-device`: `Rgbw`, the `Pixels` trait and `DynLight`/`DeviceRef::Light`/`BoxedDevice::Light` for lights; `gpio::{OutputLine, InputLine}` as devices over embedded-hal pins. Board drivers `ws2812`, `gpio-output`, `gpio-input`; `Buses::gpio_output`/`gpio_input` (`LinuxBuses` over GPIO uAPI v2).
- `lemnos-linux-sys`: `poll_many` (a `poll` set) and `signal::SignalFd`.
- `packaging/`: the `lemnosd` systemd unit, environment file, sysusers entry and preset, and a Gaia layer (`packaging/gaia/lemnosd.toml`) that builds static aarch64 musl binaries with the new `service` profile.
- The Linux GPIO probe falls back to the character devices when `/sys/class/gpio` is absent (`CONFIG_GPIO_SYSFS=n`, feature `gpio-cdev`): chips with their labels and line counts, lines with their names (`line_name`, also the display name), consumers and whether they are in use.
- `lemnos_linux::hal::AsyncGpioLine` (features `gpio-cdev` + `tokio`): `embedded_hal_async::digital::Wait` for a GPIO line, awaiting edge events through Tokio's reactor. `GpioLine` and `GpioLines` implement `AsRawFd`.
- `lemnos_drivers_linux::UserspaceRegulator` (a `reg-userspace-consumer` supply as a `lemnos_hal::Regulator`) and `DebugfsClock` (a clock's rate from debugfs as a `ClockOutput`; gating stays with the kernel).
- Size images for the device model: firmware `device-static`, `device` and `lite`, and Linux `sensors` / `sensors-lite` (three I2C sensors without the runtime). `scripts/check-sizes.sh` honours `CARGO_TARGET_DIR`.

- `no_std`, allocation-free sensor drivers over embedded-hal I2C, blocking and async, in SI units:
  - `lemnos-drivers-bmi088`: Bosch BMI088 IMU (both dies on one bus; ranges, data rates, die temperature).
  - `lemnos-drivers-bmm150`: Bosch BMM150 magnetometer with factory-trim compensation to µT and repetition presets.
  - `lemnos-drivers-ina2xx`: TI INA226, INA238 and INA260 power monitors with calibration from shunt and maximum current.
- Each driver has `resume` (or, for INA2xx, a bus-free `new`) so a runtime adapter can rebuild it around a borrowed `lemnos_bus::hal::HalI2cBus` per operation; `crates/lemnos/tests/nostd_driver_in_runtime.rs` shows the pattern.
- `scripts/check-nostd.sh` builds the three crates for the embedded and wasm targets.
- The sensor drivers read in integers (`read_fixed`: milli-g, milli-°/s, 1/16 µT, µV/nV/nA/nW, m°C) and gate their `f32` APIs behind a default `float` feature. Without it, an image for an FPU-less MCU links no software float routines: all four device drivers take 5.6 KB of flash on `riscv32imac` (9.9 KB with floats) and 5.3 KB on a Cortex-M4F.
- `lemnos-drivers-bmm150` gains Bosch's integer trim compensation; `lemnos-drivers-ina2xx` calibrates in integers (`Config::from_micro`).
- Fault reasons: `lemnosd` keeps why each device faulted (`init: ...`, `read: ...`, or a board build error) and sends it in `DeviceDesc::reason` and `Event::Status::reason`; `lemnos-ctl list` prints `why:`. The writer is `DynDevice::init_why` / `DynSensor::read_why` (`lemnos-device` feature `reasons`, which `alloc` implies), and `HalError::describe` gives the driver's own account.

### Changed

- CI does less work (CPU for a cold `ci.sh all` 506 s to 282 s, `ci.sh matrix` 171 s to 78 s, target dir 11 GB to 2.6 GB; `docs/testing.md`, "CI Cost"): every step prints its wall and CPU time; the `workspace` and `docs-and-lints` jobs no longer repeat the full-feature clippy, tests and docs; the feature matrix drops `cargo check` (clippy covers it) and runs tests only where the feature set adds behaviour (`lint` entries compile their tests without running them); `CARGO_INCREMENTAL=0`; the dev profile keeps line tables for workspace crates and no debug info for dependencies; the size check shares one target dir across Linux images; `cargo package` runs offline. The GitHub workflow calls the same scripts.
- The `service` profile uses the default 16 codegen units instead of 1: the final fat-LTO step runs on every core (about a third of the wall time) for about 1 % (aarch64) to 3 % (x86_64) larger `lemnosd`/`lemnos-ctl`.
- Static aarch64 musl builds of `lemnosd` need no container: the linker settings moved into `.cargo/config.toml`, `packaging/gaia/lemnosd-host.toml` builds both binaries on the host, and both Gaia artifacts are one build group (one cargo invocation).
- Size: the facade's Linux lite image grows from 564 KB to 573 KB (the thermal-zone probe) and, with the built-in drivers, from 669 KB to 728 KB (the generic device-model adapter, now behind the hwmon fan driver and the thermal-zone driver). The baseline records both; `lemnosd` (788 KB) and `lemnos-ctl` (708 KB) are tracked as host builds of the `service` profile.
- Breaking: `InterfaceKind::Platform` for devices without a bus session (thermal zones, kernel class devices); exhaustive matches need an arm.
- The built-in hwmon fan driver runs on `lemnos_drivers_linux::HwmonFan`: same `fan.*` interactions and telemetry, plus device-model telemetry (`speed`, `duty`) and `duty.set`/`pwm_mode.set`/`device.read`. Failures surface as `DriverError::Device`.
- `DeviceStatus` now lives in `lemnos-device`; `lemnos_core::DeviceStatus` re-exports it (same variants, same serde names).
- Toolchain pin moved to Rust 1.99.0 (MSRV stays 1.94). Dependencies upgraded to their newest releases (`syn` 3, `serialport` 4.10, `ordered-float` 5.5, `tokio` 1.53, `libc` 0.2.190, ...). No API changes. The size baseline is refreshed for 1.99 codegen.
- `I2cRegisters::write` sends one register straight from a 6-byte buffer instead of going through the burst packer, and the drivers write registers one at a time, so images that never enable bursts do not link the packer.
- `lemnos_drivers_ina2xx::Config` holds µΩ and µA (`Config::new(ohms, amps)` still exists with `float`).
- Size (x86_64 service profile): `lemnosd` 905 KB to 920 KB and `lemnos-ctl` 798 KB to 813 KB for fault reasons. Firmware: the fault-reason and BMI088 step-name code is compiled out of MCU images (feature `reasons` on `lemnos-device` and `lemnos-drivers-bmi088`, enabled by `lemnos-board`). The device and lite images grow by at most 156 bytes (riscv32imac) and 88 bytes (thumbv7em), and the BMI088 image by 124 and 98 bytes, from the tolerated soft resets and the chip-ID re-read.

### Fixed

- `lemnosd` no longer lets a client that never reads (an `LedClient`) grow its server-side queue without bound: clients say in their greeting whether they read events (LED clients default to no), and a client that falls behind loses readings first, then events, reported with `Event::Dropped`.
- `packaging/gaia/lemnosd.toml` and `lemnosd-host.toml` require `gaia_version = ">=2.0.0"` (was `>=2.1.0`, a Gaia version that does not exist: Gaia's unreleased features, build groups among them, sit under 2.0.0's Unreleased), so images importing the layer pass Gaia's version check.
- The facade's Linux API (`with_linux_backend*`, `refresh_with_linux`, hotplug helpers) now needs only `linux-backend` instead of the umbrella `linux` feature, and `LinuxBackend` implements every bus backend trait in every build (compiled-out buses return `BusError::UnsupportedInterface`). Builds can leave out `linux-usb` (libusb, a C toolchain) and `linux-uart` (serialport, nix); a `lemnos linux lite` CI matrix entry keeps that working.
- Fan hand-back for the Linux `pwm-fan` driver (found on the Raze, kernel 7.2): `pwm-fan` has no automatic `pwm1_enable` mode (2 only keeps its regulator on), and its thermal governor drives it through a cooling device, so writing `pwm1_enable = 2` left the fan at the last userspace duty. `lemnos_drivers_linux::FanRestore` now restores the `pwm1_enable` read at bind and makes the cooling device re-apply the governor's level (`cur_state` written to a neighbouring state and back) for fans whose driver is `pwm-fan` or that have a linked cooling device; chips with an automatic mode keep `pwm1_enable = restore_mode` (default 2). `lemnosd` works the plan out at a fan's first bind and records it in `/run/lemnos/fan-restore`; `lemnos-ctl fan restore` (run as root by `ExecStopPost=+`) applies the recorded plans first. The Raze example matches the fan by its real hwmon name, `pwmfan`.
- Fan release while `lemnosd` runs: `Request::Release` (`lemnos-ipc`), `DeviceClient::release` and `lemnos-ctl fan release <device>` hand one fan back to the kernel governor with the same hand-back as a stop (bind-time `pwm1_enable`, the governor's state from before the first write, the zone-policy kick), under the device's write policy, and broadcast a `release` control event. The fan stays released until a client writes one of its controls again, which takes it back (recording the governor's state first); there is no claim request. While a fan is released or was never written, the stop helper's record carries no governor state, so a stop only restores `pwm1_enable` and kicks the governor.
- LED test layer: `lemnos_light::Layer::Test` sits above `Status` and below `Alert` (`Intent::test`). `LedRequest::test` (an optional flags byte on the wire; older frames decode as not-test), `LedClient::test`/`clear_test` and `lemnos-ctl led ... --test` put any look there, so a selftest's frames are not hidden by another client's status. `lemnosd` holds test intents on a lease (`duration_ms`, else `TEST_LEASE_MS`, 10 s; renewed by sending again) and drops them when a client that does not keep its intents disconnects.
- Board definitions can find an I2C bus by what it is instead of its probe-order number: `bus = "i2c:<key>=<value>[;...]"` with `name` (adapter name), `compatible` (the adapter's or its parent's device-tree `compatible`), `of` (device-tree path, kernel-specific: take it from the running device tree or a manifest; RP1's i2c1 is `/axi/pcie@1000120000/rp1/i2c@74000` on kernel 7.2) or `node` (the path's last component). `lemnos_board::I2cSelector`, `BusRef::I2cMatch`, `BusRef::is_i2c` and `BusRef::i2c_bus` resolve it under a sysfs root; hosts resolve at build time (the facade's board probe at each refresh), and no match or several fail that device with `not-found`. `BusRef` is no longer `Copy`.
- The Raze example (`crates/lemnos-board/examples/raze.toml`) carries the buses and addresses verified on the Raze: BMI088 on the i2c-gpio bus (`bus = "i2c:compatible=i2c-gpio"`, i2c-4 on the 7.2.9 image; 0x18/0x68), BMM150 on i2c-1 0x10, INA238 on i2c-1 0x40, the fan as `pwmfan`, the ring as `wire = "rgb"`.
- The `pwm-fan` hand-back restores the governor's state, not the controller's (retest on the Raze: writing `pwm1` moves the cooling device's `cur_state` to the matching level, so re-applying the current state kept the fan at 100 % until the next trip crossing of a zone without polling). `FanRestore` now records each cooling device's `cur_state` (`CoolingRecord`) at bind and again just before the controller's first write (`FanRestore::record_states`, `lemnosd` does this on a fan's first client write), writes it back on hand-back (after a neighbouring state when the device is already there), then makes every thermal zone bound to the device re-evaluate by writing its `policy` back (`kick_governors`). `lemnos-ctl fan restore` without a record only restores `pwm1_enable` and kicks the governor. The state file records the states (`<device>=<state>`).
- `LEMNOSD_UPDATE_STATUS` is the only place the update status path is set: `lemnosd` has no built-in default, the unit no longer sets it, and the staged `/etc/default/lemnosd.env` does (device packages redeclare the Gaia `lemnosd-env` item for another path).
- BMI088 `init` ignores the results of the two soft-reset writes (a die resets as it takes the byte, so a bit-banged `i2c-gpio` master can see it NAKed, `EIO`) and re-reads both chip IDs after the resets; a failing step is named in `Error::Step` (feature `reasons`).

## [2.0.0]

Lemnos becomes the hardware foundation under Styx: embedded-hal 1.0 is the bus vocabulary,
device drivers are `no_std`, and Linux is reached through one pure-Rust implementation. See
[docs/foundation.md](docs/foundation.md).

### Added

- `lemnos-hal` (`no_std`, no allocation): re-exports `embedded-hal` 1.0 and `embedded-hal-async` 1.0; `RegisterBus` and `asynch::RegisterBus` with `I2cRegisters` and `SpiRegisters` (8/16-bit addresses, 1-4 byte values, big/little endian, bursts, read-back, read-modify-write); `Regulator`, `ClockOutput`, `GpioRegulator`, `FixedClock`; `HalError`; a `mock` feature with I2C/SPI/pin/delay/regulator/clock doubles. Re-exported by the facade as `lemnos::hal`.
- `lemnos-linux-sys`: the workspace's only `unsafe` code, with safe wrappers over i2c-dev (incl. SMBus), spidev, GPIO uAPI v2, netlink uevent sockets, inotify and `poll`, and layout tests against the kernel headers.
- `lemnos_linux::hal`: `I2cBus`, `Spidev`, `GpioChip`/`GpioLines`/`GpioLine`, `StdDelay`, `IoError` implementing embedded-hal (and embedded-hal-async for I2C/SPI). `lemnos_linux::uevent`: `UeventSocket`, `Uevent`.
- `lemnos_bus::hal`: `HalI2cBus`, `HalI2cDevice`, `HalSpiDevice`, `HalPin`, `HalPwm` adapt sessions to embedded-hal; `BusError` implements the embedded-hal error traits.
- `lemnos-drivers-vcm`: `no_std` VCM drivers (DW9714, DW9807, DW9817, AK7375, custom formats), blocking and async.
- Linux GPIO cdev sessions support bias and debounce, and `open_gpio_edge_stream` streams edge events.
- `LinuxHotplugWatcher::{with_uevents, with_inotify, source}` and `HotplugSource`.
- `linux_hal_probe` example; `scripts/check-nostd.sh` and a `nostd` CI job.

- `AsyncLinuxHotplugWatcher` (`lemnos-linux` `tokio` feature, enabled by the facade's `tokio` feature) waits on the inotify descriptor through Tokio's reactor instead of timer polling. `LinuxHotplugWatcher` now implements `AsFd`/`AsRawFd`.
- `RuntimeBindPolicy` lets refreshes bind matching devices (by interface, kind, or resolved driver id) on their own. Set it with `LemnosBuilder::with_bind_policy` or `set_bind_policy`. The default binds nothing.
- `Runtime::device_status` and `DeviceStateSnapshot::status` summarize a device as `DeviceStatus` (`Available`, `Degraded`, `Faulted`, `Missing`) without binding it.
- Built-in `HwmonFanDriver` (`lemnos.pwm.hwmon-fan`) for Linux hwmon fans, with `fan.read`, `fan.set_duty`, `fan.set_pwm`, and `fan.set_mode` interactions and `duty_ratio`/`mode`/`rpm` telemetry.
- `MockHwmonFan` in `lemnos-mock` gives class-device drivers a fake hwmon fan without a real `/sys`.
- `ErrorKind` and a `kind()` method on every Lemnos error type classify failures (not found, busy, permission denied, timeout, and so on) through wrapped sources.
- `Value::to_label_string` and `Value::flatten_labels` render values as flat string labels.

### Changed

- Breaking: `lemnos-core` and `lemnos-driver-manifest` are `no_std` + `alloc` with a default `std` feature; the workspace dependency entries set `default-features = false`.
- Breaking: `ErrorKind` moved to `lemnos-hal` (still `lemnos_core::ErrorKind`) and gained `Nack` and `Overrun` (both transient). `ErrorKind::from_errno` classifies Linux errnos.
- Breaking: the `i2cdev`, `spidev`, `gpio-cdev` and `inotify` dependencies are gone. The `gpio-cdev` feature keeps its name and now uses GPIO uAPI v2 (Linux 5.10+); cdev sessions take a line over as-is instead of re-requesting it with a default level.
- `LinuxHotplugWatcher::new` listens to netlink uevents on the real `/sys` and uses inotify for other roots or when the socket is refused.
- Linux I2C session transactions run as one combined `I2C_RDWR` transfer (repeated starts) when the adapter supports plain I2C.
- `thiserror`, `serde` and `serde_json` are workspace dependencies without default features.
- `RuntimeRebindReport` also lists devices bound by the bind policy. Policy bind failures are recorded as `RuntimeFailureOperation::Bind`.
- `BuiltInDriverBundle::DRIVER_IDS` now has seven entries.
- The Linux hwmon probe no longer publishes live `fan.pwm`, `fan.pwm_mode`, or `fan.rpm` descriptor properties, so speed changes no longer mark the fan as changed on refresh. Read them from the bound driver's telemetry. Descriptors now carry a static `fan.has_tachometer` flag.
