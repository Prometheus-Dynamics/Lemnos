# The Allwinner FEL thunk blob

The blob is the small routine a PC side writes into SRAM and runs through the boot ROM's FEL loop (FEL_RUN). The
code is `lemnos-driver-allwinner-fel-sys` (naked assembly, one function per target). This crate holds what a PC side
pins, and the writer that fills in one run's fields:

- `pinned` (`src/pinned.rs`): the built code words of each target: the bytes the thunk's section holds before a run's
  fields are written. Generated by `drivers/allwinner-fel-sys/scripts/check-blob.sh --emit`, which checks them against
  the build.
- `layout` (`src/layout.rs`): each target's blob length, the offset of each data word, the swap table's size, the save
  area's length, and the stated `version`. The offsets are checked against the build's symbols.
- `blob` (`src/blob.rs`): `write`, which copies the pinned words into a buffer the caller owns and writes the run's
  fields: the SPL entry, the watchdog's address and its arm and disarm values, and the swap table. Every check runs
  before the first byte is written, so a refusal leaves the buffer untouched.
- `hash` (`src/hash.rs`): FNV-1a, the function the layout hash and the blob hash fold with. Its vectors are the same
  as the flash wire's (`lemnos-flash-wire`), so the two crates agree on the function.

No dependencies, no `unsafe`, `no_std` outside tests.

## Targets, versions and pins

| Target | Stated version | Blob length | Layout hash (FNV-1a) | Blob hash (FNV-1a of the pinned bytes) |
|---|---|---|---|---|
| `armv7a-none-eabi` (ARM state) | 1 | 364 | 395945050492294272 | 9449696536236141269 |
| `aarch64-unknown-none` | 1 | 456 | 7647534792890474860 | 9620355475417539984 |

The layout hashes are pinned by `layout::tests::the_layout_hashes_are_pinned`, the blob hashes by
`blob::tests::the_blob_hashes_are_pinned`. A PC side pins the blob hash it expects and refuses a different blob. Both
pins were computed twice, once by the crate's own fold and once by an independent FNV-1a walk over the same fields.

## The layout

| Target | Table at | Entry | Flag | Watchdog address | Watchdog arm | Watchdog disarm | Save area |
|---|---|---|---|---|---|---|---|
| armv7 | 208 | 304 | 308 | 312 | 316 | 320 | 324, 40 bytes |
| AArch64 | 232 | 328 | 332 | 336 | 340 | 344 | 352, 104 bytes |

The table has eight entries of three words (buf1, buf2, bytes). A zero byte count ends it, so at most seven swaps
fit. The AArch64 save area is 8-byte aligned, which leaves four bytes of padding after the last data word.

## What the thunk does

1. Arm the watchdog: write the arm value to the watchdog's register. This is the first thing the thunk does.
2. Save the ROM's callee-saved registers, the stack pointer and the link register.
3. Swap each table buffer with its backup. Each size must be a whole number of words and each entry is walked at most
   eight times. A failed check spins with no feed, so the watchdog's reset is the exit.
4. Call the SPL.
5. Swap the buffers back.
6. Disarm the watchdog, restore the registers and return into the boot ROM's FEL loop.

Every loop ends in the watchdog: a bad size, a table with no terminator, or an SPL that never returns leaves the
watchdog armed, so the SoC resets. A panic in the thunk's staticlib parks without a feed for the same reason.

## Return is proven before any write

The thunk cannot prove its own return, so the PC side does it, before it writes the real SPL or any other data:
write this blob with a return-only entry (a single return instruction at a free address: `bx lr` on armv7 (word
`0xe12fff1e`), `ret` on AArch64 (word `0xd65f03c0`)), run it, and check that the FEL loop answers again. Only then
write the real entry and the SPL. The harness in `lemnos-driver-allwinner-fel-sys` runs this exact sequence under
emulation (`a_return_only_entry_proves_the_thunk_returns`). The enforcement is the PC side's; this crate states the
rule and supplies the probe's word.

## Provenance and what is not confirmed

The layout and the swap order follow the PC-side project's clean-room record of the FEL flow. That record takes its
facts from public pages (the linux-sunxi wiki, FEL and its USB boot notes) and states that no sunxi-tools or U-Boot
source was used. The thunk here adds the watchdog and the bounds, so its bytes are not the PC side's first thunk, and
it has three more data words (the watchdog's address, arm and disarm values). A PC side that wrote the first thunk
must write these fields too.

Not confirmed, all of it data or hardware: the watchdog's address and its arm and disarm values for a given SoC (the
caller's data; nothing in this crate sources them); the SRAM addresses and the SPL entry; the A733's FEL state, which
the record marks as UNCONFIRMED, including whether its FEL loop runs the 32-bit or the 64-bit thunk. The AArch64 blob
has no reference bytes from anywhere but this repository. Both blobs are **untested on board** (see
`testing/board-runs/FEL.md`).
