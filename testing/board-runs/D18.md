# D18 board run: the PiSP front end takes its configuration from its client and gives back statistics

Run on the board 2026-11-11: check 1 passed without output 1, check 7 passed; the others were not
run.

What changed. `PispFe` (`drivers/pisp`, `fe_*`) has the back end's streams: `config` (jobs on its
ring, configurations in its buffers), `statistics`, `output0` (was `frames`) and `output1`. For each
job the driver reads the client's configuration once into its own memory, refuses it if any address
field or `ilines` is set, and writes it into the job's configuration slot (driver memory the module
was given at stream start; one slot per `output0` buffer). The statistics buffer (the one numbered
as the job's config buffer) and the output 1 buffer are borrowed from their streams as dma-bufs,
registered with the module for the one job (`LEMNOS_STREAM_IOC_REGISTER`), named in the job's
ranges, unregistered when the frame is finished and then published with the job's identity.
`PispFe` is now registered in `lemnosd` (`pisp-fe`). The host tests (`drivers/pisp/tests/fe_frames.rs`,
`drivers/pisp/src/fe_device/tests.rs`) prove this against a stand-in for the block and module;
nothing here has run on the block.

## Setup

1. Take the board lock, `/run/lock/board-gpu.lock`, as AGENTS.md says. CM5 (Raze #2). Builds on
   NVMe or SSD. Load `lemnos.ko` from `next` with the camera front-end block in `owned=`.
2. Board file: the camera front-end block as a `pisp-fe` device (the receiver's driver can't run on
   the same block), `config = { device = "<the block>", lanes = 2, mbps = <the sensor's>,
   data_type = 0x2c }`, and streams:
   - `[devices.streams.config]`: `buffers = 4`, `buffer_bytes` at least `config_layout(0).bytes`
     (632), `job_slots = 8`, `job_bytes = 128`.
   - `[devices.streams.statistics]`: `buffers = 4` (as many as `config`), `buffer_bytes` at least
     `info().statistics_bytes`, `memory = "dma-buf"`, `heap = "linux,cma"`.
   - `[devices.streams.output0]` and `[devices.streams.output1]`: `buffers = 4`, `buffer_bytes` at
     least the `size` `set_output(2, ...)` / `set_output(3, ...)` answer, `memory = "dma-buf"`.
   The sensor device with `link` to it, as in `docs/design.md`.

## Checks

1. **Configuration from the client.** Sensor streaming colour bars. `set_input`, `set_output(2)`,
   `set_output(3)` (same size), `start`. Write a configuration built with the library's `FrontEnd`
   (output 0 and 1, 16-bit, AWB and AGC statistics on) into config buffer 0, and post one job per
   `output0` buffer, cycling config buffers 0..3. Pass: every frame on `output0` and `output1`,
   read through its handle, is the pattern; a frame arrives on `statistics` for every job, in the
   buffer numbered as the job's config buffer, with the job's identity; `stats::Statistics`
   decodes it and the AWB zone sums move when the scene's colour changes (cover the lens with a
   red filter).
2. **The configuration is what the client posted.** Post a job with the black level (`bla`) at a
   visibly high value, then immediately overwrite that config buffer with one at zero before the
   frame. Pass: the frame shows the high black level (the copy taken when the job was taken), and
   the stream stays open.
3. **Address fields refused before the module.** Post a configuration with `stats_buffer.addr_lo`
   set. Pass: `counters().dropped` rises by one, `LEMNOS_STREAM_IOC_STATUS` still open, no
   `EINVAL` fault in the kernel log.
4. **Held buffers.** Keep a statistics frame unreleased and post a job on its config buffer with
   statistics on. Pass: dropped by the driver, the held statistics unchanged; released, the next
   such job runs.
5. **Registration room.** Post 8 jobs at once with statistics and output 1 on (16 registrations
   wanted, the module has 14 regions beside the configuration region). Pass: the jobs that don't fit
   are dropped, the stream stays open, and the next round runs once frames finish. Record how many
   fit.
6. **Reattach.** Detach and reattach the `statistics` client mid-stream, then `output1`'s, ten times
   each. Pass: a job on a buffer taken for the old client is dropped; later ones land in the new
   client's memory; the front end is never stopped (`LEMNOS_PISP_FE_IOC_INFO.streaming` stays 1);
   `/sys/kernel/debug/dma_buf/bufinfo` shows no registration left over after each round.
7. **Stop in flight.** `stop` with jobs on the block. Pass: returns, not wedged, `bufinfo` shows
   nothing attached to the block after `lemnosd` stops.
8. **Cache.** Record whether the client needs `DMA_BUF_IOCTL_SYNC` around reading statistics and
   output 1 on the CM5.
9. **`lemnosd` hosts it.** The daemon binds `pisp-fe` from the board file and answers
   `camera.isp/1` `info`, `config_stream` (`config`), `statistics_stream` (`statistics`) and
   `output_stream(2)`/`(3)` (`output0`/`output1`).

## Not tested here

- The kernel's copy happening frames after the post: modelled by the stand-in, which reads the
  configuration slot only when it runs the job.
- Full module registration table on real hardware (check 5).
