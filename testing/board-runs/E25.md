# E25: this board as a USB device (FunctionFS gadget on Linux, and the driver that keeps it up)

Status: untested on board. The descriptor layout and its checks, the mock, the simulated board
and the microcontroller host's test port are covered by unit tests. On Linux, the FunctionFS blob
formats, the event layout and the ioctl numbers are pinned against `<linux/usb/functionfs.h>`,
the `struct iocb` and `struct io_event` layouts against `<linux/aio_abi.h>`, the gadget is built
and taken down on a stand-in tree of plain directories, and what a session does with each answer
FunctionFS can give is covered against a scripted stand-in. No test goes near the real configfs,
a real controller, a real FunctionFS mount or a real USB device, so nothing below has been seen
to happen.

What only a board can show:

- that configfs takes each attribute as written (`idVendor` and the rest in `0x` hex, `MaxPower`
  in mA, `max_speed` by name), and that the order of steps binds a gadget;
- that FunctionFS takes the descriptors and strings blobs, names the endpoint files by address
  (`FUNCTIONFS_VIRTUAL_ADDR`), and reports the events in the order assumed;
- that a transfer the wrong way on `ep0` stalls a request and answers `EL2HLT`, and on an
  endpoint file halts it and answers `EBADMSG`;
- that a read or write on an endpoint file through native AIO comes back by its timeout: the
  path that cancels and waits for the completion can't be reached on files a test may open;
- that lemnosd's user may do all of it (write access to the gadget directory, the mount and
  `UDC`).

Before running: take the board lock named in `AGENTS.md`. Builds go on NVMe or SSD. The driver is
not registered by this PR; a maintainer runs `scripts/generate-builtins.py`. A board with a
device-mode USB port is needed (the CM5's USB-C port with `dr_mode` set to `peripheral` or `otg`),
and a host computer on the other end of the cable with `lsusb`, `usbmon` and a way to send
control and bulk transfers (pyusb or libusb's examples).

## 0. What the image sets up

FunctionFS can only be mounted once its function directory exists, and this code mounts nothing.
With `NAME` the one entry of `ls /sys/class/udc` to be used:

```
modprobe libcomposite
modprobe usb_f_fs
mkdir -p /sys/kernel/config/usb_gadget/lemnos-NAME/functions/ffs.NAME
mkdir -p /dev/usb-ffs/NAME
mount -t functionfs NAME /dev/usb-ffs/NAME
```

Expect `/dev/usb-ffs/NAME/ep0` to exist. Record the kernel version and whether
`/sys/kernel/config/usb_gadget/lemnos-NAME/max_speed` exists.

The board entry:

```toml
[[devices]]
id = "gadget"
driver = "usb-gadget"
function = "udc:NAME"
config = { vendor = 0x1209, product = 0x0001, manufacturer = "Lemnos", product_name = "E25 check", serial = "E25-0001", interfaces = "interface 0xff 0 0 check\nendpoint in bulk\nendpoint out bulk\n" }
```

(`interfaces` is the text itself; if lemnosd builds the driver with its `std` feature it is a
path to a file holding that text.)

## 1. The gadget enumerates with the identity given

1. Start lemnosd with the cable unplugged. Expect the device's health `Ok`, and in
   `/sys/kernel/config/usb_gadget/lemnos-NAME`: `UDC` reads `NAME`; `idVendor` `0x1209`;
   `idProduct` `0x0001`; `strings/0x409/manufacturer`, `product` and `serialnumber` as given;
   `configs/c.1/MaxPower` `100`; `configs/c.1/ffs.NAME` a link to `functions/ffs.NAME`; and
   `ep81` and `ep02` in `/dev/usb-ffs/NAME`.
2. Plug the cable into the host. Expect `lsusb -v -d 1209:0001` on the host to show the
   manufacturer, product and serial strings, one configuration, one interface of class 0xff
   named `check`, and one bulk endpoint each way (512-byte packets at high speed). Record the
   endpoint addresses the host sees: the controller picks them, so they may not be 0x81 and 0x02.
3. Record `dmesg` on both ends. Any error from `configfs-gadget` or `functionfs` on the board is
   a finding.

## 2. A control request is answered

The driver refuses every request, so the answer to check is a stall.

1. From the host, send a vendor request to the device: `bmRequestType` 0xc0, `bRequest` 1,
   `wLength` 4. Expect a stall (`EPIPE` from libusb) within a few tens of milliseconds, and the
   device still enumerated afterwards.
2. Send a vendor request with data to the device (`bmRequestType` 0x40, `wLength` 4, four bytes).
   Expect a stall again.
3. With `strace -f -e read,write` on lemnosd, expect each stall to be one read or write on `ep0`
   that returns `EL2HLT`. Any other errno is a finding against `backends/linux-sys/src/functionfs.rs`.
4. A request the function answers with data needs a caller, and no contract carries one yet. To
   check `control_in` and `control_out` now, drive the backend from a test binary: open
   `LinuxBoard`'s `udc:NAME`, enable it with a descriptor set, and for a vendor IN request call
   `control_in(&[1, 2, 3, 4], ..)`, for a vendor OUT request `control_out`. Expect the host to
   read `1 2 3 4`, and the board to read what the host sent.

## 3. An endpoint carries bytes both ways

No contract carries endpoint bytes yet either, so this uses the same test binary.

1. After `Configured` from `next_event`, call `write(0x81, b"hello", 1 s)` and read the IN
   endpoint on the host. Expect `hello`.
2. Write 5 bytes to the OUT endpoint from the host and call `read(0x02, &mut [0; 512], 1 s)`.
   Expect 5 and the bytes.
3. Call `read(0x02, .., 200 ms)` with the host sending nothing. Expect `Timeout` after about
   200 ms, and the next `read` after the host does send to return its bytes. This is the AIO
   cancel path: a hang here, or a `read` that never returns, is a finding against
   `backends/linux-sys/src/aio.rs`.
4. Call `set_halt(0x81, true)`. Expect the host's next read of the IN endpoint to stall. Call
   `set_halt(0x81, false)` and expect reads to work again. The same for the OUT endpoint.
5. Send 1 MiB each way in 16 KiB transfers and compare. Record the rate.

## 4. Unplug and replug recover

1. With the device configured, pull the cable. Expect the driver's health to stay `Ok`, the
   gadget to stay bound (`UDC` still reads `NAME`), and, in the test binary of check 3,
   `next_event` to report `Deconfigured` and a `write` to fail with `Unavailable`.
2. Plug it back in. Expect the host to enumerate the same identity with no restart of lemnosd,
   `Configured` from `next_event`, and transfers to work again.
3. Pull the cable during a `read` with a 5 s timeout. Expect it to return `Unavailable` well
   before the timeout. Record what it does return.
4. Reset the device from the host (`usbreset`, or unbind and bind the host's port). Expect the
   same as a replug.
5. Unbind the gadget behind the driver's back (`echo "" > UDC`). Expect health `Failed` with
   `the controller let go of the gadget: enabling it again`, then `Ok` after 1 s with the gadget
   bound again.
6. Stop lemnosd. Expect `UDC` empty, `configs/` and `strings/` empty, the function directory and
   the mount still there, and the device gone from the host. Kill lemnosd with `SIGKILL` instead
   and expect the kernel to have unbound the gadget (closing `ep0` does it); start lemnosd again
   and expect the leftovers removed and the gadget up.
7. Start lemnosd without the mount (`umount /dev/usb-ffs/NAME` first). Expect health `Failed`
   with `the USB device controller, or what the board sets up for it, is not there: retrying`,
   nothing written under the gadget directory, and retries 1, 2, 4, 8, 8 s apart. Mount it and
   expect `Ok` within 8 s.

Record anything else. A kernel older than 5.12 has no `max_speed`: with a full-speed-only
descriptor set on a high-speed controller, record what speed the host sees.
