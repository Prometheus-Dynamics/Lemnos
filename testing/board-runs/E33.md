# E33 board run: the VIP9000 NPU (`drivers/vip9000`)

Status: untested on board. This is the vendor node's check (`route = "vipcore"`): there the driver
refuses to load programs because the vendor kernel driver cannot confine a job to its own buffers
(see `drivers/vip9000/src/confine.rs`). Jobs run only through `lemnos.ko`, whose check is
[`H7a.md`](H7a.md). What ran on the PC: the layout assertions (generated by
`drivers/vip9000/layout-check/run.sh` with gcc on x86_64, and the same numbers checked with
`aarch64-linux-gnu-gcc` and `clang --target=aarch64-linux-gnu`), and `cargo test -p
lemnos-driver-vip9000` (16 tests: checked builders, the confinement facts, the reach check against a
model of `vipcore`'s single shared page table and against a per-job table, the backoff, the
contract's refusals, no allocation). Everything was read from the Radxa `allwinner-bsp` tree at
`a842bb8dc74608ba13975c97c31b9518f1976c01`, not from a running board.

The board run is to confirm, on the A733 (Cubie A7A or another `sun60iw2` board) with the vendor
kernel, the facts the refusal rests on. It changes nothing in the crate unless a fact is wrong.
Build on NVMe or SSD, never on the Github HDD. Module loads and unbinds are allowed; report each.

## Which driver serves the block

```sh
ls -l /dev/vipcore /dev/galcore 2>/dev/null
readlink /sys/bus/platform/devices/3600000.npu/driver
cat /sys/bus/platform/devices/3600000.npu/uevent
ls /sys/bus/platform/devices/3600000.npu/iommu_group 2>/dev/null || echo "no iommu group"
cat /sys/module/vipcore/parameters/* 2>/dev/null | head -50
zcat /proc/config.gz | grep -E 'AW_NNA|NNA_VIP|NPU_USER_IOMMU'
```

Record: the bound driver's name (expect `vipcore`, built from `aw_nna_vip/vip2`), that the device
has no IOMMU group, whether `CONFIG_NPU_USER_IOMMU` is set (expected not), and the module
parameters `contiguousSize`, `reservePhysicalSize`, `reservePhysicalBase`, `AXISramSize`.

## Who can open the node

```sh
stat -c '%a %U %G' /dev/vipcore
```

Open the node twice from two processes (a small C or Python `os.open` twice): the second open is
expected to succeed (`vpmdENABLE_MULTIPLE_TASK` 3 uses a task queue, so `drv_open` does not refuse
it). Record the result.

## The shared page table

Unload and reload the module (`rmmod vipcore; modprobe vipcore`), then record
`dmesg | grep -i -E 'vipcore|vip|npu'`: what it prints about the video memory heap, the MMU and the
SRAMs. The crate takes the build to be `vpmdENABLE_MMU` 1 (one table for the device); if the log or
the module's build shows per-process or per-task tables (`vpmdENABLE_MMU` 2 or 3), the facts in
`confine.rs` are wrong for this build: report it. Nothing from the vendor's user-space runtime is
run for this check.

## What does not need a board

The refusal itself: `Vip9000::check` on any `Device` answering `Kernel::Vipcore` is
`State::Unconfined`, and `Npu::load` answers `NOT_SUPPORTED`. A board cannot change that while the
kernel driver is `vipcore` or `galcore`.
