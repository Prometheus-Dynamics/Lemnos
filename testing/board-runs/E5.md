# E5 board run: nonai2d

Status: untested on board. The layouts follow the SDK driver's source, the device session is
tested on a played-back node, and the checks between a caller and the engine (one dma-buf per
plane, each at least its plane by the kernel's own size of it, buffers the driver holds, strides
the driver computes) have passed their tests on memfds and on dma-bufs from a system heap. No
frame has reached an engine, on dev or here.

Run in a local session after this PR merges, on a K230 board running the K230 Linux SDK kernel
(`kendryte/k230_linux_sdk`, the tree the driver was read from, `fc6cc21` or later) with the
`nonai2d` package's module loaded. The CM5 has no such engine. Build on NVMe or SSD, never on the
Github HDD. Module loads and unbinds are allowed; report each.

## Checks

1. **The node answers.** `v4l2-ctl --list-devices`; `v4l2-ctl -d <node> --all` shows driver
   `nonai-2d` with `Video Memory-to-Memory Multiplanar`; `ls -l /dev/dma_heap/`;
   `dmesg | grep -i 2d`. Record the kernel version and the heaps present.
2. **Conversions.** As root (or with access to the node and the heap):

   ```sh
   LEMNOS_NONAI2D_HEAP=/dev/dma_heap/linux,cma \
     cargo test --release -p lemnos-driver-nonai2d --test board -- --ignored --nocapture
   ```

   Pass: the test passes: an ARGB32 frame becomes ABGR32 with every pixel's bytes reversed, and an
   NV12 frame of one colour becomes an ARGB32 frame of one colour. Record what it prints: the node,
   and the colour Y=0x80, U=0x40, V=0xc0 became. With those values it must be reddish (high R,
   low B); if it comes out bluish, the driver's NV12 and NV21 are swapped. If the CMA heap has
   another name, use it and record which. Run it three times.
3. **What the checks refuse, the kernel refuses too.** Not needed for safety, but record any
   `dmesg` lines from check 2: it must be clean of `nonai 2d invalid dma addr` and IOMMU or bus
   errors.
4. **Recovery.** While conversions run in a loop (a small program over `Nonai2d` and
   `node(find().unwrap())`), unload the module or unbind the device (report which), wait 20 s,
   and load or bind it again. Pass: `run` answers `Device` and then `BackingOff`, with delays of
   250 ms doubling to 8 s and holding there; once it is back, the next due call reopens and
   conversions pass again. Nothing panics and the engine never stops trying.

Record each result here.
