# E9 board run: rkisp (ISP21, ISP30, ISP35)

Status: untested on board. What landed first (PR #64) is the layouts (`drivers/rkisp-sys`), the
generation table, the ISP path plan over a media graph and the per-job checks (`drivers/rkisp`). The
second part (`E9b`) is the `camera.isp/1` driver itself, `Rkisp`: it links the path, sets the formats,
runs the vendor driver's parameter, statistics, main path and self path nodes through `lemnos-v4l2`,
and per job reads the parameters once from the config stream, queues that copy, and writes the
statistics and images of the frame the parameters were applied to into the stream buffers the job
named. All of it passes its tests against a stand-in kernel and mocked streams. No real ISP graph has
been read by this code, no parameter buffer from it has reached a running ISP, and no node of the
vendor driver has been opened by it.

Run in a local session after this PR merges, on a Rockchip board running the vendor kernel with
`rkcif` and `rkisp` bound and a camera whose kernel sensor driver probes. An RK3588 board (ISP30) is
the first target, an RK3566 or RK3568 board (ISP21) the second, an RV1126B board (ISP35) the third.
Build on NVMe or SSD, never on the Github HDD. Module loads, unbinds and rebinds are allowed; report
each.

## Checks

1. **The graph matches `graph`.** `media-ctl -p -d <dev>` on each ISP media device (driver name
   e.g. `rkisp-vir0`). Pass: entities `rkisp-isp-subdev`, `rkisp-input-params`,
   `rkisp-statistics`, `rkisp_mainpath`, `rkisp_selfpath`; `rkisp-input-params:0 -> isp:1`,
   `isp:2 -> rkisp_mainpath:0`, `isp:2 -> rkisp_selfpath:0`, `isp:3 -> rkisp-statistics:0`, and
   pad 0 fed by the receiver's subdevice. Then a small program reads the topology with
   `lemnos-v4l2` and prints `graph::plan(&t, None, true)`. Pass: the `source` is the entity
   `media-ctl` shows enabled into pad 0, and `enable` lists exactly the links `media-ctl` shows
   without `[ENABLED]`.

2. **The sizes match the running kernel.** On each board, the parameter node's
   `v4l2-ctl -d <rkisp-input-params> --get-fmt-meta-out` and the statistics node's
   `--get-fmt-meta-cap` report `buffersize`. Pass: at least
   `Generation::config_layout().bytes` and `statistics_layout().bytes` for that board's generation
   (ISP21 10475 / 13700, ISP30 10921 / 16172, ISP35 13065 / 14542). If the kernel's headers on the
   board differ from `develop-5.10` (ISP21, ISP30) or `develop-6.1` (ISP35), run
   `drivers/rkisp-sys/layout-check/run.sh` against them and record the diff.

3. **A parameter buffer is taken.** A small program binds `Rkisp` (`generation` as the board's,
   `device` the ISP's media device driver name) to host streams: `config` of 4 buffers holding the
   generation's parameter size, `statistics` of 4 holding the statistics size, `output0` of 4 holding
   a 1280x720 NV12 image. `set_input` with the sensor's mode, `set_output(0, 1280x720 NV12)`,
   `start`. Pass: `start` returns `Ok`, `media-ctl -p` shows the path's links enabled and the ISP's
   sink pad at the sensor's mode, `dmesg` shows no rkisp error. Then fill config buffer 0 all zero
   but `module_en_update` and `module_ens` set for `AWB_GAIN` with unit gains, post one job naming
   config buffer 0 and output buffer 0. Pass: within a second, `counters()` shows `jobs` 1, frames
   arrive on `output0` and `statistics` with the job's identity.

4. **Parameters come back with the frame they were applied to.** The driver ties a job to the frame
   whose sequence the vendor driver puts on the returned parameter buffer. With the program of
   check 3, log for 100 jobs the sequence of each returned parameter buffer and of the statistics
   and image published for it. Pass: each job's statistics and image carry the sequence its
   parameter buffer came back with, and `errors` stays 0. If the parameter buffer comes back with
   sequence 0 or a sequence no frame has, record it: the driver's matching rule is wrong for this
   kernel.

5. **Statistics come back.** With `RAWAE0` enabled in the parameters, read a published statistics
   buffer. Pass: `bytes` is at most the statistics size; `frame_id` in the buffer's header (ISP21 and
   ISP30 at offset 4, ISP35 after the statistics) counts up with the frames.

6. **Streaming with no parameters queued.** `start`, then post no job for 5 s. Pass: frames
   flow on the nodes (the driver gives each straight back), `dmesg` shows no rkisp error. If the
   vendor driver needs a first parameter buffer before the main path starts, record it.

7. **The self path.** As check 3 with `output1` (a stream of 2 buffers of 640x360 NV12) and
   `set_output(1, 640x360 NV12)`. Pass: `start` returns `Ok` (the media core takes a second enabled
   link from the ISP's source pad) and a job naming buffers on both outputs gets both images.

8. **Recovery.** While running, unbind and rebind the ISP's platform device
   (its `unbind` and `bind` under `/sys/bus/platform/drivers/`, as the vendor kernel names the
   driver; report it). Pass: health turns degraded,
   the driver retries with the delay doubling to 8 s, and comes back to `Ok` with frames flowing
   once the device is back.

## Not tested here, and known not to be

The ISP's input size limits per generation (the driver passes up to 8192 in each direction and
relies on the kernel's refusal at `start`), the crop and selection rectangles on the ISP's pads
(left at the vendor driver's defaults), image formats other than NV12 and NV16, ISP32 and every
other generation, HDR and multi-camera (`vir1`) modes.
