# D16 board run: receiver and front end frames reach a lemnosd client

Status: untested on board.

What changed. A module stream can be made with no pool (`LEMNOS_STREAM_CREATE_BUFFERS`), each
buffer a dma-buf of its own given with `LEMNOS_STREAM_IOC_BUFFER`. The receiver driver
(`drivers/rp1-csi2`) and the PiSP front end driver (`drivers/pisp`, `fe_*`) make their module
stream that way and hand the module the dma-buf of every buffer of the board's `frames` stream
they hold, so the block's DMA lands in the memory `lemnosd` hands the stream's consumer. Before
this both wrote only to a private pool: a client got `NOT_FOUND`, a stream with no producer, or
buffer numbers over memory the block never wrote. The host tests
(`drivers/rp1-csi2/tests/frames.rs`, `drivers/pisp/src/fe_device/frames_tests.rs`) and the QEMU
checks prove it against stand-ins; nothing here has run on the block.

## Setup

1. Take the board lock, `/run/lock/board-gpu.lock`, as AGENTS.md says. CM5 (Raze #2). Builds on
   NVMe or SSD. Load this branch's `lemnos.ko` with the camera front-end block in `owned=`.
2. Board file, receiver run: the `rp1-csi2` device with
   `[devices.streams.frames]`, `memory = "dma-buf"`, `heap = "linux,cma"`, `buffers = 8`, and
   `buffer_bytes` at least the `size` that `configure` answers (1 280 000 for 1280x800 RAW10
   packed). The sensor device (`ov9782`) with `link` to it, as in `docs/design.md`.
3. Board file, front end run: the same block as a `pisp-fe` device instead (the two can't run on
   one block), with `[devices.streams.jobs]` and `[devices.streams.frames]` (`memory = "dma-buf"`,
   `buffer_bytes` at least the `size` `set_output(2, ...)` answers). `PispFe` is not registered in
   `lemnosd` yet, so this run needs a build that adds it to the built-in list, or a small test
   binary that hosts it the way `frames_tests.rs` does with `LinuxHardware`.

## Checks, receiver

1. **Content, not just numbers.** Start the sensor streaming a test pattern (colour bars), then
   `configure` and `start` the receiver. Attach a `lemnos-client` consumer to `frames`, and for 100
   frames map the handle the attach reply carried for the frame's buffer and check the image is the
   pattern: not all zero, the bar edges at the same columns in every frame, and every buffer number
   0..7 seen. Pass: every frame. Record `lemnosd`'s CPU use at 1 ms ticks, CM5 timings only.
2. **Nothing armed, then armed.** `start` with no consumer attached. Pass: `counters().dropped`
   rises at the frame rate, `LEMNOS_RP1_CSI2_IOC_INFO` shows `streaming` and no error count, the
   kernel log is clean. Then attach the consumer. Pass: frames arrive within a few frame periods,
   with content as in 1. This is the first run of the block started with no address armed and
   armed later, which the stock driver also does but this module has only done on the fake block.
3. **Reattach without a stop.** With frames flowing, detach the consumer and attach a new one, ten
   times. Pass: each new consumer's first frames have correct content in its own memory;
   `LEMNOS_RP1_CSI2_IOC_INFO` never leaves `streaming`; the module's stream status stays open; the
   link is not restarted (no D-PHY bring-up in the kernel log); `/sys/kernel/debug/dma_buf/bufinfo`
   shows 8 buffers attached to the block after each round, not 16.
4. **A held buffer is not rewritten.** Keep one frame unreleased for a second while others flow.
   Pass: its bytes don't change; the others keep cycling.
5. **Stop and close release everything.** `stop`, then stop `lemnosd`. Pass: `bufinfo` shows
   nothing attached to the block, and unbinding the block returns.
6. **Wrong board file.** `frames` without `memory = "dma-buf"`, consumer attached: `start` answers
   `NOT_SUPPORTED`. `buffer_bytes` smaller than a frame: `INVALID_ARGUMENT`.
7. **Cache.** Record whether the consumer needs `DMA_BUF_IOCTL_SYNC` (read) around reading a frame
   on the CM5 to see the block's bytes.

## Checks, front end

1. **Content.** Sensor test pattern as above. `set_input`, `set_output(2, ...)`, `start`. Write a
   front end configuration (the library's `FrontEnd`, output 0 only, 16-bit) into config slot 0.
   The configuration region is still the driver's own memory (see "Not tested here"), so this
   needs the same debug hook D15's run uses for the back end. Post one job per `frames` buffer.
   Pass: every frame's buffer, read through its handle, holds the pattern; identities match.
2. **A job on a buffer the consumer holds is dropped, not run.** Pass: the driver's `dropped` goes
   up by one, the stream stays open (`LEMNOS_STREAM_IOC_STATUS`), the held frame is unchanged.
3. **Reattach.** Detach the `frames` consumer mid-stream and attach a new one. Pass: a job posted
   on a buffer the block had at that moment produces no frame for the new consumer; later jobs
   produce frames with correct content in the new consumer's memory; the front end is not stopped.
4. **Stop in flight.** `stop` with a job on the block. Pass: returns, `LEMNOS_PISP_FE_IOC_INFO`
   not wedged, `bufinfo` shows only what a running stream should.

## Not tested here

- The front end's configuration, statistics and output 1: still the driver's own memory, with no
  stream through which a client fills or reads them.
- A wedged block (DMA that never stops) on real hardware: the QEMU checks cover it on the fake
  block, where both buffers' dma-bufs stay attached and no memory can be swapped (`EIO`).
