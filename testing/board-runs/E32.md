# E32 board run: the Rockchip NPU (`drivers/rknpu`, `drivers/rknpu-sys`)

Status: untested on board. What has run on the PC: the layout tests (request numbers, the six
structures, flags and action ids; regenerated from `rknpu_ioctl.h` with `gcc` on x86_64 by
`drivers/rknpu/layout-check/run.sh`, and the sizes, key offsets and request numbers checked with
`clang --target=aarch64-linux-gnu`), the framing and request builders, and the claim, programs,
attachments, runs and confinement rules against a played kernel that maps objects into domains
the way `drivers/rknpu/` does (`cargo test -p lemnos-driver-rknpu`), and the session's refusals
against a regular file and a sysfs tree made for the test (`cargo test -p lemnos-driver-rknpu-sys`).
Everything was read from rockchip-linux/kernel `develop-6.1` at
`77168c8d5ab82399f65a80e9f807b50ba37cf483`, `drivers/rknpu/`, not from a running board.

Run it in a local session on an RK3588 board with the vendor kernel and the `rknpu`
DRM driver (`CONFIG_ROCKCHIP_RKNPU_DRM_GEM`), RK3568 second (one core, 32-bit DMA). Take
`/run/lock/board-gpu.lock`. Build on NVMe or SSD, never on the Github HDD. Module loads, unbinds,
rebinds and reboots are allowed; report each.

## 1. The node and the kernel build

```sh
for n in /sys/class/drm/renderD*; do echo "$n $(readlink $n/device/driver) $(readlink $n/device/iommu_group)"; done
dmesg | grep -i 'rknpu'            # "rknpu iommu is enabled, using iommu mode"
cat /sys/kernel/debug/rknpu/version 2>/dev/null
zcat /proc/config.gz | grep -E 'ROCKCHIP_RKNPU|CONFIG_NO_GKI|CONFIG_IOMMU_API'
fuser -v /dev/dri/renderD*         # who else holds the node
```

Record the render node whose driver is `RKNPU`, its IOMMU group, and the driver version. Record
every other process holding the node: confinement assumes the daemon is its only opener (the
kernel's domains are shared by every opener).

## 2. The claim

`lemnos_driver_rknpu::Service::new(lemnos_driver_rknpu_sys::NpuNode::new("/dev/dri/renderD129"))`
(the node found above), then `claim(now)`. Expect `Ok`, and record `claim.domains()`:
`PerProgram` when the kernel has `CONFIG_NO_GKI` and switches domains, `Shared` otherwise. Compare
with the config from step 1. With the IOMMU node disabled in the device tree (an overlay), expect
`ClaimError::NotConfined`.

## 3. Objects and domains

Load a framed program whose body is one task (any bytes; it is not run here) and attach two slots.
Then read `/sys/kernel/debug/iommu/` or the rockchip IOMMU's debugfs if present, and `dmesg` with
the driver's debug log on (`echo 8 > /proc/sys/kernel/printk`): each `MEM_CREATE` logs its domain
id. Expect program 1's objects in domain 1, program 2's in domain 2. Unload program 1 and check its
objects are gone (`/sys/kernel/debug/dri/*/gem_names` or the rknpu debugfs `mm` file). Drop the
claim and check nothing of the session is left.

## 4. A fault stays a fault

Load a program whose task 0 `regcmd_addr` is an address no object of its domain has (for example
`0xfff00000`), with an `int_mask` of `0x300`. Run it. Expect: an IOMMU page fault in `dmesg`
(`rk_iommu ... Page fault at 0xfff00000`), the job timing out and the block reset ("soft reset"),
the run completing as `Failed`, and the claim still working for the next program.

## 5. The question the source does not answer

Whether the block's register command stream can write the registers of its own IOMMU. From the
device tree, compare the NPU core's `reg` windows with its IOMMU's:

```sh
for n in /proc/device-tree/npu@*/ /proc/device-tree/iommu@*/; do echo "$n"; xxd "$n/reg"; done
```

If the IOMMU's registers sit inside a window the command stream addresses (on RK3588 the MMUs are
at offsets `0x9000`/`0xa000` of each core's `0x10000` window), build a program whose first command
writes the IOMMU's `DTE_ADDR` (offset 0) and read the register back over `/dev/mem` before and
after (`busybox devmem`). If it changes, a program can move its own page table and the driver's
confinement does not hold on that chip; say so in the report.

## 6. A real program

A program compiled for the chip by the caller, framed with its addresses as relocations, run on
two attached buffers. Compare outputs with the same program run elsewhere. Lemnos never compiles
or reads it; the caller brings the compiled bytes and the relocation table.
