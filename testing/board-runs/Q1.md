# Q1: addressable LED strip over the RP1 PIO block

Status: untested on board. The bit stream, reset gap, failed-transfer retry, allocation and program
words are covered by tests against a cycle-level model of the program (`drivers/ws2812/tests/pio.rs`,
`pio_alloc.rs`), and the backend's name, pin, clock and relocation checks by unit tests
(`backends/linux/src/pio_out.rs`). No frame has reached a real strip, and the PIO path has not been
run through the kernel module on a board.

Board: the reference board, with 16 LEDs on RP1 GPIO13. The board file names the strip
`bus = "pio-out:gpio=13"`, `count = 16`, `wire = "rgb"` (or `"rgbw"` for an RGBW part), and the
machine clock is 8 MHz, so one bit is 1.25 µs.

Before the run: the stock `ws2812-pio-rp1` driver must not be bound to GPIO13, since the module
takes the pin the stock way. Take the board lock named in `AGENTS.md`.

1. Probe GPIO13 while a frame is shown. Pass: a 1 bit is high 875 ns and low 375 ns, a 0 bit high
   250 ns and low 1000 ns, within 10%. The first bit starts 3 cycles (375 ns) after the first shift.
2. `set` a full red frame, then `show`. Pass: every LED is red, and none flicker.
3. `show` a frame whose last LED's blue bit is set, then probe the line after the frame. Pass: the
   line is low for at least 80 µs before the next frame's first bit.
4. Run `show` 1000 times in a row. Pass: every call returns OK and no LED changes between frames.
5. Unplug nothing, reboot nothing: a failed write must leave the frame in place, which the next
   `show` sends. Pass: after a forced failure (for example by stopping the module's PIO client),
   the next `show` after restoring it sends the same frame.

Timings: the zero bit's high time (250 ns) is at the low end of the WS2812 datasheet's tolerance
for its T0H. If the strip misreads zeros, the program's zero path is the first thing to check.
