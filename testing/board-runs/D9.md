# D9 board run: camera proof tool on the CM5

Status: untested on board.

Target: 120 fps with 0 drops over a soak on the CM5 (Raze #2), using the camera chain of a
sensor, a receiver and an ISP found from the board file, and frames saved to NVMe or SSD.

## Blocked until these land

The tool cannot complete on a board yet. Each item below is a known gap, not a fault in D9.

1. `LinuxBoard` provides no `StreamHandle`, so no in-process frame stream can be made for a
   receiver on a board.
2. `backends/linux-stream` `exactly()` refuses the kernel module's non-memfd ring, so a consumer
   cannot map frames the module makes.
3. The lemnosd wire does not carry a device's `link` (`engine/wire` and `service/lemnosd` have no
   field for it), so a client cannot follow sensor to receiver to ISP over `lemnosd`.
4. A PiSP front end is not in the lemnosd builtin list: the generator takes one driver name per crate, and `pisp-be` holds it.
   list, so the ISP leg of the assembly has no driver to bind on a board.
5. `camera-proof` is a library with no binary. `HostBus` runs in one process with simulated time.
   A board needs a `Bus` over `lemnosd`, and a command to run it.
6. There is no hotplug-to-bind path, so a USB camera (`camera.frames/1`) cannot be proven here.

## Steps once unblocked

Run by a local session, after the blockers above are resolved.

1. Take the board lock, `/run/lock/board-gpu.lock`, as AGENTS.md says.
2. Stop the old services, then start `lemnosd` with the board file for this camera.
3. Build the proof tool on NVMe or SSD, never on the Github HDD.
4. Assemble the camera in the 120 fps mode of the sensor's mode table, and capture a soak of at least
   60 s of frames, saving them to NVMe or SSD.
5. Record: frames, receiver `dropped`, sequence gaps, and the fps measured from timestamps. Pass
   means 120 fps within 1 percent, 0 dropped, and 0 gaps.
6. Record the CM5 figures here, with the command used and the dev `lemnosd` figures on the same
   scene for comparison.
