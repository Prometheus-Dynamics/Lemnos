# B20 board run: lemnos-orion publishes every device on the CM5

Status: untested on board. Run against a real Orion node (comm core and node logic, Orion `next`
at the revision `service/orion/Cargo.toml` pins) on a PC, with lemnosd on the simulated board:
see "The PC run" below.

The service has no code for any device, so the check is that each device lemnosd lists on the CM5
is a resource in Orion with its topics and actions, and that both sides coming and going are
followed. The host tests cover the mapping and the retries with a simulated lemnosd and an
in-process comm core and node logic.

Setup: lemnosd running on the CM5 with the board's file, and Orion's comm core and node logic
running (`orion comm`, `orion node`). Build `lemnos-orion` for aarch64 on the NVMe or SSD, not the
HDD, and run it under the board lock (`/run/lock/board-gpu.lock`) for the whole run. `orion` below
is Orion's command line, `--address` the comm core's socket.

1. Start `lemnos-orion` with `LEMNOSD_SOCKET` set, and `ORION_NODE_ID` set to the node's name.
   Pass: the log says `connected to Orion node <name>; N devices published`, with N the number of
   devices `lemnos-ctl list` shows, and no `not publishing` line.
2. `orion resource list lemnos.`.
   Pass: one `lemnos.<device>` resource for each device `lemnos-ctl list` names, of the kind
   `lemnos.device`. A device with no plain value item still has its resource and status topic.
3. For every device, compare `orion resource show lemnos.<device>` with `lemnos-ctl list`.
   Pass: a running device is `Ready`, one retrying or with failed health `Failed`, one off
   `Pending`; `orion topic read lemnos.<device>.status` shows the same state, health and reason.
4. For each value item, compare `lemnos-ctl read <device> <item>` with
   `orion topic read lemnos.<device>.values`.
   Pass: the values agree in the item's unit. Items that are not numbers or flags are absent from
   the topic and the log says so.
5. Change a value on the board (tilt the IMU) while `orion topic watch lemnos.<device>.values` runs.
   Pass: the new value appears within one second, with no restart of `lemnos-orion`.
6. For a device with a control item, `orion action run lemnos.<device>.set --resource
   lemnos.<device> --args "<item> <value>"`, then read it back with `lemnos-ctl`.
   Pass: the action ends `Succeeded` and the device holds the value. A value the item does not take
   ends `Rejected` with why.
7. `orion action run lemnos.<device>.power --resource lemnos.<device> --args off`, then `on`.
   Pass: `lemnos-ctl list` shows the device off, then running; the resource is `Pending`, then
   `Ready`.
8. Restart the comm core while `lemnos-orion` keeps running.
   Pass: within 10 s every resource is back `Ready` with its topics live, and the log says
   `connected to Orion node <name> again`.
9. Stop lemnosd (it needs the board lock as well), then start it again.
   Pass: while it is down `orion resource list lemnos.` is empty and `orion topic read` of a
   device's topic says its publisher is gone; nothing shows `running` from before. Within 30 s of
   lemnosd answering again every device is back with its values.
10. Start `lemnos-orion` with `ORION_NODE_ID` set to another name than the node's.
    Pass: the log says `not publishing`, and Orion holds no `lemnos.` resource.

## The PC run

2026-11-13, on the PC that builds Lemnos (no hardware touched): Orion `next` at `61e95a4`, built
from that revision, run as `orion comm` and `orion node` (node name `bench`) from one settings
file; `lemnosd --sim --board docs/examples/sim-board.toml`; `lemnos-orion` with `ORION_NODE_ID=bench`.
Every step above that needs no board passed:

- 1, 2, 3: `connected to Orion node bench; 6 devices published`. Six `lemnos.*` resources, the
  five running ones `Ready`, `lemnos.absent` (no bus on the simulated board) `Failed`, its status
  topic `retrying`, `failed`, `bind failed: Status(-2)`.
- 4: `lemnos.accel.values` read `x = 0 m/s²`, `y = 0 m/s²`, `z = 9.81 m/s²`, as the board file says.
- 6: `set` `target 1000` succeeded and `call` `peek` answered 1015 (the counter counts on each
  read); `set` `count 3` ended `Rejected: count is read-only`; `call` `fail` ended
  `Failed: refused (-5)`.
- 7: `power off` made the counter `off`/`manual` in `lemnos-ctl list`, the resource `Pending`, the
  status `off`; `power on` brought it back `Ready` with its count moving.
- 8: comm core stopped and started: `connected to Orion node bench again`, every resource back,
  values readable, `call` working. Node logic stopped and started: every resource back.
- 9: lemnosd stopped: `orion resource list lemnos.` empty at once; a reader holding the status
  topic read `state = gone`, `reason = lemnosd is not there`, never `running`; a new reader found
  the topic undeclared. lemnosd started again: all six back within 4 s, the held reader went on to
  `running`, and the first `call` after the return succeeded.
- 10: a second bridge with `ORION_NODE_ID=other` logged `not publishing`.

Two faults the run found were fixed before landing: the first action after lemnosd came back
failed with "not connected" (the call connection now reconnects), and a device not running when
the bridge connected never got its values or actions once it ran (the bridge now reads the
devices again).

## Detached form (image where lemnosd owns the USB link and the comm core serves the login)

Two steps cut the runner's own session on that image: step 8 restarts the comm core (the login is
its SSH), step 9 stops lemnosd (the gadget, and with it the network, is lemnosd's). Both run
detached, in `scripts/checks/B20.sh`; steps 1 to 7 and 10 run over the session as before.

- Step 8: `systemctl restart COMM_UNIT`; lemnosd stays up, so the watchdog is not involved. Measured:
  the time until `orion resource list lemnos.` again lists one resource per `lemnos-ctl list` device
  (0.25 s samples, up to 15 s), and the bridge's journal line `connected to Orion node ... again`.
  Timed restore: 25 s (the record's 10 s, the restart and margin); it starts the comm core again.
- Step 9: `systemctl stop lemnosd`; while down, one `orion resource list lemnos.` and one
  `orion topic read lemnos.<first device>.status`; then lemnosd is started again at once. Down
  window: the stop, two bounded reads (3 s each at most) and the start; measured 1.6 s in the
  rehearsal. Timed restore: 5 s. Then up to 30 s for every resource to come back.
- The comm core is `orion-comm.service` on the image (Orion's `packaging/systemd` at the pinned rev
  455a956e, with drop-ins in `orion-comm.service.d/`): the default of `COMM_UNIT`, which a run may
  override. The command line is `/usr/bin/orion` (`orion-bin` at 455a956e; `ORION_CLI` overrides).
  At that rev `resource list [PREFIX]` and `topic read TOPIC` exist as used here, and `--address`
  and `--timeout` are global options; the check passes `--timeout 2000` so each call ends inside its
  own 3 s bound (the client's default is 5000 ms). Resources are counted from the rows
  `lemnos.<device>  lemnos.device  STATE  on NODE`. The status topic counts as gone in the forms
  that rev prints: `nobody has declared` (the bridge withdraws it with the resource), `(its
  publisher is gone; these are the last values)`, or `state = gone`; a `state = running` line
  fails the step. The check refuses if the comm core's unit, the bridge or the command is missing,
  or if the resources do not match the devices before anything is touched.

Running it (shared by every detached form; `scripts/lemnos-check.sh`'s header has the details):

1. Upload `scripts/lemnos-check.sh`, `scripts/detached-lib.sh` and `scripts/checks/` to
   `/data/board/checks/bin/` over the session (not `/tmp`: the session's `/tmp` may be private to the
   comm core's unit, and the transient units would not see it).
2. Hold no board lock in the session: the check takes `/run/lock/raze-gpu.lock` and
   `/run/lock/board-gpu.lock` itself (10 s wait) and refuses, stopping nothing, if either is held.
3. As root: `bash /data/board/checks/bin/lemnos-check.sh start B20 [COMM_UNIT=orion-comm.service] [STEPS="8 9"] [ORION_CLI=/usr/bin/orion] [ORION_ADDRESS=<socket>]`. It copies the
   scripts into `/data/board/checks/B20/<UTC stamp>/bin/`, starts the check in the transient unit
   `lemnos-check-B20` and returns. The link then goes; nothing on the board depends on the session.
4. The check logs its hypothesis, a baseline and every step (CLOCK_REALTIME stamp and seconds since
   boot) to `log` in the run directory, verdicts to `result`. Before each stop it arms a timed
   restore in its own transient unit (`lemnos-restore-B20-NAME`) and sees it running; at the bound,
   uncancelled, the restore kills the check's unit, undoes what the check changed, starts lemnosd
   and the comm core (`COMM_UNIT`, default `orion-comm.service`) with backoff 1, 2, 4, 8, 8 ... s, never giving up, and checks the end state.
   The end state, checked by the check or the restore: lemnosd active, the `hw-watchdog` device
   `running ok`, the comm core and the bridge as before, the gadget bound to the same controller, no
   drop-in of ours, the link's addresses back, the same boot id. The address on `lemnos0` is
   systemd-networkd's (a runtime `.network` file written at boot, applied again when the interface
   comes back): the end check waits 30 s for it. One still missing then is added back by hand so
   the board stays reachable, and the run is FAILED: a recovery never lets a run pass. Nothing touches config.txt, the default slot,
   `mem=`, `.reboot-ok` or the watchdog.
5. Reconnect after 40 s and run `bash /data/board/checks/bin/lemnos-check.sh collect B20`: the
   log, the restore logs, the results, whether each restore was cancelled or fired, and whether the
   board reset since the baseline (`THE BOARD RESET`, from the boot id). Its first and last lines
   are the run's verdict: `RUN PASSED`; `RUN INCOMPLETE` when a step was not run; `RUN FAILED` with
   the reasons when a step failed, the board was not as found (an address re-added by hand
   included), the board reset, or a restore had to finish the check. Paste it here.

The watchdog: once slot-init has exec'd away, lemnosd's `hw-watchdog` driver is the only feeder of
`/dev/watchdog`. It feeds every half period and never writes the magic close. When lemnosd stops or
dies the kernel pings once on the close and logs `watchdog did not stop!`
(`drivers/watchdog/watchdog_dev.c`, `watchdog_release`); the board resets one period (15 s) after
that unless a new lemnosd feeds. A stop that hangs before it drops the driver leaves only what was
left of the last feed: half a period (7.5 s) at worst. Every lemnosd down window is therefore bounded
by its timed restore at `DOWN_BOUND_S` = 5 s, plus 2 s for lemnosd's start, under that 7.5 s; the
check refuses to start if the device's own `timeout` makes this false. The log says for each window
whether the close ping was seen and how long lemnosd was down. A lemnosd that cannot be started
inside the period (the backoff running past it) resets the board: expected, recorded by `collect`.

Status of the detached form: untested on board. Rehearsed on the PC against the stand-in board
(`scripts/rehearse/rehearse.sh ID CASE`: fake systemd with `Restart=always` and starts that fail
like a failed start job, the kernel's close ping, a 15 s watchdog that resets the stand-in): the
normal run; the check killed right after it stops lemnosd (the stand-in's `systemctl stop` freezes
the check at that exact point); the check frozen there; two failed starts (the restore retries 1
and 2 s apart and the board stays up); five failed starts (the backoff passes the period and the
stand-in resets, which `collect` reports as RUN FAILED); the link's address put back by networkd
(RUN PASSED) and not put back (re-added by hand, RUN FAILED). Three failed starts are the most a
restore survives inside one period.
