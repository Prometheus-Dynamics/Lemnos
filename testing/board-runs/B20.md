# B20 board run: lemnos-orion publishes every device on the CM5

Status: untested on board.

The service has no code for any device, so the check is that each device lemnosd lists on the CM5
appears in Orion with its values. The host tests cover the mapping and the retries with a simulated
lemnosd and an in-process Orion node. Nothing here has run on the CM5 yet.

Setup: lemnosd running on the CM5 with the board's file, and an Orion node named by `ORION_NODE_ID`
(its own default is `node.local`). Build `lemnos-orion` for aarch64 on the NVMe or SSD, not the
HDD, and run it under the board lock (`/run/lock/board-gpu.lock`) for the whole run.

1. Start `lemnos-orion` with `LEMNOSD_SOCKET` and `ORION_NODE_ID` set to the node's id.
   Pass: the log says `connected to Orion node <id>`, and no `not publishing` line appears.
2. List the devices lemnosd has (`lemnos-ctl list`), then list the Orion resources whose ids start
   with `lemnos.`.
   Pass: the two lists name the same devices, with one `lemnos.<device>` resource for each device
   lemnos-ctl lists. A device with no plain value item still has its resource.
3. For every device, compare its health and availability in Orion with its state in
   `lemnos-ctl list`.
   Pass: a running device shows `Available` and `Healthy` (or `Degraded` when lemnosd says so), and a
   device in retry or off shows `Unavailable`.
4. For each value item, read it with `lemnos-ctl read <device> <item>` and compare it with the status
   key of the same name on the device's resource.
   Pass: the values agree in the item's unit (the status holds the value scaled by the item's
   exponent, as `lemnos-ctl` prints it). Items that are not numbers or flags are absent from Orion and
   the log says so.
5. Change a value on the board (tilt the IMU, or read a counter that moves on each read) and watch
   the status key in Orion.
   Pass: the new value appears in Orion within one second, with no restart of `lemnos-orion`.
6. Leave a steady device unchanged for six minutes.
   Pass: its status keys are still present in Orion at the end. The refresh every 60 s keeps them
   inside the node's 300 s entry life.
7. Restart the Orion node while `lemnos-orion` keeps running.
   Pass: within 10 s the resources and their status keys are back in Orion, and the log shows
   `connected to Orion node <id>` again with no restart of `lemnos-orion`.
8. Restart lemnosd (it needs the board lock as well).
   Pass: the devices disappear from Orion while lemnosd is down, and they are back with their values
   within 30 s of lemnosd answering again. `lemnos-orion` keeps running throughout.
9. Keep a value changing for one minute, faster than Orion's local rate limit (256 messages per
   second per client).
   Pass: `lemnos-orion` logs `Orion refused a publish, retrying` at most a few times, it never logs
   `reconnecting` during the minute, and every device stays in Orion.
10. Start `lemnos-orion` with `ORION_NODE_ID` set to a node id other than the one Orion runs as.
    Pass: the log says `not publishing`, and Orion holds no `lemnos.` resource from this service.
