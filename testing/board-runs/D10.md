# D10 board run: exposure at frame cadence

Status: untested on board.

The question this run answers is whether a value posted at frame cadence latches on the frame it
was aimed at, and how close to the blanking window a post can be before it misses. The answer
decides whether D10's second half is needed. That half (the module running a prepared register
list at frame start) is not built. It is built only if this run shows posts missing latch frames
that a consumer cannot avoid by posting earlier.

Run in a local session after this PR merges, on the CM5 (Raze #2), with an OV9782 on the board and
the sensor's board entry from D8. Take the board lock named in `AGENTS.md`, `/run/lock/board-gpu.lock`.
Build on NVMe or SSD, never on the Github HDD. Report CM5 timings only.

## What the driver does, so the run can check it

- `post_values` writes the exposure under group hold: group 0 start, the three exposure bytes, group
  end, then group launch at the next vertical blanking (`0x3208` = `0xA0`).
- A group whose launch write completes inside frame `F` is latched at the start of frame `F + 1`
  and first shows on frame `F + 2`. One whose launch completes after frame `F + 1` starts first
  shows on `F + 3`.
- The mode table reports `exposure_delay` = 2 for every mode. This run checks that number.
- The ring path (a job read by a 1 ms poll, `VALUES_POLL_NS`) adds up to one poll of latency before
  the same group write. It cannot run on a board yet: `LinuxBoard` provides no `StreamHandle`. Step 1
  runs the call path, which exists today. Step 6 runs the ring path once that gap is closed.

## Setup

1. Power, the 24 MHz input clock and the reset line are the board's, with the sensor running.
2. Mode 0 (1280x800 RAW10, gated clock), default frame length 1822 lines. Frame period 17.42 ms.
   Record the frame period from the frame timestamps, not from the table.
3. A consumer that reads frame timestamps and mean brightness for each delivered frame, and that
   can post a call at a chosen time after a frame start. The brightness step between two exposures
   marks the first frame that shows a new exposure. Use exposures 16 lines (short) and 200 lines
   (long), so one frame shows a clear step.
4. Start the sensor, then wait for 60 frames before measuring, so the clock and the first-frame
   masking (`0x4242`, `FIRST_FRAMES_MASKED`) have settled.

## Checks

1. **Call path.** Post `post_values` through `lemnosd` and record, for each call, the post time, the
   time the reply came back and the frame it was aimed at. Pass: the reply comes back without error
   on every call, and the sensor reports `applied()` with the identity posted.

2. **Latch frame parity.** Post the short and long exposures alternately, one post per frame, at
   offsets of 0.5, 2, 4, 6, 8, 10, 12, 14, 15, 16 and 16.5 ms after the frame start. For each post,
   find the first frame whose brightness shows the new exposure. Record it as the observed landing,
   and compare it with the prediction: the frame the call completed in, plus 2. Pass: every post
   before the deadline in check 3 lands on the predicted frame, and every post after it lands one
   frame later. Record the count of mismatches in each class.

3. **How close a post gets before it misses.** Find the largest offset that still lands on the
   predicted frame. Record it, with the reply time minus the post time (the wire's own latency), and
   the group's bus time. The predicted deadline is the frame period minus the group's bus time
   (six transactions at the I2C clock), minus the wire latency and minus the poll interval for the
   ring path. Pass: the measured deadline is within 1 ms of the prediction. Report the margin, in
   milliseconds, between the last landing offset and the next frame start.

4. **Two posts in one frame.** Post two different exposures in the same frame, first at 4 ms and then
   at 12 ms. Record which exposure shows on the landing frame, and whether the first shows on any
   frame. Pass: the second shows, and the first never does, if the sensor latches only the last group
   before a frame start (the assumption the driver's tests make). A different result is a defect in
   that assumption, and the decision above depends on it.

5. **Line-blanking launch.** The sensor also has a group launch at line blanking (`0x3208` = `0x60`).
   Record whether it gives a later deadline than vertical blanking at the same posts. This is data
   only, and nothing in the driver changes unless the run asks for it.

6. **Ring path.** Once `LinuxBoard` has a `StreamHandle` and a consumer can push jobs, repeat checks
   2 and 3 with the consumer posting jobs on the values stream. Pass: the deadline moves earlier by
   the poll interval, within 0.5 ms. Measure the poll's CPU use in `lemnosd` at idle and at a 1 ms
   poll, and report it.

7. **Recovery.** Interrupt the sensor's bus while posting at frame rate. Pass: no post lands on a
   frame after the bus returns unless it was posted after the sensor reported healthy again.

## Decision

- If checks 2 and 3 pass, and the measured deadline leaves the margin a consumer needs, D10 is done.
  The second half is not built.
- If a post at a time the consumer can know is early misses its frame, the second half is needed.
  It is built as a separate PR, with its own review, not as part of D10.
- If check 4 fails, the driver's rule for two posts in one frame is wrong, and it is changed with its
  test before anything else.
