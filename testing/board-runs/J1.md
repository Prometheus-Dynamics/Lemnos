# J1 board run: the sensor's link is confirmed from the receiver's side

Status: untested on board. The bind check, the receivers' `source` and `layout` answers and the
buffer length accessors are proven in the gate's tests. None of it has run on a real camera.

The receivers answer from what the kernel shows, so the same board can answer differently by
driver. Check each on the reference board (CM5, the camera path) and on any other camera board.

## Checks

1. `lemnos-ctl describe cam0-receiver` lists `source` (9) and `layout` (10) on `camera.receiver/1`.
2. `lemnos-ctl call cam0-receiver source` on the reference board's `rp1-csi2` receiver: expect
   `NOT_SUPPORTED`. The module names no sensor, so the link is unknown.
3. `lemnos-ctl list`: the sensor `cam0-sensor` (`ov9782`) shows `degraded` with the reason
   `the kernel does not name this sensor`. This is expected for every `ov9782`: no kernel driver binds
   the sensor, so no kernel name exists to match. A `failed` row for the sensor means the receiver
   answered nothing wired; investigate the board's `link`.
4. `lemnos-ctl chain cam0-sensor` shows the sensor, receiver and ISP, each with the reason it is not
   `ok`, if any.
5. On a board whose receiver is `rkcif` or `sunxi-vin` with a kernel sensor entity wired into its
   graph, `call <receiver> source` names that entity. Expect the name, not `NOT_SUPPORTED`, and the
   sensor's link is then `confirmed` only when the sensor answers the same name from `identity`.
6. A `layout` call after `configure` returns the same `FrameLayout` `configure` returned, and the
   frame stream's buffer length (from a client's `FrameStream::buffer_len`) is at least `size`.

## Reporting

For each check, paste the command and its output. Times are not reported, only the results.
