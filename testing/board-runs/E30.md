# E30 board run: k230-capture (the ISP8000 frame path and CSI receiver, programmed directly)

Status: untested on board. What landed is `drivers/k230-capture-sys` (the `vvcam-mipi` request and
its 424-byte `DevAttr`, pinned by tests and by `layout-check/run.sh` against clang for host and
riscv64 and gcc; the frame path's register offsets; the table of frame-path registers a caller may
write, with masks; `FrameMemory`, `Planes` and `Capture`, which arms the memory interface only with
addresses of DMA memory it holds and checks every plane against every memory of the ring) and
`drivers/k230-capture` (`K230Capture`, a `camera.receiver/1` driver: link set through `vvcam-mipi`,
ISP input, windows and main-path format written through the table, a ring of three memories,
each frame copied into the frame stream with the driver's own sequence and the interrupt's time).
All of it passes its tests against stand-in devices and mocked streams. No request from this code
has reached a `vvcam-isp` or `vvcam-mipi` device.

Run in a local session after this PR merges, on a K230 board running the SDK's kernel
(`k230_linux_sdk` at `fc6cc21`) with the `vvcam-isp` and `vvcam-mipi` modules loaded and the vendor's
`isp_media_server` not running. Build on NVMe or SSD, never on the Github HDD. Module loads, unbinds
and reboots are allowed; report each.

## Before anything: the DMA memory

`K230Capture` needs the host's `dma` provider. `lemnosd` on Linux has none yet, so the driver does
not bind there. Until one lands, run the checks from a test program that builds `Capture` from
`lemnos-driver-k230-capture-sys` with a `DmaBuffers` implementation over the board's DMA heap
(`/dev/dma_heap/*`, contiguous, below 4 GiB) whose `device_address` is the bus address. If no heap on
the board gives memory with a known bus address below 4 GiB, stop here and record what the heaps
are: nothing else can be checked safely.

## Checks

1. **The nodes and the CSI request.** `ls -l /dev/vvcam-isp.0 /dev/vvcam-mipi.0`. Pass: both exist.
   `drivers/k230-capture-sys/layout-check/run.sh` with the board's own compiler (`CC=gcc`). Pass:
   `host: layouts match`. `MipiNode::set_link` with `DevAttr::csi(2, 0, 10, 800, w, h)` for the
   attached sensor's mode, after the sensor's own driver has set it up and before it streams. Pass:
   `Ok`, and `dmesg` shows the receiver configured with nothing reported as an error.

2. **The register map.** Through `Capture::read`, read `MIV2_CTRL` (`0x1300`), `MP_CTRL` (`0x1310`),
   `MIV2_MIS` (`0x16D0`) and the two shadows, `MP_Y_BASE_AD_SHD` (`0x1370`) and
   `MP_RAW_BASE_AD_SHD` (`0x13B4`). Pass: each returns `Ok`; with the path off `MIV2_CTRL` reads 0.
   These offsets come from the ISP8000's open register map (`github.com/nxp-imx/isp-vvcam` at
   `e6453233e67f5d2f180d6ec277158dd54fa67a25`, `mrv_all_regs.h`); the four that the K230 SDK also
   names agree. The others are not confirmed on this chip.

3. **The memory interface stays inside its memory.** This is the one place the design relies on
   the hardware: the memory interface's writes are bounded by each plane's base plus its size
   field, wrapping at the size. Provide the ring at the frame's exact size, surrounded by guard
   memory from the same heap filled with `0xA5` (one guard buffer allocated right before and right
   after each ring memory; check their bus addresses touch the ring's), start a raw 10-bit frame,
   take 100 frames, stop, wait `RELEASE_AFTER`. Pass: every guard byte still reads `0xA5`. Repeat
   with the sensor set to a mode one line taller than configured (the block given more lines than
   its size field allows). Pass: the guards are untouched. If any guard byte changed, the address
   path is not sound on this chip: record it and do not use the driver.

4. **The ring turns.** Start `Capture` as the driver does (`provide`, `start`, `rearm` on each
   frame end) and record, for 300 frame ends, the event's `MIV2_MIS` value and `Capture::active`.
   Pass: every frame end carries bit 0 (`MP_YCBCR_FRAME_END`) for a YUV format or bit 1
   (`MP_RAW_FRAME_END`) for raw, and `active` names memories 1, 2, 0, 1, ... in turn. If `active`
   returns `None`, the shadow registers read something other than the armed bases: record them.

5. **Each format.** For each of `bayer` at 8, 10 and 12 bits, `nv12`, `nv16`, `yuyv`, `bgr24` and
   `p010`, take a frame of a test scene (a colour chart, or the sensor's test pattern) and save it.
   Pass: it opens in a viewer as that format with the layout `configure` returned and the right
   colours. These register values are from the open map and are unconfirmed on this chip: the
   NV12 and YUV-format bits of `MP_FMT`, the RGB888 values of `MRSZ_FORMAT_CONV_CTRL` (record
   whether red and blue are swapped), raw 10 and 12 bits placed at the top of each 16-bit word
   (MSB aligned) with the raw byte swap, P010's 10 bits at the top, and the main path's
   `VI_DPCL` channel-mode bits (`0xC`; the SDK's own header names `0x7000`). Record every format
   that comes out wrong and how.

6. **Times and sequence.** Stream 600 frames at the sensor's rate with a consumer that returns
   every buffer. Pass: `sequence` runs 1, 2, 3, ... with no gaps, consecutive `timestamp_ns` differ
   by the frame period within 1 %, and each is within a frame period before the `CLOCK_MONOTONIC`
   time the consumer received it. Then stall the consumer for one second. Pass: `dropped` grows by
   about the frame rate, the gap shows in `sequence`, and frames flow again when it resumes.

7. **Stop and recovery.** Stop and start 20 times. Pass: each start delivers frames; `dmesg` shows no
   ISP or memory-interface error. While streaming, unload `vvcam-isp`. Pass: health turns degraded,
   the retries back off to 8 s and continue; after reloading the module, frames flow again within
   one retry.

8. **CPU cost.** At the sensor's largest mode, record the driver thread's CPU time per frame (the copy
   into the stream is one pass over the frame).

Record the results here, with the kernel version, the sensor and its mode.
