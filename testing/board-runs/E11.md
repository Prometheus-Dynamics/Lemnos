# E11 board run: k230isp (the K230's ISP8000 behind `vvcam-isp`)

Status: untested on board. What landed is `drivers/k230isp-sys` (the `vvcam-isp` request numbers and
structures, pinned by tests and by `layout-check/run.sh` against clang for riscv64; the register
map; the table of registers a caller may write and read; `IspNode`, whose reads and writes are
refused before any request unless the table allows them) and `drivers/k230isp` (`K230Isp`, a
`camera.isp/1` driver: a job's register list is checked whole, written, followed by the
`GEN_CFG_UPD` strobe, and the statistics registers of the second frame to leave the ISP after it
are copied into a statistics buffer). All of it passes its tests against a stand-in device and
mocked streams. No request from this code has reached a `vvcam-isp` device.

The driver does not deliver frames and does not set up the frame path (sensor, CSI, ISP input,
memory interface): it gives statistics only while something else runs frames through the ISP.
The board's frame path is still an open question (see `TODO.md` at `27cc96e`, "K230 frame path").

Run in a local session after this PR merges, on a K230 board running the SDK's kernel
(`k230_linux_sdk` at `fc6cc21`, kernel `ruyisdk/linux-xuantie-kernel` at `7d4e1f44`) with the
`vvcam-isp` module loaded. Build on NVMe or SSD, never on the Github HDD. Module loads and reboots
are allowed; report each.

## Checks

1. **The window and the node.** `cat /proc/iomem | grep -i 90000000` and `dmesg | grep "isp addr"`.
   Pass: the ISP's window is `0x90000000`, size `0x9000` (`regs::WINDOW_BYTES`). `ls -l
   /dev/vvcam-isp.0`. Pass: the node exists. If the size differs, stop: `access::WRITABLE` was
   checked against `0x9000`.

2. **The request numbers.** On the board, `drivers/k230isp-sys/layout-check/run.sh` with the
   board's own compiler (`CC=gcc`). Pass: `host: layouts match`. A program opens the node with
   `IspNode::open` and reads `regs::AE_V_SIZE` and `regs::HIST_BIN_0`. Pass: both return `Ok`.

3. **The table refuses.** The same program writes `regs::MIV1_CTRL`, `regs::FE_DMA_ADDR`,
   `regs::WINDOW_BYTES` and `u32::MAX` with `IspNode::write`. Pass: each is `InvalidInput`, and
   `dmesg` shows nothing new from the ISP (the request never reached it).

4. **The interrupt mask.** `regs::ISP_IMSC` (`0x5BC`) is inferred from the MRV layout, not stated by
   the vendor's headers. With the vendor's camera stack streaming (only for this check; the daemon is
   never used by Lemnos), `devmem 0x900005BC 32`, then `0x900005C0` and `0x900005C4`. Pass: `0x5BC`
   reads a mask with bit 1 (`MIS_FRAME_OUT`) set while frames run, and `0x5C4` (`ISP_MIS`) reads
   values that are a subset of it. If `0x5BC` reads something else, record it and do not run check
   6 until `ISP_IMSC` is corrected.

5. **The register map.** With frames running through the ISP (by whatever path is available on the
   board), read `ISP_AWB_GAIN_G`, `ISP_AWB_GAIN_RB`, `ISP_CC_COEFF_0..8`, `ISP_GAMMA_OUT_Y_0..16` and
   `AE_MEAN_0..24` through `IspNode::read`. Pass: the gains read near `0x100` per channel (1.0), the
   matrix near the identity at `0x80`, the gamma points rise, and the AE means change when the lens
   is covered. Record any register that reads constant 0; its offset may be wrong (the gamma points'
   offset and the colour offsets are marked unconfirmed in `regs`).

6. **A job and its statistics.** Bind `K230Isp` (`device` left at its default) to host streams:
   `config` of 4 buffers of `CONFIG_BYTES` (8196), `statistics` of 4 buffers of `STATISTICS_BYTES`
   (172). `start`. With frames running, fill config buffer 0 with one write
   `(ISP_AWB_GAIN_RB, 0x0200_0100)` and post a job naming it. Pass: within a second `counters()`
   shows `jobs` 1, a statistics buffer arrives with the job's identity, and the image (seen on the
   frame path's own output) turns red; `Raw::decode` of the buffer gives AE means that match
   `devmem` reads of `0x90002614..` taken right after.

7. **Frames and timing.** Post 100 jobs. Pass: `jobs` 100, `errors` 0; the published sequences rise
   by at least 2 per job; timestamps are on `CLOCK_MONOTONIC` and rise. If `errors` grows, record
   the frame rate: the driver counts a job as an error when two frames leave between its looks
   (1 ms apart).

8. **No frames running.** Stop whatever runs frames, post one job. Pass: after 2 s `errors` is 1 and
   the driver takes the next job. `dmesg` shows nothing new from the ISP.

9. **Recovery.** While running, `rmmod` the `vvcam-isp` module (or unbind the platform device), then
   load it again after 20 s. Pass: health goes degraded, attempts are spaced 250 ms doubling to 8 s,
   and after the module is back the driver runs jobs again with no restart of the host.
