# B15 board run: gpio-power-switch on the CM5

Status: untested on board. `drivers/gpio-power-switch` is covered by unit tests on the simulated
board (`backends/sim`). No line has been driven on real hardware. Take the board lock (`/run/lock/board-gpu.lock`, per `AGENTS.md`) before any run.

Setup: two USB ports on the CM5, each with its power switched by one GPIO output (GPIO 16 and
GPIO 20), and a device on each port that enumerates when powered. A board file device such as:

```toml
[[devices]]
id = "usb-a-power"
driver = "gpio-power-switch"
bus = "gpiochip0:20"
config = { default_on = true }

[[devices]]
id = "usb-c-power"
driver = "gpio-power-switch"
bus = "gpiochip0:16"
config = { default_on = true }
```

Use `default_on = false` on a run that should start with the port off. No fault input is wired in
this run, so `power.fault` is absent.

1. Bind `usb-a-power` with its default on and the port powered.
   Pass: bind succeeds, `power.on` reads 1, and the device on that port enumerates.
2. With a scope or logic probe on GPIO 20, unbind and bind `usb-a-power` again.
   Pass: the line stays high across the bind, with no low pulse.
3. Write `power.on` 0, then 1, to `usb-a-power`.
   Pass: the device on that port drops off the bus after 0, and returns after 1. Each write returns
   without waiting for the port.
4. Repeat checks 1 to 3 for `usb-c-power` on GPIO 16.
   Pass: as for check 1 to 3.
5. Bind `usb-a-power` with `default_on = false`, and check the port's state before any write.
   Pass: the line is low at bind and the device does not enumerate. A write of 1 powers it.
6. Force a line failure: hold GPIO 20 claimed by another process, then write `power.on` 0.
   Pass: the write reports `BUSY` on that call. Once the other process releases the line, the next
   write succeeds, and the device follows it.
