# B15 board run: gpio-power-switch on the CM5

Status: run on the board. Checks 1, 3, 4 and 5 passed on Raze #2 (2026-11-17) and check 6, as restated
below, passed on Raze #1 (2026-11-18); check 2 needs a logic probe and is not run. `drivers/gpio-power-switch`
is also covered by unit tests on the simulated board (`backends/sim`). Take the board lock (`/run/lock/board-gpu.lock`, per `AGENTS.md`) before any run.

Setup: two USB ports on the CM5, each with its power switched by one GPIO output (GPIO 16 and
GPIO 20), and a device on each port that enumerates when powered. A board file device such as:

```toml
[[devices]]
id = "usb-a-power"
driver = "gpio-power-switch"
bus = "gpiochip0:20"
config = { default_on = true }

[[devices]]
id = "usb-c-power"
driver = "gpio-power-switch"
bus = "gpiochip0:16"
config = { default_on = true }
```

Use `default_on = false` on a run that should start with the port off. No fault input is wired in
this run, so `power.fault` is absent.

1. Bind `usb-a-power` with its default on and the port powered.
   Pass: bind succeeds, `power.on` reads 1, and the device on that port enumerates.
2. With a scope or logic probe on GPIO 20, unbind and bind `usb-a-power` again.
   Pass: the line stays high across the bind, with no low pulse.
3. Write `power.on` 0, then 1, to `usb-a-power`.
   Pass: the device on that port drops off the bus after 0, and returns after 1. Each write returns
   without waiting for the port.
4. Repeat checks 1 to 3 for `usb-c-power` on GPIO 16.
   Pass: as for check 1 to 3.
5. Bind `usb-a-power` with `default_on = false`, and check the port's state before any write.
   Pass: the line is low at bind and the device does not enumerate. A write of 1 powers it.
6. A second process and GPIO 20, in two orders. The second process is `lemnos-line-hold`
   (`testing/crates/line-hold`): it claims the line through this repository's Linux backend and leaves
   its direction and level alone.
   Order A, the service first: with `usb-a-power` bound, start the second process on the line.
   Pass: the kernel refuses the second process (`EBUSY`), and the service's writes go on working.
   Order B, the second process first: start it, then start the service, write `power.on` 0, then end
   the second process and write again.
   Pass: while the line is held `usb-a-power` does not bind; its state names the line as busy and it
   retries on the host's backoff, capped at 8 s. A write is refused on that call, with the host's
   no-device status (the device is not bound). The port stays powered. After the second process ends,
   the device binds on its scheduled retry, inside the 8 s cap and with no restart, and the next write
   succeeds and the device on the port follows it.
   As first written: "Force a line failure: hold GPIO 20 claimed by another process, then write
   `power.on` 0. Pass: the write reports `BUSY` on that call. Once the other process releases the line,
   the next write succeeds, and the device follows it." That order cannot be staged on Linux: the kernel
   gives a line to one requester, the driver holds its line from bind, and a write on a held line cannot
   meet a second holder. The line being busy is met at the bind, so `BUSY` is in the device's state.

## Run on the CM5, 2026-11-17 (Raze #2, boot 0f80a3d6-6aa1-4814-ba3d-800bfff5dd06)

Board file: the bench file, with `usb-a-power` on `gpiochip15:20` and `usb-c-power` on `gpiochip15:16`. The record's
`gpiochip0` lines are not this board's: its USB power lines are on `gpiochip15` (RP1). Our `lemnosd` ran alone, under the
failsafe; the image's services were restored and compared with the baseline (`RAZE/bseries/B15*/` on the HDD scratch).

- Check 1: pass. `usb-a-power` binds with its default on, `out hi`, the count of USB devices is 2 (both enumerate).
- Check 2: not run. It needs a scope or logic probe on the line: a hands step.
- Check 3, usb-a: pass. `power.on` 0 returns at once (0 ms), the line goes `out lo`, the device count drops 2 to 1 within
  0.25 s. `power.on` 1 returns at once, and the count is 2 within 0.5 s.
- Check 4, usb-c on GPIO 16: pass for the same steps. `off` gives `out lo` on line 16 and the count drops 2 to 1 (the
  other device stays). `on` gives `out hi` and the count is 2 within 0.5 s. The two ports carry one device each (inferred
  from the counts: each switch removes one, and with usb-a off the count is 1).
- Check 5 (`default_on = false` on usb-a): pass. At bind the line is `out lo` and the count is 1 (only the usb-c device
  enumerates). The write of 1 powers it (the restore in the same run).
- Check 6 (a second process holds GPIO 20; write 0): not run. It needs a second holder of the line on the board, and this
  session has none. Not claimed.

Restore: lemnosd and lemnos-orion active, `systemctl --failed` 0, helios-engine active, the failsafe stopped.

## Check 6 on Raze #1, 2026-11-18 (pr/BOARD-R1, origin/next abd1d51b)

Board, as read before the run: Raze #1, serial 0708c973b00a37bc, a CM5 Rev 1.0, boot
d9559f52-e264-4544-ab5e-789b166a5af0. Its USB power lines are on `gpiochip15` (pinctrl-rp1), lines 20 and
16, as on Raze #2, with one USB device on each port (two in all). The image has no `gpioset`, python or
compiler, so the second holder is `lemnos-line-hold`, built static for aarch64 musl from this rev, copied to
the board's tmpfs with the run's stage and removed with it. Our `lemnosd` ran alone, on a bench file with the
two switches (`default_on = true`), behind a 900 s failsafe, both board locks held. The writes are
`lemnos-ctl call usb-a-power set false|true` (the contract's `set`). Rehearsed on the PC against
`lemnosd --sim` first, with the helper failing on a missing chip and with a stand-in holder (the sim has no
GPIO line, so its switch only ever retries).

Hypothesis, written before the run: order A, the helper exits 16; order B, the device retries with a busy
reason, the port stays powered, a write is refused on that call but not with the word `BUSY`, and after the
release the device binds within 8 s and follows writes. All of it held.

- Order A. With `usb-a-power` and `usb-c-power` `running ok` (both lines `lemnos`, `out hi`, 2 USB devices), the
  helper: `lemnos-line-hold: /dev/gpiochip15 line 20: Resource busy (os error 16)`, exit 16. The service was
  not disturbed: `set false` returned in 1 ms, line 20 `out lo`, 2 devices to 1 within 0.25 s; `set true`
  returned in 1 ms, `out hi`, 2 devices again within 0.75 s.
- Order B, held. The helper holds line 20 (`held /dev/gpiochip15 line 20`; the line reads `out hi`, as it was
  left). `lemnosd` starts: `usb-c-power` binds; `usb-a-power` is
  `retrying failed (retrying: attempt N, last reason: bind failed: busy, next try in ...)`, attempts 1 to 4 seen
  0.5, 2 and 4 s apart, the next due 8 s later. Two writes during the hold: `refused (-19): the call failed`, rc 1, in 1 to 2 ms.
  `read usb-a-power`: `usb-a-power is retrying: attempt 3, last reason: bind failed: busy`. The port stayed
  powered: line 20 `out hi` and 2 USB devices on all 24 samples over 12 s.
- Order B, released. The helper is ended (SIGTERM). `usb-a-power` is `running ok` 2.8 s later, on the retry that
  was already scheduled, with no restart of anything. `set false`: rc 0 in 1 ms, `out lo`, 2 devices to 1 within
  0.25 s. `set true`: rc 0 in 1 ms, `out hi`, 2 devices within 0.75 s. `power.on = true` at the end.

Result: check 6 as restated **passes**. Against the sentence as first written: the write does fail on that
call while the line is held, but with -19 (no device), not `BUSY`, and only in the order where the other
process came first.
