# C5: PIO through the module, on a board

Run on the board 2026-11-11, in board mode: passed after a fix to the module (a killed holder lived
for a minute). The A/B on the IMU bus was not run.

On the CM5, A/B of the IMU bus, the same PIO I2C program driven two ways: through `/dev/pio0` and through `LEMNOS_IOC_PIO_CALL` and `LEMNOS_IOC_PIO_XFER`:

1. Same IMU, same read pattern, many reads. Same data both ways.
2. Record read time and CPU for each.
3. Kill the holder mid-transfer: the state machines and programs are freed (a new claim can take them), no splat in `dmesg`.

## Result, 2026-11-11

Run 2026-11-11 on the CM5 (Raspberry Pi Compute Module 5 Rev 1.0, Raze #2), kernel `7.2.9-v8-16k`,
with `lemnos.ko`, `lemnosd` and the tools from PR F2a, built on NVMe and copied to
`/tmp/lemnos-run/` on the board. Raw logs are kept off the repository.

`lemnos_pio_check /dev/lemnos board`, with the product's own service that holds `/dev/pio0`
stopped for the run. Board mode takes a machine the RP1 firmware says is free and loads a loopback
program with no pins; the mock mode drives machines 0 and 1 whoever owns them (the product's PIO
I2C and the LEDs), so it is not run on a board.

- A free machine (1) at program offset 25; 2000 words back through it. Put plus get of one word:
  median 18.5 µs, p99 28.7 µs (first run); 17.5 / 18.5 µs (rerun).
- 64 KiB out and back by DMA in 4 KiB pieces: 2262, 2207, 2199 µs (first run); 2202, 2155,
  2152 µs (rerun). A bad pointer gives `EFAULT`; a drain with nothing sent times out and the
  channel then refuses with `EIO` until it is configured again.
- Kill the holder mid-transfer (check 3). First run: the machine and program space were freed, but
  the killed child lived about 60 s, because the transfer waited with
  `wait_for_completion_timeout`, which a signal can't end. Fix: the wait is killable
  (`kernel/lemnos_pio.c`), with a QEMU check that fails without it (63 s) and passes with it.
  Rerun with the fixed module: the whole check, kill included, took 0.49 s, 0 failed, nothing in
  `dmesg`.
- With the product's service running, the check fails at its first step (no free machine with room
  for the program): that service holds the PIO. Expected, and why it was stopped.

Checks 1 and 2 (the IMU's PIO I2C both ways) were not run: the backend's PIO I2C opens `/dev/pio0`
even when the module is loaded (C7), so there is no module route to compare yet.
