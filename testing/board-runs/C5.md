# C5: PIO through the module, on a board

Run on the board 2026-11-11, twice. Board mode passed after a fix to the module (a killed holder
lived for a minute). The A/B on the IMU bus passed in the second run, after the backend gained a
module route for PIO I2C and two fixes to it.

On the CM5, A/B of the IMU bus, the same PIO I2C program driven two ways: through `/dev/pio0` and through `LEMNOS_IOC_PIO_CALL` and `LEMNOS_IOC_PIO_XFER`:

1. Same IMU, same read pattern, many reads. Same data both ways.
2. Record read time and CPU for each.
3. Kill the holder mid-transfer: the state machines and programs are freed (a new claim can take them), no splat in `dmesg`.

## Result, 2026-11-11

Run 2026-11-11 on the CM5 (Raspberry Pi Compute Module 5 Rev 1.0, Raze #2), kernel `7.2.9-v8-16k`,
with `lemnos.ko`, `lemnosd` and the tools from PR F2a, built on NVMe and copied to
`/tmp/lemnos-run/` on the board. Raw logs are kept off the repository.

`lemnos_pio_check /dev/lemnos board`, with the product's own service that holds `/dev/pio0`
stopped for the run. Board mode takes a machine the RP1 firmware says is free and loads a loopback
program with no pins; the mock mode drives machines 0 and 1 whoever owns them (the product's PIO
I2C and the LEDs), so it is not run on a board.

- A free machine (1) at program offset 25; 2000 words back through it. Put plus get of one word:
  median 18.5 µs, p99 28.7 µs (first run); 17.5 / 18.5 µs (rerun).
- 64 KiB out and back by DMA in 4 KiB pieces: 2262, 2207, 2199 µs (first run); 2202, 2155,
  2152 µs (rerun). A bad pointer gives `EFAULT`; a drain with nothing sent times out and the
  channel then refuses with `EIO` until it is configured again.
- Kill the holder mid-transfer (check 3). First run: the machine and program space were freed, but
  the killed child lived about 60 s, because the transfer waited with
  `wait_for_completion_timeout`, which a signal can't end. Fix: the wait is killable
  (`kernel/lemnos_pio.c`), with a QEMU check that fails without it (63 s) and passes with it.
  Rerun with the fixed module: the whole check, kill included, took 0.49 s, 0 failed, nothing in
  `dmesg`.
- With the product's service running, the check fails at its first step (no free machine with room
  for the program): that service holds the PIO. Expected, and why it was stopped.

Checks 1 and 2 (the IMU's PIO I2C both ways) were not run: the backend's PIO I2C opens `/dev/pio0`
even when the module is loaded (C7), so there is no module route to compare yet.

## Result, 2026-11-11, second run (F2b)

Same board, with `lemnos.ko`, `lemnosd` and `lemnos-module-check` from PR F2b, and the product's
service that holds `/dev/pio0` stopped for the run. The backend's PIO I2C now goes through the
module's client of the PIO driver when the module is open (a claim on `pio-0`, which a holder that
dies lets go of), and through `/dev/pio0` otherwise (`backends/linux/src/pio_i2c/`,
`backends/linux-sys/src/rp1_pio.rs`). `lemnos-module-check board` reads register 0 of both IMU
chips on `pio-i2c:sda=8,scl=7` many times, on the stock route and on the module's, alternately.

1. Same data both ways in every round: 0x1E from the accelerometer (0x18), 0x0F from the
   gyroscope (0x68), the same value every read.
2. A register read, three rounds each way: stock median 144.1 to 144.2 µs, p99 164 to 169 µs,
   CPU 16.8 to 17.3 µs a read; module median 144.4 to 144.5 µs, p99 167 to 172 µs, CPU 22.6 to
   22.8 µs a read (all threads of the process). 0 allocations a read on both routes. The bus time
   dominates; the module route costs about 6 µs more CPU a read.
3. Covered by the board mode result above (a killed holder frees its machines and programs at once).

Then `lemnosd` on the C7 board file through the module: the IMU, power monitor and magnetometer
read values (acceleration x 9.83 m/s², bus 4.44 V, 2.19 W), and the daemon's descriptors are
`/dev/lemnos` and three claims, with no `/dev/pio0` and no `/dev/i2c-*`. With the module unloaded
the same file gives `/dev/pio0` and `/dev/i2c-1` twice and the same values.

What the first try of this run found, each fixed with a host test that fails without it:

- **A read allocated now and then** (`register reads allocate nothing` failed on the module
  route, 1 allocation in a steady run). The bus handed each transfer to its TX helper through a
  channel, whose blocking receive allocates the first time it has to wait. Fix: a mutex and a
  condition variable (`backends/linux/src/pio_i2c/bus.rs`).
- **A bus that never recovered on the module route.** A transfer that times out leaves its DMA
  channel refusing every later transfer (`EIO`) until it is configured again, and the bus's
  recovery did not configure it. Fix: the recovery sets the machine's DMA up again.
- The first try also read the daemon's chips right after start and got `AGAIN` (the power-up C7
  describes); the rerun waited for it.
