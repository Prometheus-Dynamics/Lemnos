# M37 board check: refused binds on the reference board (NOT RUN)

Purpose: confirm on the reference board (Raze #2, Compute Module 5) what M37 changes and could not prove off
board. That is the I2C chips' ID reads at bind (bmi088, bmm150, ina2xx, ov9782), the sensor's power-up order
(cam0-power before cam0-sensor's ID read), and that a device present on the board binds `running ok`, not
`retrying`. The check is read-only, and the board ends exactly as it started. It runs before any product pins M37.
Record the next rev under test at the top of the run's record.

## Rules

- Board: Raze #2 only. Take `/run/lock/raze-gpu.lock` and `/run/lock/board-gpu.lock` on the board with `flock`; if
  another run holds them (another project's batched run may), queue behind it. Never break or steal a lock.
- Never touch the default slot, `config.txt`, `mem=` or `.reboot-ok`. No reboot. If one is needed, stop and report.
- Services are stopped and started with `systemctl` only, in the order below, and only after the failsafe timer
  is armed. Processes are signalled only by PID, only PIDs this run started, each in `/tmp/lemnos-run/m37/pids`.
  No pkill or killall.
- The board's busybox has no `timeout` and no `taskset`. The script uses neither. Step 0 checks every command the
  script uses before anything else runs.
- Our files live under `/tmp/lemnos-run/m37/` only. aarch64 binaries, built on NVMe. Check the board's libc first.
- Report every change made and every change undone.

## The board file for the check

A copy of `testing/boards/reference.toml` keeps only the devices whose bind reads and changes nothing lasting:

- kept: `identity`, `imu` (bmi088), `mag` (bmm150), `power` (ina2xx), `cam0-power` (gpio-power-switch, needed for
  the sensor's power-up order; the supply is put back to its baseline level at the end, on if it was on), `cam0-sensor` (ov9782), `cam0-receiver`,
  `cam0-fe`, `cam0-isp` (present checks only; no stream is started), `cpu-thermal`.
- removed: `watchdog` (opening the node arms a watchdog that is never magic-closed; kept only under the watchdog
  rule below), `slots` and `reboot` (they
  write records and restart), `gadget` (configfs and USB state), `ring` (drives LEDs), `fan` and `fan-control`
  (drive the PWM).

## Steps, in order

The board's image runs `lemnosd.service`, `lemnos-orion.service` and `helios-engine.service` (probe of
2026-11-15: all active, `systemctl --failed` empty). So the check stops them for its window and starts them
again. The project lead approved this for this check only. Nothing is stopped before the failsafe in step 2 is
armed and seen.

0. Preflight, no changes. For every command the script uses, `command -v` must answer: `flock`, `systemctl`,
   `systemd-run`, `sleep`, `kill`, `cat`, `ls`, `readlink`, `grep`, `sed`, `date`, `mkdir`, `cp`, `rm`, `tar`,
   `gpioget` (optional: without it the supply level is read from the driver's own report instead). The script
   carries its own bound: it starts lemnosd in the background, records the PID, and a second background shell
   sleeps 120 s and sends that one PID a TERM. If any required command is missing, the run is NOT RUN and
   nothing has changed. Take the two locks here and hold them to the end.
1. Baseline, no changes. Record: boot id, kernel, loaded modules, the active unit list
   (`systemctl list-units --type=service --state=active --no-legend`), `systemctl --failed`, the main PID of
   `lemnosd.service`, and what it has open (`ls -l /proc/<pid>/fd`: I2C, GPIO, video, media and watchdog nodes).
   The units that need lemnosd: `systemctl list-dependencies --reverse lemnosd.service`, plus every unit whose
   process has the lemnosd socket open. `lemnos-orion` and `helios-engine` are expected in it; the list found on
   the board is the one used. The camera supply level as the running lemnosd reports it
   (`lemnos-ctl list`/`get` on `cam0-power`). Free memory.
   The slot state before the run: the active slot, each slot's state and the boot count, as the running
   lemnosd reports them (`lemnos-ctl` on `slots`, read only).
   If the running lemnosd holds a watchdog node, record its timeout and time left from
   `/sys/class/watchdog/*/`. See the watchdog rule below.
2. Arm the failsafe before stopping anything:
   `systemd-run --unit=m37-failsafe --on-active=600 --timer-property=AccuracySec=1s systemctl start
   lemnosd.service <the dependents from step 1>`. Confirm with `systemctl list-timers m37-failsafe.timer` that
   it is waiting. If it is not, NOT RUN. A session that dies at any point after this leaves a board that starts
   its services again by itself.
   The timer must never fire while our lemnosd is up, so the script keeps a time budget from the moment the
   timer is armed: the stops in step 3 must be done by 120 s, our lemnosd runs for 120 s and gets its TERM by
   250 s at the latest, it must be gone by 270 s, and the service starts in step 7 begin by 300 s. If step 3
   is not done by 120 s, our lemnosd is not started and the run goes straight to step 7 as NOT RUN. That leaves
   300 s of margin before the timer. The script records the time of each point against the budget.
3. Stop, with `systemctl stop` only, in this order: the dependents (helios-engine first, then lemnos-orion and
   any other found in step 1), then `lemnosd.service`. After each, `systemctl is-active` must say inactive.
   Record the time of each stop. Stop conditions checked here, each recorded as NOT RUN, followed by step 7:
   - a stock driver holds the camera sensor or the I2C chips after lemnosd is down;
   - the camera supply line is held by another process.
4. Run M37's `lemnosd` in the background with its own socket (`/tmp/lemnos-run/m37/lemnos.sock`), its own state
   directory under `/tmp/lemnos-run/m37/`, and the reduced board file. Record its PID. Start the 120 s bound
   from step 0 for that PID.
5. At about 15 s and about 90 s, take `lemnos-ctl --socket … list` and `lemnos-ctl --socket … health` (and the
   events), saved under `/tmp/lemnos-run/m37/`. Expected, and recorded as CONFIRMED or not:
   - `imu`, `mag` and `power`: `running ok` (ID read matched). A chip that is missing reads
     `retrying failed: no I2C chip … at 0x…` or the driver's own sentence; a wrong ID reads as failed with the ID seen.
   - `cam0-power` binds before `cam0-sensor`'s ID read, so the sensor binds `running ok`. If it reads absent,
     capture the order of the bind events (this is the power-up order check).
   - `cam0-receiver`, `cam0-fe` and `cam0-isp`: `running ok` (their nodes and blocks exist on this board).
   - `cpu-thermal`: `running ok`.
   - No `Status(-N)` anywhere in the list text.
6. The bound sends TERM at 120 s. Confirm by PID that our lemnosd has exited. Never send SIGKILL unless it is
   still alive 10 s after the TERM, and record it if that happens.
7. Restore, in reverse order, with `systemctl start`: `lemnosd.service`, then lemnos-orion, then helios-engine
   and the rest. Then compare with the baseline:
   - the active unit list equals the baseline list, and `systemctl --failed` equals the baseline (empty);
   - the camera supply is at its baseline level as the restored lemnosd reports it (on if it was on);
   - the slot state and the boot count equal the baseline (read the same way as in step 1);
   - no I2C, GPIO or video holder of ours remains; the modules match the baseline; the boot id is unchanged.
   Only when all of that is confirmed: `systemctl stop m37-failsafe.timer`, and check it is gone. If any line
   differs, leave the timer armed, report the difference, and do not retry by hand in a way that hides it.
   Last, copy the records off the board and remove `/tmp/lemnos-run/m37/`. Release the locks.

### The watchdog rule

The service's lemnosd may hold the hardware watchdog, and it never magic-closes it. Stopping the service then
leaves the watchdog running with nobody feeding it. So:

- If step 1 shows the running lemnosd holds a watchdog node, the reduced board file KEEPS `watchdog` on the same
  node, so M37's lemnosd feeds it for the window. The two handovers (service stop to our start, our TERM to the
  service start) must each be shorter than half the watchdog's timeout; the script measures both and records
  them. If the timeout read in step 1 is under 10 s, the run is NOT RUN.
- If a handover is missed, the board resets, boots its default slot and starts its services by itself. That is an
  unattended return, and it is recorded as a failed run with the boot id change, never as a pass. Before anyone
  runs anything else on the board, read the slot state and the boot count again and report what the reset did to
  them against the baseline.
- If the running lemnosd holds no watchdog node, `watchdog` stays removed as listed above. The probe of
  2026-11-15 points this way: systemd feeds `/dev/watchdog0` itself (RuntimeWatchdogUSec=15s, timeout 15), and
  the node is single-open. Step 1 settles it on the board: `ls -l /proc/1/fd` and the lemnosd PID's fd list,
  both read-only. If PID 1 holds it, stopping the services leaves the feeding untouched.
