# B14: fan-control

Status: untested on board. The control law, the timed holds, the retry backoff and the failure
paths are covered by the crate's unit tests and by host tests over simulated devices
(`drivers/fan-control`). No real fan has been driven by this driver.

Run on the CM5 with a real fan, bound through `hwmon-fan` (B12), and the controller
`fan-control` wired to that fan and to a thermal zone (B13). The board file looks like this:

```toml
[[devices]]
id = "fan"
driver = "hwmon-fan"
config = { name = "pwmfan" }

[[devices]]
id = "cpu-thermal"
driver = "thermal-zone"
config = { path = "/sys/class/thermal/thermal_zone0" }

[[devices]]
id = "fan-control"
driver = "fan-control"
uses = { fan = "fan", t0 = "cpu-thermal" }
config = { curve_t0 = "30000:300,60000:600,75000:1000", floor = 300, slew_per_s = 50, max_age_ms = 3000 }
```

The run needs the controller registered in the host's driver registry. That is not in this PR, so
the run waits for the PR that registers it. Until then the controller is not reachable from a
client. Take the board lock named in `AGENTS.md` (`/run/lock/board-gpu.lock`) before starting, and
build on NVMe or SSD, not the HDD.

Record the fan's `pwm1`, `pwm1_enable` and `fan1_input`, and each thermal zone's `temp` and
`policy`, before check 2. Those are the baseline for checks 9 and 10.

1. Baseline. Record, before any write, the fan's `pwm1`, `pwm1_enable` and `fan1_input`, the
   `temp` of `thermal_zone0`, and the fan's cooling device `cur_state`.
   Pass: every value is written to the run notes and nothing has changed them since.
2. Bind. Start the service with the board above and read the controller's description and state.
   Pass: `fan-control` is listed `available`, its description has `duty` and `demand`, and
   `degraded` is false.
3. Curve at idle. With the CPU idle, read `temp` and the controller's `state`. Work out the duty
   from the curve: at 30 °C it is 300, at 60 °C it is 600, and between points it is linear.
   Pass: `state.duty` and the fan's `duty` equal the curve's value for the read temperature, and
   never fall below the floor of 300, within one step.
4. Heat. Load the CPU until `temp` passes 60 °C, and read the state each second.
   Pass: `state.duty` rises to the curve's value in the same step as the temperature passes the
   point, with no delay, and `pwm1` at `fan1_input` rises with it.
5. Cool. Stop the load and read the state each second.
   Pass: the duty falls by at most 50 per-mille a second, then settles at the curve's value (or at
   the floor), and the run notes show the fall second by second.
6. Step timing. From the run's log of the state reads.
   Pass: the controller steps once a second, with no gap longer than 1.1 s, on the CM5. Record the
   largest gap and the mean. Timings are CM5 numbers only.
7. Hold. Hold the fan at 900 for 10 s with `hold(900, 10000)`.
   Pass: the duty reads 900 at once, reads 900 for the whole 10 s (`state.held` is true), and then
   comes down from 900 at the slew rate to the curve's value.
8. Failed sensor. Stop the thermal zone's device with `off` on the host (not the sysfs node), then
   keep reading the state.
   Pass: for the first 3 s the duty holds its last value. From the fourth second the duty is 1000,
   `state.degraded` is true and the controller's health is `degraded`. The controller keeps
   stepping throughout. Turn the zone back on with `on`, and the duty comes back to the curve's
   value within a few seconds with `degraded` false.
9. Disable. Disable the controller with `set_enabled(false)`.
   Pass: `pwm1_enable` and `pwm1` equal the step 1 baseline within a second, and the fan's
   `cur_state` and the zone's `policy` are back to the kernel's. Nothing is written while it is
   disabled.
10. Restart. With the controller enabled again, change its curve with `set_curve`, then restart the
    service.
    Pass: after the restart the controller's curve is the one in the board file, not the one set,
    and the state reads from a fresh start. No tuning file is kept.
11. Write failure. Make the fan's `pwm1` unwritable (a bind mount over it, the run's note records
    it), then read the state each second for 24 s.
    Pass: the controller's writes fail, the fan is handed back each time, and the next attempts come
    at 1, 3, 7, 15 and 23 s after the first. Health is `degraded` with the write-failed reason. The
    kernel's `pwm1_enable` equals the baseline while the writes fail. Remove the mount, and the next
    attempt takes the fan again.
12. Stop. With the controller running, stop the service with `SIGTERM`.
    Pass: after the process exits, `pwm1`, `pwm1_enable` and `cur_state` equal the step 1 baseline.
13. Kill (documents the gap). Start the controller and `kill -9` the service.
    Pass: the fan keeps the last duty it was given, because no code runs after `SIGKILL`. Restore
    the fan from the step 1 baseline by hand and record in the run notes that it was restored by
    hand. The watchdog and `ExecStopPost` hand-back for this case are not part of this PR.
