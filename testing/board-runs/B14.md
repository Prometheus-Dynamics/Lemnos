# B14: fan-control

Status: untested on board. The control law, the timed holds, the retry backoff and the failure
paths are covered by the crate's unit tests and by host tests over simulated devices
(`drivers/fan-control`). No real fan has been driven by this driver.

Run on the CM5 with a real fan, bound through `hwmon-fan` (B12), and the controller
`fan-control` wired to that fan and to a thermal zone (B13). The board file looks like this:

```toml
[[devices]]
id = "fan"
driver = "hwmon-fan"
config = { name = "pwmfan" }

[[devices]]
id = "cpu-thermal"
driver = "thermal-zone"
config = { path = "/sys/class/thermal/thermal_zone0" }

[[devices]]
id = "fan-control"
driver = "fan-control"
uses = { fan = "fan", t0 = "cpu-thermal" }
config = { curve_t0 = "30000:300,60000:600,75000:1000", floor = 300, slew_per_s = 50, max_age_ms = 3000 }
```

The run needs the controller registered in the host's driver registry. That is not in this PR, so
the run waits for the PR that registers it. Until then the controller is not reachable from a
client. Take the board lock named in `AGENTS.md` (`/run/lock/board-gpu.lock`) before starting, and
build on NVMe or SSD, not the HDD.

Record the fan's `pwm1`, `pwm1_enable` and `fan1_input`, and each thermal zone's `temp` and
`policy`, before check 2. Those are the baseline for checks 9 and 10.

1. Baseline. Record, before any write, the fan's `pwm1`, `pwm1_enable` and `fan1_input`, the
   `temp` of `thermal_zone0`, and the fan's cooling device `cur_state`.
   Pass: every value is written to the run notes and nothing has changed them since.
2. Bind. Start the service with the board above and read the controller's description and state.
   Pass: `fan-control` is listed `available`, its description has `duty` and `demand`, and
   `degraded` is false.
3. Curve at idle. With the CPU idle, read `temp` and the controller's `state`. Work out the duty
   from the curve: at 30 °C it is 300, at 60 °C it is 600, and between points it is linear.
   Pass: `state.duty` and the fan's `duty` equal the curve's value for the read temperature, and
   never fall below the floor of 300, within one step.
4. Heat. Load the CPU until `temp` passes 60 °C, and read the state each second.
   Pass: `state.duty` rises to the curve's value in the same step as the temperature passes the
   point, with no delay, and `pwm1` at `fan1_input` rises with it.
5. Cool. Stop the load and read the state each second.
   Pass: the duty falls by at most 50 per-mille a second, then settles at the curve's value (or at
   the floor), and the run notes show the fall second by second.
6. Step timing. From the run's log of the state reads.
   Pass: the controller steps once a second, with no gap longer than 1.1 s, on the CM5. Record the
   largest gap and the mean. Timings are CM5 numbers only.
7. Hold. Hold the fan at 900 for 10 s with `hold(900, 10000)`.
   Pass: the duty reads 900 at once, reads 900 for the whole 10 s (`state.held` is true), and then
   comes down from 900 at the slew rate to the curve's value.
8. Failed sensor. Stop the thermal zone's device with `off` on the host (not the sysfs node), then
   keep reading the state.
   Pass: for the first 3 s the duty holds its last value. From the fourth second the duty is 1000,
   `state.degraded` is true and the controller's health is `degraded`. The controller keeps
   stepping throughout. Turn the zone back on with `on`, and the duty comes back to the curve's
   value within a few seconds with `degraded` false.
9. Disable. Disable the controller with `set_enabled(false)`.
   Pass: `pwm1_enable` and `pwm1` equal the step 1 baseline within a second, and the fan's
   `cur_state` and the zone's `policy` are back to the kernel's. Nothing is written while it is
   disabled.
10. Restart. With the controller enabled again, change its curve with `set_curve`, then restart the
    service.
    Pass: after the restart the controller's curve is the one in the board file, not the one set,
    and the state reads from a fresh start. No tuning file is kept.
11. Write failure. Make the fan's `pwm1` unwritable (a bind mount over it, the run's note records
    it), then read the state each second for 24 s.
    Pass: the controller's writes fail, the fan is handed back each time, and the next attempts come
    at 1, 3, 7, 15 and 23 s after the first. Health is `degraded` with the write-failed reason. The
    kernel's `pwm1_enable` equals the baseline while the writes fail. Remove the mount, and the next
    attempt takes the fan again.
12. Stop. With the controller running, stop the service with `SIGTERM`.
    Pass: after the process exits, `pwm1`, `pwm1_enable` and `cur_state` equal the step 1 baseline.
13. Kill (documents the gap). Start the controller and `kill -9` the service.
    Pass: the fan keeps the last duty it was given, because no code runs after `SIGKILL`. Restore
    the fan from the step 1 baseline by hand and record in the run notes that it was restored by
    hand. The watchdog and `ExecStopPost` hand-back for this case are not part of this PR.

## Rehearsal on the PC against the sim (pr/B14-SIM)

Still untested on board. The rehearsal below is the one the board runner runs first, on the PC, against
`lemnosd --sim` built with `--features fake-devices` (the fake fan `fake-fan` and the fake thermal zone
`fake-thermal-zone` stand in for `hwmon-fan` and `thermal-zone`, with the same contracts and ids). Run:

```
testing/fan-control/b14.sh sim              # starts its own lemnosd --sim, stops it by PID
testing/fan-control/b14.sh board --socket PATH --temp-hook CMD --restart-hook CMD   # on the board
```

The board form takes the board lock and needs the operator's hooks: `CMD` for `--temp-hook` is given the
target in millidegrees and makes the CPU reach it; `--restart-hook` restarts the service. Samples go to
`OUT/samples.tsv`. The daemon-level test is `service/lemnosd/tests/fan_control.rs`.

Covered by the rehearsal: checks 2 (bind), 3 (curve at idle), 4 (heat, the 1.1 s step), 5 (cool, slew),
7 (hold), 8 (failed sensor, then the zone back on), and the restart (check 10, the curve after the
restart is the board file's). Not covered: 1 (the baseline, read off the board), 6 (the controller's step
gaps, which the board measures), 9 (disable), 11 (write failure, a bind mount), 12 (SIGTERM hand-back),
13 (kill). The rehearsal reads the real CPU's temperature nowhere: on the board the temp hook does that.

Proof on the sim, origin/next 25c49ab5 plus this PR: `b14.sh sim` gives `37 passed, 0 failed`. The
daemon-level tests: `cargo test -p lemnosd --features fake-devices --test fan_control` give `5 passed`.

Three places where the record's wording and the driver's behaviour differ, recorded here rather than
changed in the driver:

- Check 8, health. When the host turns the zone off, the host reports `fan-control` as `failed` with the
  reason `a required device failed`, not `degraded`. The controller's own state reads `degraded: true` and
  `duty: 1000`, which is the failsafe the check is about. The rehearsal accepts `degraded` or `failed`.
- Check 8, recovery. The duty falls to the curve at the slew rate of check 5 (50 per-mille a second), so
  from 1000 back to 450 at 45 C takes about 11 s, not "within a few seconds". The rehearsal allows 20 s.
- Check 4, the 1.1 s step, is measured by the rehearsal's reads on the host. The controller steps once a
  second (the sim shows one step a second, 50 per-mille each).

## Rerun on Raze #2, 2026-11-18 (origin/next 72c4274a): testing/fan-control/b14.sh, board mode, and checks by hand

Sim first: `b14.sh sim` passed 37 of 37 on the PC (lemnosd --sim, fake fan and zone). A copy with the zone held still
failed 8 checks and exited non-zero.

Board run (our lemnosd on testing/fan-control/board.toml, both locks held, image units restored; failsafe cancelled). The
temperature hook heats with four busy-loop processes on the board's own cores, each bounded (a 150 s window per call,
killed by its own killer), and stops them on the cool calls. Nothing ran on the PC. Result: **21 PASS, 16 FAIL**.
- The 20 C and 30 C curve checks and "settles at the curve's duty at 30 C" cannot pass: the board idles at 39 to 40 C,
  and the zone does not cool below ambient. These are environment FAILs.
- The 61 C heat (check 3) and the 70 C and 75 C curve points: four-core load plateaus at 58 to 60 C in 150 s (measured
  in bounded tests); 61 C was not reached on a sustained read, so these are environment FAILs too.
- Check 6 "back on within 20 s" and "back to 45 C on the curve before the fault", and check 7 "450 at 45 C after the
  restart": the samples file has no temperature column, so the reason is not determined from it. The hook log shows the zone
  at 44.7 to 49.6 C at its 45 C calls, against a curve value of about 450 at 45 C, so a zone that was not steady at 45 C is
  the likely cause, not checked. Recorded as FAIL; not attributed to the driver.
- **Finding, fan release:** after the controller stopped (the script's SIGTERM), pwm1 stayed at the last duty it wrote
  (255 at 1000 per mille) and the cooling state read 4. The baseline was pwm1 179, cooling state 0. Restored by hand to
  the baseline (pwm1 179, enable 1, cur_state 0, step_wise), read back. The release does not return the fan to the kernel's
  values; this is check 12's expected behaviour and it fails. Not fixed here.

Checks outside the script, by hand (our lemnosd, the same board file, fan restored to baseline after each):
- **Check 12, SIGTERM.** Held at 900 (pwm1 230, state 1); SIGTERM; read pwm1 255, state 4. **FAIL** (the same as above).
- **Check 9, set_enabled false.** Held at 900; disabled. pwm1 255 and state 4 one second later and four seconds later, not
  the baseline. Enabled again: the controller resumed (pwm1 105, state 0). **FAIL** for the disable restore.
- **Check 11, write failure.** A read-only bind mount over pwm1 (mounted and unmounted, no mount left). The state was read each
  second for 24 s; health was `degraded` or `failed` on every read, and each read exited 0. The attempt times at 1, 3, 7, 15, 23 s
  were not recorded (the reason text was not captured). **Partial**: the failure is visible, the schedule is not checked.
- **Check 13, kill -9.** Held at 900 (pwm1 230, state 1); SIGKILL; pwm1 230 and state 1 two seconds later. **PASS**: the fan keeps
  the last duty, as the record expects. Restored by hand to the baseline afterwards.
- **Check 1** is covered by the script's check 1 (PASS: fan-control listed running and ok, duty and demand described).
