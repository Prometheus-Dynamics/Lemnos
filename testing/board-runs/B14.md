# B14: fan-control

Status: untested on board. The control law, the timed holds, the retry backoff and the failure
paths are covered by the crate's unit tests and by host tests over simulated devices
(`drivers/fan-control`). No real fan has been driven by this driver.

Run on the CM5 with a real fan, bound through `hwmon-fan` (B12), and the controller
`fan-control` wired to that fan and to a thermal zone (B13). The board file looks like this:

```toml
[[devices]]
id = "fan"
driver = "hwmon-fan"
config = { name = "pwmfan" }

[[devices]]
id = "cpu-thermal"
driver = "thermal-zone"
config = { path = "/sys/class/thermal/thermal_zone0" }

[[devices]]
id = "fan-control"
driver = "fan-control"
uses = { fan = "fan", t0 = "cpu-thermal" }
config = { curve_t0 = "30000:300,60000:600,75000:1000", floor = 300, slew_per_s = 50, max_age_ms = 3000 }
```

The run needs the controller registered in the host's driver registry. That is not in this PR, so
the run waits for the PR that registers it. Until then the controller is not reachable from a
client. Take the board lock named in `AGENTS.md` (`/run/lock/board-gpu.lock`) before starting, and
build on NVMe or SSD, not the HDD.

Record the fan's `pwm1`, `pwm1_enable` and `fan1_input`, and each thermal zone's `temp` and
`policy`, before check 2. Those are the baseline for checks 9 and 10.

1. Baseline. Record, before any write, the fan's `pwm1`, `pwm1_enable` and `fan1_input`, the
   `temp` of `thermal_zone0`, and the fan's cooling device `cur_state`.
   Pass: every value is written to the run notes and nothing has changed them since.
2. Bind. Start the service with the board above and read the controller's description and state.
   Pass: `fan-control` is listed `available`, its description has `duty` and `demand`, and
   `degraded` is false.
3. Curve at idle. With the CPU idle, read `temp` and the controller's `state`. Work out the duty
   from the curve: at 30 °C it is 300, at 60 °C it is 600, and between points it is linear.
   Pass: `state.duty` and the fan's `duty` equal the curve's value for the read temperature, and
   never fall below the floor of 300, within one step.
4. Heat. Load the CPU until `temp` passes 60 °C, and read the state each second.
   Pass: `state.duty` rises to the curve's value in the same step as the temperature passes the
   point, with no delay, and `pwm1` at `fan1_input` rises with it.
5. Cool. Stop the load and read the state each second.
   Pass: the duty falls by at most 50 per-mille a second, then settles at the curve's value (or at
   the floor), and the run notes show the fall second by second.
6. Step timing. From the run's log of the state reads.
   Pass: the controller steps once a second, with no gap longer than 1.1 s, on the CM5. Record the
   largest gap and the mean. Timings are CM5 numbers only.
7. Hold. Hold the fan at 900 for 10 s with `hold(900, 10000)`.
   Pass: the duty reads 900 at once, reads 900 for the whole 10 s (`state.held` is true), and then
   comes down from 900 at the slew rate to the curve's value.
8. Failed sensor. Stop the thermal zone's device with `off` on the host (not the sysfs node), then
   keep reading the state.
   Pass: for the first 3 s the duty holds its last value. From the fourth second the duty is 1000,
   `state.degraded` is true and the controller's health is `degraded`. The controller keeps
   stepping throughout. Turn the zone back on with `on`, and the duty comes back to the curve's
   value within a few seconds with `degraded` false.
9. Disable. Disable the controller with `set_enabled(false)`.
   Pass: `pwm1_enable` and `pwm1` equal the step 1 baseline within a second, and the fan's
   `cur_state` and the zone's `policy` are back to the kernel's. Nothing is written while it is
   disabled.
10. Restart. With the controller enabled again, change its curve with `set_curve`, then restart the
    service.
    Pass: after the restart the controller's curve is the one in the board file, not the one set,
    and the state reads from a fresh start. No tuning file is kept.
11. Write failure. Make the fan's `pwm1` unwritable (a bind mount over it, the run's note records
    it), then read the state each second for 24 s.
    Pass: the controller's writes fail, the fan is handed back each time, and the next attempts come
    at 1, 3, 7, 15 and 23 s after the first. Health is `degraded` with the write-failed reason. The
    kernel's `pwm1_enable` equals the baseline while the writes fail. Remove the mount, and the next
    attempt takes the fan again.
12. Stop. With the controller running, stop the service with `SIGTERM`.
    Pass: after the process exits, `pwm1`, `pwm1_enable` and `cur_state` equal the step 1 baseline.
13. Kill (documents the gap). Start the controller and `kill -9` the service.
    Pass: the fan keeps the last duty it was given, because no code runs after `SIGKILL`. Restore
    the fan from the step 1 baseline by hand and record in the run notes that it was restored by
    hand. The watchdog and `ExecStopPost` hand-back for this case are not part of this PR.

## FAN-RELEASE (pr/FAN-RELEASE): the baseline return, and the board's temperatures

Still untested on board: this PR's sim proof is below, and the board rerun is the list at the end.

**Cause.** `release` (fan/1, method 4) puts the fan at full duty, which is the hwmon-fan safe state (pwm1 255). The controller's
`set_enabled(false)` and its drop (the daemon's SIGTERM) called it, so the fan went to full duty and the baseline the take-over
found (pwm1 179, pwm1_enable 1, cooling state 0) was never kept. The rerun above saw pwm1 255 and state 4 after SIGTERM and after
disable, and that is what the code did.

**Fix.** The ruling (the fan returns to its baseline on SIGTERM and on `set_enabled(false)`) needs two operations, because a
failed write still needs full duty:
- fan/1 gains method 5, `hand_back`, marked `#[added]`: the contract's base hash does not move (`docs/wire.md`, `contract_hashes`
  unchanged). `release` keeps its meaning, the safe state for a failure.
- hwmon-fan records `pwm1` and `pwm1_enable` at take-over, before its first write. `hand_back` writes `pwm1` (in manual mode) and
  then `pwm1_enable`, and keeps the baseline until both have worked. Nothing is written if it never took the fan.
- pwm-channel-fan records no baseline (its channel starts at full duty), so its `hand_back` is full duty.
- fan-control: `set_enabled(false)` and its drop call `hand_back`. A failed write still calls `release` (full duty), so
  check 11's write-failure path is unchanged.

**Sim proof.** The fake fan (`testing/crates/fake-devices`, fake-fan) starts at its baseline, 702 per mille (pwm1 179), records it
at take-over, releases to full duty, and keeps its duty in a file so a test can read it after the daemon stops.
- Before the fix, `service/lemnosd/tests/controller_on_fakes.rs` fails both new tests:
  ```
  test stopping_the_daemon_hands_the_fan_back_to_its_baseline ... FAILED
  assertion `left == right` failed: a stopped daemon hands the fan back to its baseline
    left: "1000"
   right: "702"
  test disabling_the_controller_hands_the_fan_back_to_its_baseline ... FAILED
  assertion `left == right` failed: set_enabled(false) hands the fan back to the duty it had before the take-over
    left: 1000
   right: 702
  ```

- After the fix: `cargo test -p lemnosd --test controller_on_fakes` gives `7 passed; 0 failed`.
- After the fix: `testing/fan-control/b14.sh sim` gives `41 passed, 0 failed` (it was 37; checks 9 and 12 are new).
- The unit and host tests of hwmon-fan (baseline restored: value then mode; a failed hand-back kept and retried; nothing
  written untaken), pwm-channel-fan (hand-back is full duty) and fan-control (disable and stop hand back, a failure
  releases) pass.

## B14-CURVE: write failure retries, the baseline after a fault, and the procedure for the board

**Causes (found on the PC, with the sim).**

- Check 11 stopped after three refused writes. The host counts `IO` statuses from one device in a row, and five
  in a row mark a device gone and bind it out (`Backoff`, health `failed`). A controller attempt makes two
  calls to the fan (the write, then the release), so three attempts reached five. The fan was then out of the
  controller's reach: its writes returned `NO_DEVICE` and were never logged. `hwmon-fan` maps a refused sysfs
  write (`EIO`) to `IO` as well, so the board does the same. The controller itself also reported duty 0 after a
  failed write.
- Check 12 failed after check 11 in one service start. A dropped fan instance leaves full duty on the fan. The
  next bind took that full duty as the baseline, so the stop handed back 1000 instead of 702. A fault
  (a real one, not only a refusal) had the same effect.

**Fixes.**

- A refused fan write is `AGAIN` ("try again later"), not `IO`, in `hwmon-fan` (`sysfs::write_number`) and in
  `fake-fan`. The host keeps the fan bound and the controller keeps retrying under the failure rule.
- The controller asks for the safe state (`release`, full duty) on each failed attempt and reports duty 1000
  while writes are refused, never 0. Its retry state (`retrying`) gives the attempt count, the reason and the time
  of the next attempt. The host shows it in the device's row.
- The fan's baseline is recorded per attribute, so a later bind after a drop gives the first take-over's baseline
  back, and a hand-back with no write yet still goes back to it.

**Fail-before lines** (each run once against the pre-fix behaviour, then restored):

- `drivers/fan-control`, `a_refused_write_is_retried_past_the_cap_on_sim_time_and_recovers`: `t=0: the safe state, not zero`, left 0 right 1000.
- `service/lemnosd/tests/controller_on_fakes.rs`, `a_fan_refusing_writes_past_the_host_limit_is_retried_and_handed_back_to_its_baseline`:
  with refusals as `IO`, `a refused write is not a gone device: the fan stays bound` fails (the fan is `Failed`).
- The same test with the health asserts off and refusals as `IO`: `left: "1000"  right: "702"` at the stop (the baseline is lost).
- `drivers/hwmon-fan`, `a_rebind_after_a_drop_keeps_the_baseline_the_first_take_over_recorded`: with the record never read, left `"255"` right `"77"`.

**Sim result.** `testing/fan-control/b14.sh sim --out ...`: `b14: 52 passed, 0 failed`. Check 11 ran in the same
service start as check 12. Its health row read `retrying: attempt 6, last reason: the fan write failed: released to full
duty, retrying, next try in 5228 ms`, and the retry gaps were 1000, 2000, 4001 and 8001 ms.

**Phases and checks.** `b14.sh` runs two phases. The FILE phase (`board.toml`, `sim-board.toml`) takes the curve,
slew, hold, sensor fault, disable, restart, stop and check 11 against a file-backed zone. The REAL phase
(`board-real.toml`, `sim-board-real.toml`) runs the controller on the real thermal zone under a bounded load and
checks the duty against the curve at the zone's own reading. Each check line says `[file]` or `[real]`.
The real phase has no fixed temperature targets; per the FAN-RELEASE ruling the record states idle ~40 C and load ~60 C.

**Hooks (renamed).** `--restart-hook CMD` is called as `CMD file` or `CMD real` and switches the board file.
`--stop-hook CMD` sends SIGTERM and returns when the process has exited. `--load-hook CMD` runs the bounded load
(REAL phase only; the busybox board has no `timeout`).

**What the board run does (operator steps, in order):**

1. Record the fan's baseline before any write: `pwm1`, `pwm1_enable` and the cooling device's `cur_state`, with the service stopped.
2. FILE phase. Start the service with `board.toml` (restart hook `file`). Run
   `testing/fan-control/b14.sh board --phase file --socket PATH --restart-hook CMD --stop-hook CMD --baseline-pwm N --baseline-enable N --baseline-state N`.
   Check 11 does not run inside the script on the board. Do it by hand in this same service start, before the stop
   that the script's check 12 makes: bind-mount a read-only copy of `pwm1` over the fan's `pwm1`, then sample
   `ctl list` every 0.25 s for 26 s. Record each new `attempt N` and its `next try in` value with the time. The
   expected schedule is attempts 1, 2, 3, 4, ... with gaps of 1, 2, 4 and then 8 s (each ended by the first
   controller step after it). Confirm the health row says `degraded` and the duty is never 0. Remove the bind mount,
   then confirm the duty is back on the curve within 25 s. Then the stop hook runs, and check 12 expects the fan at its
   baseline once the process is gone.
3. REAL phase. Restart with `board-real.toml` (restart hook `real`), then `b14.sh board --phase real ... --load-hook CMD`.
4. Every board step is reported with its check lines and its samples. The board lock (`/run/lock/board-gpu.lock`) is taken by the script.

**Consumer-visible changes.** A refused write from `hwmon-fan` and `fake-fan` now returns `AGAIN` (was `IO`). A
device whose writes are refused is no longer bound out by the host. The fan-control `duty` is 1000 while writes are
refused (was 0). After a recovery the duty falls from full at the 50 per mille per second slew limit.
The `retrying` state of `fan-control` appears in its row. No shared interface changed (`engine/abi`, `hal`,
`core`, `macros` are untouched).

**Not fixed here.** Other drivers that return `IO` for a refused write are still bound out after five in a row by
the host's containment; this change covers the fan drivers. A fan that is dropped and bound again in a new
daemon process still has no baseline record (the record is per process).
