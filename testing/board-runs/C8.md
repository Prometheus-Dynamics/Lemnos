On the CM5 (Raze #2), holding `/run/lock/board-gpu.lock` for the whole run, builds on NVMe:

1. Build `lemnos-module-check` for the board in release and debug, and `lemnos.ko` against the
   board's kernel. Use the same binary for every step below.
2. Pick, from the reference board file: one I2C bus with a real sensor on it (an address that
   answers, ideally a register it can read back), one SPI device on a real peripheral, one GPIO line
   that is free to drive (nothing wired that minds toggling), and one PWM channel if the board file
   has one. Give the measurement the bus names directly; on this board the simulated-chip directory
   argument has no use, so run only the `measure` part (adapt the addresses and register in
   `testing/crates/module-check/src/main.rs` on a local branch, or add a board mode there; do not
   run the QEMU checks against real devices, they write to fixed addresses).
3. Stock route: no module loaded, the SPI device bound to `spidev`. Record every `measure` line.
4. Module route: `insmod lemnos.ko owned=<the SPI device's compatible>`, bind the SPI device with
   `driver_override` and `bind`. Record every `measure` line.
5. Module loaded, SPI bound back to `spidev`: record the lines again (SPI stock, rest module).
6. Repeat 3 to 5 three times, alternating the order, and report median and 99th percentile per
   operation and route, plus allocations (expected 0). Report the bus clock used for I2C and SPI
   and the transfer sizes, so the wire time can be told apart from the software path.
7. Reference driver set on each route: run `testing/bench/bench.sh --real` against the reference
   board file once with no module loaded and once with `lemnos.ko` loaded and `lemnosd` opening
   it (the SPI device bound to the module). Compare the reference set's figures between the two;
   check with `ls -l /proc/$(pidof lemnosd)/fd` that the module run really holds `/dev/lemnos` and
   one `[lemnos-claim]` per device, and the stock run holds none.
8. Kill `lemnosd` with SIGKILL during the module run and start it again: it reclaims every device
   without `EBUSY` (claims ended with the holder). Report any module load, unload, bind or unbind
   done, and any reboot.

Write the numbers into `testing/bench/module.md` beside the simulated ones, marked as board figures.

## Result, 2026-11-11

Run 2026-11-11 on the CM5 (Raspberry Pi Compute Module 5 Rev 1.0, Raze #2), kernel `7.2.9-v8-16k`,
with `lemnos.ko`, `lemnosd` and the tools from PR F2a, built on NVMe and copied to
`/tmp/lemnos-run/` on the board. Raw logs are kept off the repository.

`lemnos-module-check` gained a board mode (`board i2c=BUS:ADDR:REG:BYTES held=BUS:ADDR
line=CHIP:LINE pwm=CHIP:CHANNEL`) that touches only what it is given: register reads, a held
address, a free input, and a PWM channel with its output off. Three rounds, alternating the order,
0 failed in each, 0 allocations everywhere.

| Operation | Stock, median / p99 | Module, median / p99 |
| --- | --- | --- |
| I2C register read, `i2c-1` 0x40, 1 byte out, 2 in | about 505.4 µs / 524 µs | about 505.6 µs / 525 µs |
| GPIO get, `gpiochip15:27` | 1278 ns / 1408 ns | 1241 ns |
| PWM configure (off), `pwmchip0:0` | about 25.1 µs / 33 to 40 µs | 3945 ns / about 4.5 µs |

SPI was skipped: the only SPI device is the boot EEPROM. The I2C figure is the wire's on both
routes; the module adds nothing measurable. PWM is one ioctl against several sysfs writes. Step 8:
SIGKILL of `lemnosd` on the module route and a restart took both claims again without `EBUSY`
(C7). Step 7 was not run in this session.
