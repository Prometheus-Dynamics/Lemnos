# B22 board run: the reference set on the CM5

Status: untested on board. The harness (`testing/bench/`) has run in simulation only: a dry run on
the build host, with `lemnosd --sim` and no hardware. Its board steps (the IMU run, the CPU windows,
the power readings and the USB port cycle) have not run against a real bus, so their first run is
this one.

Run in a local session after this PR merges. The session holds the CM5 (the bench's second board).
Take the board lock named in `AGENTS.md`
(`/run/lock/board-gpu.lock`); `bench.sh --real` takes it with `flock` before anything else and
refuses to run without it. Build on NVMe or SSD, never on the Github HDD (`bench.sh` checks both the
build directory and the output directory). Report CM5 timings only.

Commands. Run them from the repository on the local session:

```sh
testing/bench/bench.sh                                  # dry run: simulation only, no board
BENCH_TARGET=aarch64-unknown-linux-gnu \
BENCH_BOARD_SUDO="sudo -n" \
testing/bench/bench.sh --real --board USER@CM5-HOST     # the whole reference set on the CM5
```

`BENCH_TARGET` names the CM5's target triple, so the services built for it run there; a build on the
CM5 itself works too, with `BENCH_TARGET` unset. `BENCH_EXTRA_UNITS` adds unit patterns to stop when
the image's camera services run as separate units. The real run stops every service matching `lemnos*`,
records what it stopped in the output directory's `stopped-units.txt`, and starts those units again at
the end, whatever happens. Its output directory is printed at the end and holds `report.txt`.

The board file is `testing/bench/board.toml`. Before the run, check each bus name on the CM5 (the I2C
and SPI nodes, and `gpiodetect` for the GPIO chip). The USB power switches are on `gpiochip0` lines 16
and 20 in the file, as in B15. Confirm the chip number on the CM5 before the run.

1. Board lock and build location. Run `bench.sh --real` and watch it take the lock, then check the
   build directory and the output directory.
   Pass: the lock is taken before the first `ssh` call, and the storage check passes for both
   directories (neither is on a rotating disk).

2. The board file on the CM5. The real run first runs `lemnosd --check` on the CM5 build.
   Pass: `board.toml` parses on the CM5 (`measured` row `lemnosd.check`, status ok).

3. Old services stopped. Before the stop, the run lists the active `lemnos*` units.
   Pass: each listed unit is stopped (`systemctl is-active` reports `inactive` during the run), and
   `stopped-units.txt` names each one.

4. The devices bind. The report's `lemnosd on the bench board file` section lists every device with
   its state and reason.
   Pass: `imu`, `power0`, `fan`, `cpu-thermal`, `usb-c-power` and `usb-a-power` are `running`, or
   each one that is not running has its reason recorded. `fan-control` is expected to read `no driver
   named "fan-control"`: it is not registered in lemnosd yet (see check 11). `ring-pixels` and `ring`
   are disabled.

5. IMU at 200 Hz. The run reads the IMU for 9000 readings at 5 ms (45 s), each line stamped on the CM5.
   Pass: `imu.delivered` reads 9000 of 9000 (dev: 9000 or 9001 of 9000), `imu.misses` is 0 (dev: none),
   and `imu.largest_gap_ms` is recorded beside dev's 5.1-5.2 ms. `imu.repeats` is recorded beside
   dev's 0-5 of 9000 at 200 Hz. `imu.read_us` stays not measured: the watch returns values, not read
   times, so the check does not claim dev's 555-576 us.

6. lemnosd CPU at idle, 50 Hz and 200 Hz. Each figure is over a 30 s window (45 s for 200 Hz, during
   the IMU run in check 5).
   Pass: `cpu.idle_pct`, `cpu.50hz_pct` and `cpu.200hz_pct` are each measured and recorded beside dev's
   0.7-0.8 %, 1.4-1.5 % and 3.1-3.2 %. A figure more than half again dev's is a regression: explain it
   in the PR before the next one merges.

7. Memory and threads of lemnosd. Both are read after the 200 Hz run.
   Pass: `mem.pss_kb` and `threads.lemnosd` are measured. Dev has no lemnosd-only figure, so the
   report prints them without a dev comparison.

8. Binary sizes. Every service binary that built, from the CM5 build.
   Pass: `size.lemnosd` and `size.lemnos-ctl` are measured from the CM5 build (the note reads
   `CM5 build, target ...`), and the other service binary's row is present or its build failure is
   recorded.

9. Steady-state allocations. Nothing counts a lemnosd running on the board
   (`service/lemnosd/tests/alloc.rs` counts one in a test process on the build host).
   Pass: `alloc.steady_state` reads not measured, with its reason. It is recorded here as a gap, not
   claimed as zero.

10. Power readings. The power monitor is read with `lemnos-ctl read power0`.
    Pass: `power.readings` holds the bus voltage, current, power and die temperature, each as a
    value. Dev's figures (4.253 V, 2.953 W, 38.6 deg C) are from another board and are shown for
    scale only.

11. Fan steps. The curve steps of B14 need `fan-control` registered in lemnosd.
    Pass: `fan.steps` reads not measured, with the reason that the driver is not registered. Run B14
    after that registration lands, then this check's row can be measured.

12. Light frame rate. The ring write interval of B17 needs the status light registered and a strip
    fitted (`ring-pixels` and `ring` are disabled in the board file).
    Pass: `light.frame_rate` reads not measured, with its reason. Run B17 after registration.

13. USB port power cycle. The camera's port (`usb-a-power`) is switched off, then on. The sysfs USB
    device count is read before, after the switch is off and after it is on again.
    Pass: `usb.cycle` shows the count drop after the off, return after the on, and the switch on at the
    end. Dev's cycles are recorded as counts only, so no timing is compared.

14. Camera chain at 120 fps. Nothing on next drives a sensor, receiver, ISP or frame stream yet.
    Pass: `camera.fps`, `camera.drops`, `camera.latency_ms` and `camera.latch_frames` read not
    measured, with the reason. Dev's 120 fps with no drops stays a dev figure until the camera PRs land.

15. Restore. The run starts the stopped units again and stops its own lemnosd by PID.
    Pass: every unit in `stopped-units.txt` is `active` again, and no `lemnosd` process started by the
    run is left (its PID is killed by the script, not by name).

16. The report. The run prints the report and saves it to the output directory.
    Pass: every reference item appears with next's rows beside dev's figure and its source, and the
    two closing lists name the blocked items (allocations, the status light, fan steps, the camera chain)
    and the partial ones (IMU read time, the USB cycle, and the two that need their driver registered).
    Those lists are the gaps this PR reports. Nothing in them is claimed as working.
