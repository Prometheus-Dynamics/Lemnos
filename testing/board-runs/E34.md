# E34 board run: the K230 KPU (`drivers/k230-kpu`)

Status: untested on board. No operation of this crate reaches the block: the driver refuses to load
programs because nothing in front of the KPU confines a job to its own buffers (see
`drivers/k230-kpu/src/confine.rs`). What ran on the PC: the layout assertions (`layout.rs`, and
`drivers/k230-kpu/layout-check/run.sh` with `clang --target=riscv64-unknown-linux-gnu` and gcc on
x86_64) and `cargo test -p lemnos-driver-k230-kpu` (13 tests: the memory zone builders, the
confinement facts, the reach check against the board's reach and against per-job windows, the
backoff, the contract's refusals, no allocation). Everything was read from `kendryte/k230_linux_sdk`
at `fc6cc2151d54cb307be47f81815023f7ffb0eae6` and the kernel it pins
(`ruyisdk/linux-xuantie-kernel` at `7d4e1f444f461dbe3833bd99a4640e7b6c2cd529`), not from a board.

The board run confirms, on a K230 board (CanMV-K230) running the SDK's image, the facts the
refusal rests on. It changes nothing in the crate unless a fact is wrong. Build on NVMe or SSD,
never on the Github HDD.

## The node and what it offers

```sh
ls -l /dev/k230-gnne /dev/mmz
readlink /sys/bus/platform/devices/80400000.gnne/driver
ls /sys/bus/platform/devices/80400000.gnne/iommu_group 2>/dev/null || echo "no iommu group"
ls /sys/class/iommu 2>/dev/null
zcat /proc/config.gz | grep -E 'K230_GNNE|K230_MMZ|STRICT_DEVMEM|IOMMU'
grep -i gnne /proc/interrupts
```

Record: the bound driver (`k230-gnne`), that no IOMMU group or IOMMU class device exists, the
config lines, and the interrupt (189 in the device tree).

## The node takes no request

Open `/dev/k230-gnne` and issue any `ioctl` (for example request 0): expect `ENOTTY`. `mmap` on it:
expect `ENODEV`. Record both. Open it from two processes at once: expect both opens to succeed.

## The memory zone maps any physical page

As root, `mmap` one page of `/dev/mmz` at offset `0x80400000` (the KPU's register window) read-only
and read one word; then at an offset inside RAM that no allocation made. Expect both to succeed
(the kernel's `mmz_map` checks only that the range does not wrap). Do not write. Record the results.

## What does not need a board

The refusal itself: `Kpu::check` on any `Device` answering `Kernel::Gnne` is
`State::Unconfined`, and `Npu::load` answers `NOT_SUPPORTED`. A board cannot change that while
nothing is described in front of the block.
