# D15 board run: the back end's output 0 reaches a lemnosd client

Status: untested on board.

What changed: with a `frames` stream, the PiSP back end driver no longer points output 0 at its
own pool. It borrows the `frames` buffer a job names as a dma-buf (`StreamEndpoint::buffer_handle`),
registers it with the module for that job (`LEMNOS_STREAM_IOC_REGISTER`), points output 0's planes
into it, and unregisters it (`LEMNOS_STREAM_IOC_UNREGISTER`) when the job finishes, before the frame
is published. The host test (`drivers/pisp/tests/be_frames.rs`) proves this against a stand-in for
the block; nothing here has run on the block.

## Setup

1. Take the board lock, `/run/lock/board-gpu.lock`, as AGENTS.md says. CM5 (Raze #2).
2. Board file: the back end device with `[devices.streams.jobs]` and `[devices.streams.frames]`,
   the latter with `memory = "dma-buf"`, `heap = "linux,cma"`, and `buffer_bytes` at least the
   `size` `set_output(0, ...)` answers. Builds on NVMe or SSD.

## Checks

1. **Content, not just numbers.** The back end's input and configuration still come from the
   driver's own memory, which no client can fill yet (see "Not tested here"). For this check, fill
   them by hand on the board: write a flat grey RAW16 image into the driver's input region and a
   `simple_bayer` config into config slot 0 through a debug build that calls
   `BeStream::write_config`. Attach a `lemnos-client` consumer to `frames`, post one job per buffer
   naming output buffers 0..n, map each handle the attach reply carried, and check the Y plane of
   every frame is a constant near the grey level and not all zero. Pass: every frame, every buffer.
2. **Registration is released.** After 1000 jobs, `LEMNOS_STREAM_IOC_STATUS` is open, the back end's
   `refused` count is 0, and a further job still registers (no `ENOSPC`: a region not released
   would fill the 15 slots after 15 jobs).
3. **A job on a buffer the consumer holds is dropped, not run.** Keep one frame unreleased and post
   a job naming its buffer. Pass: the driver's `dropped` goes up by one, the module's `refused` does
   not, and the held frame's bytes are unchanged.
4. **Reattach.** Detach the consumer and attach a new one. Pass: the first job naming a buffer held
   from before is dropped, the next on the same buffer produces a frame whose content is correct in
   the new consumer's memory.
5. **Cache.** Record whether the consumer needs `DMA_BUF_IOCTL_SYNC` (read) around reading a frame
   on the CM5 to see the block's bytes.

## Not tested here

- The back end's input image and configuration: still the driver's own memory, with no stream
  through which a client fills them.
- The receiver (rp1-csi2) and the front end: their output 0 still goes only to the module's pool.
