# E21 board run: the K230 video codec block (`drivers/k230-vpu`)

Status: untested on board. What has run on the PC: the layout tests (the driver's private
request numbers, structures, control ids, formats and flags; the layouts also checked with `gcc`
on x86_64 and `clang --target=riscv64-linux-gnu` and `--target=riscv32-linux-gnu`), and the claim,
buffer, submit and completion logic against a played-back `mvx` node, on memfds
(`cargo test -p lemnos-driver-k230-vpu`, 25 tests). Everything was read from the Kendryte K230
Linux SDK at `fc6cc2151d54cb307be47f81815023f7ffb0eae6` and the kernel it builds
(`ruyisdk/linux-xuantie-kernel` at `7d4e1f444f461dbe3833bd99a4640e7b6c2cd529`,
`drivers/media/platform/canaan/vpu/`), not from a running board. No frame has reached the block.

Run it in a local session on a K230 board running that SDK's kernel with `VPU_CANAAN` built in or
loaded (`amvx`). The CM5 has no such block. Build on NVMe or SSD, never on the Github HDD. Module
loads and unbinds are allowed; report each.

## Checks

1. **The node answers.** `v4l2-ctl --list-devices`; `v4l2-ctl -d <node> --all` shows driver `mvx`,
   card `Linlon Video device`, `Video Memory-to-Memory Multiplanar`;
   `v4l2-ctl -d <node> --list-formats-out --list-formats` lists H.264, HEVC, JPEG and NV12;
   `ls -l /dev/dma_heap/`; `dmesg | grep -i mvx`. Record the kernel version and the heaps.
2. **The layouts on the board's compiler.** Compile the declarations from the board kernel's
   `mvx-v4l2-controls.h` with the board's compiler and print every `VIDIOC_S_MVX_*`, `sizeof` and
   the `offsetof`s `drivers/k230-vpu/src/uapi/tests.rs` pins. Pass: the pinned values (for example
   `VIDIOC_S_MVX_ROI_REGIONS` = `0xc0e856c1`, `sizeof(struct v4l2_mvx_color_desc)` = 46). Also
   say whether the image runs an LP64 or an ILP32 user space.
3. **A frame through JPEG and back.** As root (or with access to the node and the heap):

   ```sh
   LEMNOS_K230_VPU_HEAP=/dev/dma_heap/system \
     cargo test --release -p lemnos-driver-k230-vpu --test board -- --ignored --nocapture
   ```

   Pass: the test passes: the encoded bytes start with `ff d8` and end with `ff d9`, and the decode
   finishes without `V4L2_BUF_FLAG_ERROR`. Record what it prints: the formats and plane sizes the
   kernel answered on each side (the NV12 plane count must be 2), the encoded size, the time, the
   source-change event and the decoded first row of luma (it should rise in steps of 4 from 0,
   within JPEG's error). If the heap has another name, use it and record which. Run it three times.
4. **What the checks refuse, the kernel refuses too.** Not needed for safety, but `dmesg` must be
   clean of `Buffer plane too small`, MMU faults and `Failed to` lines from `mvx` during check 3.
5. **Sessions are confined.** With debugfs mounted, read the driver's `session/` directory under
   `/sys/kernel/debug/` (made in `mvx_ext_v4l2.c`) during check 3: each session lists only the
   buffers its own claim queued. Record the path and what it shows.
6. **Recovery.** While a loop takes a claim, encodes one frame and drops the claim, unload the
   module or unbind the device (report which), wait 20 s, and load or bind it again. Pass: `claim`
   answers `Device` and then `BackingOff`, with delays of 250 ms doubling to 8 s and holding there;
   once the node is back, the next due claim succeeds and frames encode again. Nothing panics and
   the driver never stops trying.

Record each result here.
