# E40: the IEP2 deinterlacer on the shared service layer, as `codec.block/1`

Status: untested on board. `lemnos-driver-rk-mpp` gained a second job type, the parameter
block, with the IEP2's facts (`struct iep2_params`, its descriptor words and the words the
kernel uses as indices, sizes, counts and modes); `lemnos-driver-rk-mpp-sys` checks that
chain shape again before the ioctl; `rk-iep` builds its jobs from planes checked against the
claim's measured buffers and serves them through `codec.block/1`. All of it runs against a
played kernel that does what `mpp_iep2.c` and `mpp_common.c` do with each message, through a
real `Host` with sealed memfds standing in for the stream's dma-bufs. No test opened
`/dev/mpp_service`, so nothing below has been seen to happen.

Facts were read from rockchip-linux/kernel `develop-6.1` at
`77168c8d5ab82399f65a80e9f807b50ba37cf483`: `drivers/video/rockchip/mpp/mpp_iep2.c`
(`iep2_extract_task_msg`, `iep2_process_reg_fd`, `iep2_addr_rnum`, `iep2_osd_cfg`,
`iep2_result`) and `drivers/video/rockchip/mpp/mpp_common.c` (`mpp_extract_reg_offset_info`,
`mpp_query_reg_offset_info`, `mpp_collect_msgs`).

Before running: take the board lock named in `AGENTS.md`. Builds go on NVMe or SSD, never on
the Github HDD. Module loads, unbinds and rebinds are allowed; report each. Use an RK3588 or
RK3568 board running the vendor kernel with `mpp_service` and `mpp-iep2` bound
(`ls /sys/bus/platform/drivers/mpp-iep2/`).

```toml
[[devices]]
id = "iep"
driver = "rk-iep"

[devices.streams.jobs]
memory = "dma-buf"
buffers = 16
buffer_bytes = 4194304
job_slots = 16
job_bytes = 20
```

## 1. Bind and claim

1. Start lemnosd. Expect the device `Running` and `/dev/mpp_service` not open until a job
   (`ls -l /proc/$(pidof lemnosd)/fd`).
2. Post one 1920x1088 NV12 `I5O2` job (a `TAG_CONFIG` item, fifteen references less the three
   Cr slots, no tuning). Expect `Done` with 412 bytes of read-back, and in
   `strace -e ioctl -f` one `MPP_IOC_CFG_V1` for the client type 28 (`MPP_DEVICE_IEP2`), then
   per job one call of three messages (`SET_REG_WRITE` 656 bytes, `SET_REG_ADDR_OFFSET`,
   `SET_REG_READ` 412 bytes, every one with flag `0x10` set) and one `POLL_HW_FINISH`.
3. Health stays `Ok`. If it says the block is not behind an IOMMU, record
   `/sys/bus/platform/drivers/mpp-iep2/*/iommu_group`: the claim refuses to run unconfined.

## 2. What the kernel does with the words

1. **Offsets by register.** Place each of the five frames at a different offset (multiples of
   4096) in one dma-buf. Pass: the output matches a software deinterlace of the same input
   (weave of the two fields for `I2O2` on a still picture is an exact check). If the output
   reads from offset 0 of every plane, the session's `REG_NO_OFFSET` path did not find the
   offsets: record `dmesg` and the kernel's `mpp_query_reg_offset_info` behaviour.
2. **The semi-planar Cr words.** The driver puts the chroma plane in each input's Cr word
   (the kernel translates it whatever the layout). Pass: an NV12 job's output is the same as
   with E17's layout, and no IOMMU fault is logged.
3. **The stride unit, the output chroma stride, the scratch size, extents with guard
   pages, the left-out mode and the results**: E17's checks 1 to 7, posted through the job
   stream.

## 3. Refusals reach no hardware

Post each of: nine OSD areas in the tuning item, mode 5 (`I1O1T`), a plane one byte past its
buffer, an offset at a buffer's end, a reference with a length, slot 15. Expect each
`Refused`, and in `strace` no `MPP_IOC_CFG_V1` for any of them.

## 4. Recovery

While jobs run in a loop, unbind the `mpp-iep2` platform device, wait 20 s, bind it again.
Report both. Pass: jobs come back `Failed` and health is `Degraded` with the service's
reason; claims are tried again behind a backoff from 250 ms doubling to 8 s and holding;
after the bind the next due job claims the block again and runs. The driver never stops
trying.

## 5. One consumer, one session

Close the consumer between two jobs (drop the stream). Pass: `/sys/kernel/debug/dma_buf/bufinfo`
loses the session's attachments when the consumer goes, and the next consumer's first job
opens a new session (`strace`).

## 6. No allocation

Under the counting allocator (a test binary on the board, built with `lemnos-measure`'s
`alloc-count`), 1000 jobs on a held claim: 0 allocations after the first.

Record anything else.
