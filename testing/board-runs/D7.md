# D7 board run: the PiSP front end

Run on the board 2026-11-11, twice. The second run (F2b) passed every check after two fixes to the
module (frames with no job uncounted; a stop mid-frame wedging the block); output 1's filter is not
the plain mean and passes at 99 % within one step. A statistics range of the wrong size can't be
posted through the driver and was not run.

Run in a local session after this PR merges, on the CM5 (Raze #2) with an OV9782 on `cam0` (i2c-10,
1280x800 RAW10 over 2 lanes at 800 Mbit/s, from a register file kept outside the repository). Take
`/run/lock/board-gpu.lock`. Module loads, unbinds and rebinds are allowed; report each. Build on NVMe
or SSD, never on the Github HDD. Report CM5 timings only.

## Getting the block

As the D5 board run: unbind `rp1-cfe`, load `lemnos.ko owned=raspberrypi,rp1-cfe`, set
`driver_override` to `lemnos-rp1-csi2`, bind. Check the probe mapped the fourth register window (the
front end's) by reading `hw_version` with `LEMNOS_PISP_FE_IOC_INFO`; report its value.

Drive the node directly, with a small program built on `kernel/test/lemnos_pisp_fe_check.c`'s job
and ring code (the camera proof tool, D9, replaces it): a pool of 8 CMA buffers, one configuration
dma-buf, one statistics dma-buf of 8 slots, the sensor started by its own driver. `drivers/pisp`'s
`FrontEnd` builds the configuration; 3A is the caller's, so fixed gains are fine here.

## Checks

1. **Statistics and output at capture rate.** RAW10 unpacked to 16 bits (the channel in front end
   mode), output 0 at 1280x800, stride 2560, AWB, AGC and CDAF statistics on, at the sensor's 60 fps,
   3600 frames. Pass: 3600 published, 0 `dropped`, 0 `errors`, 0 `stalled`; `written` equals frames
   published; the frame rate from the published timestamps; output 0's colour bars exact against the
   D5 run's rows; the statistics buffer decodes with `stats::Statistics`, and its AWB zones change
   when the sensor's pattern does. `DMA_BUF_IOCTL_SYNC` around every CPU read of the statistics and
   of output 0.
2. **Output 1 at the same time.** Output 1 at half size through downscale, same run length. Pass as
   above, with output 1's rows matching a software halving of output 0 within the block's rounding.
3. **Queue pressure.** Post jobs late for a while (one per two frames). Pass: `dropped` counts them,
   frames that were queued are intact, no wedge, and `stalled` stays small. Report `stalled`.
4. **Every stop path with DMA running.** At 60 fps: `STOP`; close the stream; close the node; unbind.
   Each must return, report not wedged, and the buffers must be free to reuse. Run each 200 times.
   Pass: 0 wedged, no `dmesg` errors, no corrupted buffer (a guard pattern outside the frame in each
   dma-buf unchanged).
5. **Bad configurations do nothing.** With the block idle and with it running: an address in a
   configuration, a statistics range of the wrong size, a stride larger than `START`'s. Pass: the
   stream ends with `EINVAL`, a later `START` works, the guard pattern intact.
6. **Restore.** `echo > driver_override`, rebind `rp1-cfe`, confirm its nodes come back.

## What this run must settle (guesses in the code)

Each of these is read from `pisp-fe.c` and `cfe.c`, and has never been observed by this code:

- `FE_STATUS == 0` for eight reads after `ABORT` means the block's DMA is finished. The stock driver
  checks once and warns; this module holds the pins on anything else. Measure how long the wait
  takes in every check above. A wedge on a clean stop means this rule is wrong.
- The channel in front end mode writes no memory of its own: the receiver's `ADDR` is `(0, 0, -1)`
  as in the stock driver, and nothing in the pool or registered buffers changes before the first
  front end write.
- Writing every configuration word every frame, ignoring the dirty flags, is safe while a frame is
  in flight: the block's shadow registers are latched at the next frame start.
- `QUEUE` is consumed at the next frame start, and `STATUS.QUEUED` is clear by the time the next
  interrupt arrives. `stalled` above measures this.
- Frames with no job queued write nothing.
- Statistics and output 16-byte alignment, and the output AXI settings (0xaf, 0x32, 0x8410, 0x140,
  0x4100) from the stock driver's and libpisp's values, are accepted; a block revision that differs
  will refuse nothing here and could misbehave.
- `ilines` at three quarters of each output is harmless: this module doesn't use the LINES
  interrupts beyond acknowledging them.
- The block's fourth memory resource is the front end's window, at least 0x2b0 bytes.
- Compressed output is written in blocks of 8 pixels of one byte each (the unit the stride check
  uses, the same as the back end's). The module refuses a compressed output whose stride can't hold
  that; whether the block ever writes more isn't known.
- A statistics crop, or an enabled AGC, AWB or CDAF grid, under 2 in either dimension, and a crop
  under 4 with decimation on, can lock the block. The stock driver says this only of a zero-sized
  crop; the module extends it. A real configuration refused with `EINVAL` here means this rule is
  too strict.
- Uncompressed 8, 10 and 12 bit outputs are refused because the stock driver doesn't offer them; the
  block may well write them.
- The block sees the same addresses `dma_buf_map_attachment` gives through the RP1's bus mapping.
  Whether RP1's memory traffic is coherent with the CPU has not been measured; the consumer syncs.

## Not tested here

- Anything concurrent with the back end (D6), and the full proof pipeline (D9).
- More than one virtual channel, and compressed output 0.
- A sensor other than the OV9782.

## Result, 2026-11-11

Run 2026-11-11 on the CM5 (Raspberry Pi Compute Module 5 Rev 1.0, Raze #2), kernel `7.2.9-v8-16k`,
with `lemnos.ko`, `lemnosd` and the tools from PR F2a, built on NVMe and copied to
`/tmp/lemnos-run/` on the board. Raw logs are kept off the repository.

The receiver's block bound to the module as in D5, and `lemnosd` with the block as a `pisp-fe`
device instead of `rp1-csi2`: `config = { device = "1f00110000.csi", lanes = 2, mbps = 800,
data_type = 0x2b, job_slots = 8 }`, `config` 4 × 632 bytes, `statistics` 4 × 23200 and `output0`
4 × 2048000, both dma-buf from CMA. The client was `lemnos-fe-proof`
(`testing/crates/camera-proof/src/bin/lemnos-fe-proof.rs`): one configuration from the library's
`FrontEnd` (output 0 at 16 bits, AWB, AGC through RGB to Y, and focus statistics) in every config
buffer, and a job kept queued on each of the four buffers. `hw_version` reads 0x00114666 once a
stream has run (0 before, as the driver documents).

1. Colour bars, 3600 frames: 57.367 fps from the timestamps, 0 frame starts with no job queued,
   3600 statistics frames, each carrying the identity of its output frame, counters `jobs 3600,
   dropped 0, errors 0`. Output 0 of the first frame against the receiver's frame of the same
   pattern: 800 of 800 lines equal, each 10-bit value moved up 6 bits. The statistics decode: on
   the bars AWB counts 256000 pixels with means 15959 on all three channels and the AGC histogram's
   mean bin is 511.6; on the scene the means are 4171, 4168, 4185 and the mean bin 65.3. The same
   at frame lengths 911 to 4001 (D8), 600 frames each: no frame start without a job, every
   statistics frame matched.
2, 3. Not run.
4. `STOP` with four jobs queued: 5.2 to 5.4 ms, 11 times, not wedged; a start right after gave 30
   frames and 30 statistics. The four jobs posted before each stop run after the start, so the
   client's next four, naming the same buffers, are dropped (`dropped 4`), as the driver says.
   Closing, node close and unbind 200 times were not run.
5. Not run.
6. Restored: `driver_override` cleared, `rp1-cfe` bound again, its nodes back, the product's
   camera running.

## Result, 2026-11-11, second run (F2b)

Same board, setup and client as above, with `lemnos.ko`, `lemnosd` and `lemnos-fe-proof` from PR
F2b. The board file adds an `output1` stream (4 × 516096 bytes, dma-buf), gives `output0` 4096
bytes past each frame (4 × 2052096) for a guard, and has 8 `config` and 8 `statistics` buffers so
refused jobs can name buffers of their own. Raw logs are kept off the repository.

1. Again with output 1 on: colour bars, 3600 frames at 57.367 fps, 0 frame starts with no job,
   3600 statistics and 3600 output 1 frames, each with its output frame's identity, counters
   `jobs 3600, dropped 0, errors 0`, `stalled 0`.
2. Output 1 at 640x400 through the Bayer downscaler (2 in, 1 out each way), stride 1280. Against
   a software halving of output 0 (each pixel the mean of the four of its colour in its 4x4 block):
   on the bars 254400 of 256000 pixels equal, the rest at the bars' 7 edges, where the block gives
   three quarters of the step rather than half (its filter reaches the neighbouring pixel of the
   colour); on the scene 104995 equal and 255619 (99.85 %) within one 10-bit step, the largest
   difference 20448 at sharp edges. A least-squares fit puts almost all the weight on the four
   pixels of the box, with a little on their neighbours. The block's filter is not the plain mean
   and its exact kernel was not identified; the proof now passes at 99 % within one step.
3. **Failure found:** one job posted per two frames (each a frame period after the frame before
   arrived), 600 frames: every frame queued was intact (equal to the first frame of the bars), but
   `dropped` stayed 0 with 813 frame starts that had no job. The front end with nothing queued
   starts no frame and raises no interrupt, so the module's count at its own frame start never saw
   them. Fix (`kernel/lemnos_rp1_csi2.c`, `kernel/lemnos_pisp_fe.c`): the receiver's frame start on
   the channel feeding the front end is handed to the front end first, and a frame the receiver
   started and the front end did not by the next one is counted as dropped; QEMU check
   `test_frames_with_no_job`. On the board after the fix: `dropped +813` for the 813 frame starts
   the timestamps show, `errors +0`, `stalled +0`, 0 frames differing. `stalled` is now in
   `isp.pisp` `info()` (it was not observable through the driver): 0 in every run here.
4. **Failure found:** `STOP` with four jobs posted and the block writing, 200 times: the sixth
   wedged the module (`PiSP front end did not stop; buffers stay pinned until reboot`), `STATUS`
   stayed `0x5` (queued and active) for good, and the board was rebooted to recover. The stop cut
   the channel first, as `cfe_stop_channel` does, so the block was left mid-frame waiting for lines
   that never came, and `ABORT` doesn't end that. Fix (`lem_pisp_fe_stop`): `ABORT` while the
   channel still feeds the block, wait for idle, then stop the channel; a block still busy then is
   reset, as `pisp_fe_start` resets every block, and only a block that stays busy after that is
   wedged. QEMU check `test_stop_mid_frame` (the test block models a front end that stays active
   until reset, or until an abort while fed); it fails on the old order. On the board after the
   fix: 200 stops with four jobs posted, a stop 5 to 41 ms after the posts, median 5.5 ms, max
   5.6 ms, each followed by a start and 3 frames, 200 of 200; no reset was needed and nothing
   wedged. Then 200 each, waiting each time for the client's first frame: the client killed
   (streams closed), `lemnosd` killed (the node closed; a new daemon each time), and the
   receiver's block unbound and bound again under a streaming `lemnosd`: 200 of 200 streamed
   after each, the slowest first frame 210 ms, and the only kernel messages were the 201 probes.
   The guard: the 4096 bytes past every `output0` and `output1` frame were still zero after
   every run.
5. Refused configurations, through the driver (it drops them before the module sees them): an
   address field (`stats_buffer.addr_lo = 16`), `ilines = 1`, and output 0's stride 64 bytes
   larger than set. With the block running between good jobs: `dropped +3`, `errors +0`, 60
   frames, no frame start missed. Posted while stopped and taken after the start: `dropped 3` at
   frame 20, 30 frames after the start. A statistics range of the wrong size can't be posted
   through the driver, which makes the ranges itself: not run.
