# A23: stream buffers as dma-bufs

Status: untested on board. `StreamEndpoint::buffer_handle` is covered on the mock, on the host's
own stream with unnamed files and sealed memfds behind the buffers, and, on the build machine
only, with dma-bufs from `/dev/dma_heap/system` (allocation, CPU mapping with the sync calls, the
handle lent, the size check against the dma-buf's real size). The engine in every one of those
runs is a stand-in that counts jobs. No request built from a stream buffer's handle has reached a
G2D engine or any other block, and lemnosd does not yet make streams of dma-bufs: its streams
stay one memfd, and `buffer_handle` answers `Unsupported` there.

What only a board can show:

- that the engine takes a dma-buf from the heap the stream's buffers come from (the BSP engine
  may want `linux,cma` or a vendor heap rather than `system`);
- that what the engine wrote is what the consumer reads through its own mapping of the same
  dma-buf, with no cache trouble between the two;
- that a dma-buf a consumer has left behind is still safe for an engine to finish writing.

Before running: take the board lock named in `AGENTS.md`. Builds go on NVMe or SSD.

## 1. The stream path on the board's heap, without the engine

On any board with a dma-heap:

```sh
LEMNOS_TEST_DMA_HEAP=/dev/dma_heap/system \
  cargo test --release -p lemnos-driver-g2d --test stream -- --nocapture the_same_on_dma_bufs
```

Pass: the test passes and prints `ran on dma-bufs from /dev/dma_heap/system`. Repeat for each
heap under `/dev/dma_heap/` and record which ones pass.

## 2. A conversion through a stream on the engine

Needs an A733 board with `/dev/g2d` (see `testing/board-runs/E4.md`, whose checks come first),
and the follow-up that gives lemnosd streams of dma-bufs, or a test host built as
`drivers/g2d/tests/stream.rs` builds one with `Device` in place of the counting engine.

1. Open the job stream, fill buffer 0 with a 64x32 `AR24` gradient, post a job converting it to
   `XR24` in buffer 1.
2. Expect one completion on buffer 1 with the job's identity and 8192 bytes, and buffer 1 to
   hold the gradient with its alpha byte ignored. Record the byte order seen for each code in
   `drivers/g2d/src/convert.rs` (`FORMATS`): it follows the kernel header's names and has not
   been compared on an engine.
3. Post a job one row taller than the buffer. Expect an empty completion and no request in
   `dmesg`.
4. Detach the consumer while a job is posted every frame, attach another, and post a job. Expect
   it to complete, and the first consumer's buffers to be unchanged from the moment it detached
   except for at most the one job that was running.
