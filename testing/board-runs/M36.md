# M36c: the boot's watchdog, and lemnosd taking over feeding

**Untested on board.** This file is the on-board check for the watchdog gap at the boot's hand-over.
What runs on this PC is recorded below; nothing here has been run on a bench board.

## What QEMU showed (this PC, run-watchdog.sh)

Kernel: the pinned modules-off build, `tmp/pinned-2026-11-14-d/k-modules-off` (BUILT-AT absent; the
configuration has `CONFIG_I6300ESB_WDT=y` and the modules-off fragment, and both builds of the set
returned 0). The guest had `-device i6300esb -watchdog-action reset -no-reboot`, so a reset ends QEMU.

| Mode | What ran | Result |
|---|---|---|
| `slot-init` | The real `lemnos-slot-init` as `/init`, no slot named | Armed `/dev/watchdog` at 15 s. Its refusal went to the rescue as "not a Lemnos disk" (no flashing request). It restarted at 32.2 s of kernel time: fed through the 30 s wait, no reset before the restart. |
| `normal` | Hook (`watchdog-init.c`) arms as slot-init does, then exec's a stand-in | The stand-in's first open was 1.008 s after the hook's last feed. That 1 s is the hook's own sleep after its last feed. The stand-in fed 45 s and powered off. |
| `stall` | The same hook; the stand-in never opens the device | The guest ended 15.1 s after the stall line: the watchdog reset it. |

The stand-in is not lemnosd. It opens `/dev/watchdog` as lemnosd's hw-watchdog driver does: write-only
with close-on-exec, the 15 s timeout set through the same sys request numbers, a feed of byte `0`, never
`V`. No slot and no lemnosd are in the guest, so the QEMU run does not show lemnosd taking over feeding.

## The on-board check (not run)

Board: the CM5 bench board (Raze #2). It is not connected to without the coordinator's go-ahead in that
turn, and the board is handed over explicitly each time.

1. **Arming.** Boot the default slot. `slot-init` logs `watchdog armed: 15 s` before the data partition
   is found. Check the timeout the bcm2835 watchdog applies is 15 s (`/sys/class/watchdog/watchdog0/timeout`).
2. **The gap.** From `slot-init`'s last feed (before its `switch_root` exec) to lemnosd's first open of
   `/dev/watchdog`. Record it. It must be well under 15 s. Read it from lemnosd's own log, not the stand-in's.
3. **lemnosd feeds.** After the hand-over, `/dev/watchdog` is fed for at least 60 s with no reset.
   Confirm lemnosd is the holder (`/proc/<pid>/fd` of the watchdog node) and the boot count is unchanged.
4. **Stall (the return path).** Only after step 3 has passed. Prevent lemnosd from opening the device
   (for example a boot whose lemnosd is held before its watchdog open, as a test build of the image only).
   The board must reset within about 15 s of the last feed and come back on its default slot.

## Return path and rules (NOTICE 14)

- **Nothing edits the confirmed slot or its boot files.** The stall test uses no trial; the default boot
  record is untouched.
- **The watchdog is armed the whole time** (it is armed by slot-init before devtmpfs and only lemnosd feeds
  it after the hand-over). A hang returns the board by reset with nobody present.
- **Code check, per step.** Who arms: slot-init (`service/slot-init/src/sys.rs`, `arm`). Who feeds: slot-init
  until its hand-over, then lemnosd's hw-watchdog driver (`drivers/hw-watchdog`). What happens if the feeder
  dies: no feed, the watchdog resets the board, and the firmware boots the default. Stated in the plan; the
  coordinator checks it against the code before any run.
- **The return path is tested first:** step 4 is that test, and it runs only after step 3.

## Stop

Stop changing and report at once if any step does not reset or return the board in its window, or if the
board is off its default slot afterwards. Report the last known state with the times.
