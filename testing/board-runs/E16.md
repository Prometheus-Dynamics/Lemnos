# E16 board run: the Rockchip MPP service (`drivers/rk-mpp`)

Status: untested on board. The session that reaches the node now exists
(`drivers/rk-mpp-sys`, PR E16b: `ServiceSession` and `ServiceNode`), so every check below has code
to run; none has been run on a board. What has run on the PC: the layout tests (request numbers,
`struct mpp_msg_v1`, `struct mpp_bat_msg`, `struct reg_offset_elem`, command ids, flags, client
types; layouts also checked with `gcc` on x86_64 and `clang --target=aarch64-linux-gnu`), the
claim, buffer, submit and completion logic against a played kernel that translates registers the
way `drivers/video/rockchip/mpp/mpp_common.c` does (`cargo test -p lemnos-driver-rk-mpp`, 19
tests), and the session against a regular file and a pipe (the request answers `ENOTTY`, reported
as `Unsupported`) and against a played kernel that reads and writes through the exact pointers the
session issues (`cargo test -p lemnos-driver-rk-mpp-sys`, 10 tests). Everything was read from
rockchip-linux/kernel `develop-6.1` at `77168c8d5ab82399f65a80e9f807b50ba37cf483`, not from a
running board.

Run it in a local session on an RK3588 board with the vendor kernel and `rk_vcodec`
(`/dev/mpp_service`) loaded, with an RK3568 or RK3399 board second (they carry `vdpu1`/`vepu1`
variants). Build on NVMe or SSD, never on the Github HDD. Module loads, unbinds and rebinds are
allowed; report each.

## What reaches the node

`lemnos_driver_rk_mpp::Service::new(lemnos_driver_rk_mpp_sys::ServiceNode::new("/dev/mpp_service"))`.
`ServiceNode` opens a `ServiceSession` per claim (read-write, close-on-exec), answers `confined`
from `/sys/bus/platform/drivers/mpp_*/<device>/iommu_group`, and `buffer_size` with
`lemnos_linux_sys::dma_buf::size`. The session issues only the chain shapes the driver builds,
from its own scratch memory, with read-backs pointing at areas it frees only after its file is
closed.

## Getting the node

```sh
ls -l /dev/mpp_service
cat /proc/mpp_service/supports-device 2>/dev/null   # or the driver's debugfs/procfs listing
for d in /sys/bus/platform/drivers/mpp_*/*.* ; do echo "$d $(readlink $d/iommu_group)"; done
```

Record which `mpp_*` drivers are bound (`mpp_vdpu2`, `mpp_vepu2`, `mpp_jpgdec`, `mpp_jpgenc`,
`mpp_rkvdec2`, `mpp_rkvenc2`, `mpp_av1dec`, ...) and whether each has an IOMMU group.

## Checks

0. **Open, bind, query hardware id.** The first thing to run:

   ```sh
   LEMNOS_MPP_NODE=/dev/mpp_service cargo test -p lemnos-driver-rk-mpp-sys --test board \
       -- --ignored --nocapture
   ```

   It prints `hw_support` and, for each block the driver takes, whether it is present and
   confined, then binds a fresh session to each present one and prints its hardware id. Pass:
   `hw_support` matches the bound `mpp_*` drivers; every present block binds and gives a non-zero
   id; `confined` is `Ok(true)` exactly for the blocks with an IOMMU group; `dmesg` shows nothing
   from `mpp` but session open and close. Record the output.
1. **The layouts and request number on the board's kernel.** Compile the declarations in
   `drivers/rk-mpp/src/uapi.rs`'s sources (`include/uapi/linux/rk-mpp.h` from the board's kernel
   headers, and `struct mpp_msg_v1` as in `mpp_common.c`) with the board's compiler and print
   `MPP_IOC_CFG_V1`, `sizeof` and every `offsetof`. Pass: `0x40047601`, 24 / 0 4 8 12 16,
   16 / 0 8 12, 8 / 0 4, the values the layout tests pin.
2. **Claim.** For each supported block present (`Block::ALL`), take a claim. Pass: the query bit
   matches the bound drivers; a block without an IOMMU group answers `NotConfined`; a block absent
   answers `Absent`; nothing in `dmesg` from `mpp`.
3. **One JPEG decode through the JPEG decoder (or `Vdpu2` in JPEG mode).** Build the register set
   for a small baseline JPEG in a test (the caller's work: stream, tables and output registers),
   with the stream and output as `Address`es of dma-heap buffers. Submit, complete, and compare the
   output against a CPU decode. Pass: identical within the decoder's rounding; the interrupt status
   register read back says done; `dmesg` clean. Record the median and slowest job time over 100.
4. **Confinement.** With the same job, write another dma-buf's descriptor number into the stream
   register's value and name the real buffer in its `Address`. Pass: the decode is still right
   (the driver replaced the value). Then remove the `Address` for the output register so its raw
   value reaches the block: Pass: the block faults in the IOMMU (an `iommu` page fault in
   `dmesg`, the driver resets the block) and no memory outside the claim's buffers changes (fill a
   canary dma-buf that no claim holds before, and check it after).
5. **Offsets.** An `Address` at `size - 1` is accepted and at `size` refused without a call
   (`OffsetOutside`); an output `Address` with a nonzero offset lands the picture that many bytes
   in.
6. **Direct register (`Vdpu2`, H.264).** Not required for this run unless an H.264 register set is
   at hand: with mode 0 in register 53, a job without register 62 as an address is refused
   (`DirectNotAddress`); with it, `dmesg` shows no `attach failed`.
7. **Drop.** Drop a claim with jobs in flight. Pass: the drop returns after they finish, and the
   next claim on the same block works.
8. **No allocation on the job path.** Wrap 100 submit and complete pairs in the counting allocator.
   Pass: 0.

Record the board, kernel version and commit, the bound drivers, every pass and failure with its
output, and the times.

Note for checks 3 and 7: the kernel's poll (`mpp_wait_result_default`) does not report a signal
that interrupts its wait; it pops the task and the call succeeds. A completion taken that way
reads back whatever the block had written, or zeros (the session zeroes the area at submit). If a
job completes with all-zero read-back while `dmesg` shows `wait task break by signal`, record it.
