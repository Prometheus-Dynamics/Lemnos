# N1 board run: H.264 through the stateless V4L2 block (`v4l2-stateless`)

Status: untested on board. The H.264 uAPI (`backends/linux-sys/src/v4l2/h264.rs`) is checked
against the Linux 7.2 header by unit tests and a C compiler, and the block carries an H.264
job on a played-back node (`an_h264_frame_is_one_request_with_its_controls_as_the_callers_bytes`).
No test opens a codec node, so nothing below has been seen to happen on a decoder.

This run is the H.264 half of `E37.md` section 2, which covers HEVC. Use the same device
entry and job stream as there (dma-buf stream, `job_bytes` at least 20).

Before running: take the board lock named in `AGENTS.md`. Builds go on NVMe or SSD. A
stateless H.264 decoder (cedrus, rkvdec or hantro with H.264) must be the node. Lemnos parses
no bitstream: the SPS, PPS, slice and decode-parameter controls come from the caller that
parsed the stream, built as the structures of `lemnos_linux_sys::v4l2::h264`.

## Checks

1. Find the node and its formats: `v4l2-ctl -d <node> --list-formats-out` must list `H.264`
   (`S264`, parsed slices). Record the kernel version, the driver name and the node.
2. Post one IDR frame's job: `TAG_SETUP` with `S264`, the picture's size and `NV12`; `TAG_STAMP`
   a whole number of microseconds; the controls as items (SPS 1048 bytes, PPS 12, scaling
   matrix 480, slice parameters 152, decode parameters 560, the decode mode and start code as
   integers); the slice in a stream buffer as the source; another stream buffer as the picture.
   Expect `Done`, the read-back to be the picture's bytes, and the picture to match a decode of
   the same stream by another decoder (for example `ffmpeg -i idr.h264 -pix_fmt nv12 -f
   rawvideo idr.nv12`). Record which decoder made the reference.
3. Expect `VIDIOC_QBUF` with `V4L2_MEMORY_DMABUF` on both queues to be accepted, and one
   `VIDIOC_REQUEST` per job. A driver that refuses dma-bufs on its source queue is a finding.
4. Decode a P frame whose reference list names the IDR by its stamp (`reference_ts` of its
   DPB entry). Expect `Done`: the kernel found the reference among its capture buffers. Then
   name a stamp that no capture buffer carries and record what the device does: expect the job
   `Failed` with the device's own message in `dmesg`, and the block to stay open.
5. Post a job whose stamp is 123 456 789 ns (not a whole microsecond). Expect `Refused` and no
   `VIDIOC_QBUF`.
6. Slice-based multi-slice pictures: decode a picture of two or more slices, one job each,
   into the same picture buffer. Record whether the kernel sets `V4L2_BUF_FLAG_M2M_HOLD_CAPTURE_BUF`
   on the capture buffer between slices, whether the next slice's `VIDIOC_QBUF` on the same
   index is accepted, and whether the final picture matches check 2. This is the case the block
   has no special handling for; a failure here is a finding, not a retry.
7. Frame-based decoding (`DECODE_MODE_FRAME_BASED`, where the device parses the slices): one
   job per frame with no slice parameters. Record whether the device accepts it; a device that
   refuses it is a finding, not a failure of the block.
8. A decoded picture allocates nothing from the second job on, under the counting allocator
   (the unit test `decoding_allocates_nothing_once_the_session_is_open` shows it on the mock).
