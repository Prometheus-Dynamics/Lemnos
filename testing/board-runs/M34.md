# M34 board run: a front end lends its frames to a back end

Status: untested on board.

M34 lends a front-end output0 buffer to the back end's job with no copy. Here is what the tree proves
without a board: the chain proof end to end on the simulated blocks, the lend's lifetime rules in the
host and the back end, and the kernel's lend path in QEMU (`testing/qemu/lemnos_lend_check.c`: a memfd
is refused with EINVAL, a system-heap dma-buf is refused for not being one contiguous range, a CMA
dma-buf is lent, released when its job finishes, and kept pinned when its block wedges). What it does
not prove is the real PiSP back end reading a lent CMA buffer, and the real pool page written by the
kernel module on the board. The check on the board, on the chain board `testing/boards/pisp-camera-chain.toml`
(the sensor, receiver, front end and back end of the reference board):

1. Build `lemnosd` and `lemnos-ctl` for the board and install the module from `kernel/` built against the
   board's kernel. Start with the back end's `lend = "output0"` in the board file and the front end's
   `output0` at 6 buffers.
2. Run `lemnos-chain-proof` for 120 frames at 30 fps. Expect every check to pass, the back end's
   `input` stream reported as not written, and the four spans printed. Record the counts: frames
   delivered, dropped, errors, job-end reasons, sequence gaps.
3. Read the pool page the module wrote for the front end's output0 stream (its word 1 is the layout, 2;
   word 2 is the shape). A reader of a page of another layout must refuse it with a layout error that names
   both values.
4. Stop the back end while it holds a lent buffer, then start it again: the stop gives the lend back, and the
   next run's frames arrive with no job-end reason other than the stop's.
5. Take a frame with the back end's job unposted (a job-end reason `not-lent`); the proof must report it, not
   hang.
6. Before any step above, the way back is checked first (a watchdog armed, the return path run once), and the
   proof's streams are stopped before the board is left, so no step leaves a state only a user can undo.

The timings are the board's: the frame period, the job time and the end-to-end span, measured on CM5 only.

## Kernel module behaviour added by M34

This is the acceptance set for the module's behaviour when it is ported to Rust. Each item names the
QEMU check that proves it (`testing/qemu/run.sh`, which must end `lemnos-qemu: passed (0 failed)`), and
what that check asserts. A check prints only its failures; a pass is the `ok` line and the check's
final `all checks passed` or `0 failed` line.

1. `LEMNOS_STREAM_IOC_REGISTER_LENT` (0x8a) registers a dma-buf read-only for a block, with a
   generation. The check: `lemnos_lend_check`, which asserts the lent register, that a second
   unregister is `ENOENT`, and that the same generation again is a pin-cache hit at the same device
   address (`ok   lent a CMA dma-buf: addr ..., count 1 -> 2`).
2. The frame ring is 6 words: word 5 is the frame's end time. The check: `lemnos_pisp_be_check`
   (added by M34), which asserts that the frame it takes after a job's finish has word 5 nonzero and
   equal to its start word 3, the block's finish being both.
3. The pool page's layout word is written at word 1, before the shape at word 2, with the magic last.
   The check: `lemnos-shm-ring-check` (`ok   the pool page's generation and buffers (Ok((1, 4)))`)
   reads the kernel's page, and the Rust reader accepts layout 2. The write order is a code property,
   not seen at run time. A page of another layout is refused with both numbers: the Rust unit test
   `a_pool_page_of_another_layout_is_refused_with_both_numbers` (shm-ring-buffers).
4. The real refusals: a memfd is refused with `EINVAL` (`memfd refused: Invalid argument (not a
   dma-buf), nothing registered`), and a system-heap dma-buf is refused with `EINVAL` when it is not one
   contiguous DMA range (`system-heap dma-buf refused: Invalid argument (not one contiguous DMA range),
   nothing registered`). The check: `lemnos_lend_check`.
5. A lent buffer is released when its job finishes, and when a normal stop comes (`a job finished, the
   lend was released, a normal stop released the pin: count 1`). The check: `lemnos_lend_check`.
6. A lent buffer stays pinned when its block wedges on stop (`wedged stop: wedge flag 1, lent dma-buf
   kept pinned, count 1 -> 2`). The check: `lemnos_lend_check`.

Not proven by QEMU: the DMA direction of a lent region (`DMA_TO_DEVICE`, a code property), the
stale-generation eviction path, and any real PiSP block reading a lent CMA buffer (the board run above).

## Which tests run the lent chain, and in which mode

The chain tests take the host's stream buffers. With a usable dma-heap (dma-bufs) the front end's frames
are lent to the back end. Without one (memfds, as on a CI runner) the kernel and the stand-in both refuse
a lend, so the proof copies each frame through the back end's `input` stream and checks one refused lent
job (`bad-config`). `LEMNOS_TEST_NO_DMA_HEAP=1` makes a host with a heap take the memfd path.

| Test | dma-heap host (lent path) | memfd host (copy path + refusal) |
| --- | --- | --- |
| `chain_end_to_end` (the proof, as a process) | runs the lent path | runs the copy path and the refusal |
| `chain_latch_sim`, `chain_latch_lag`, `chain_latch_beside`, `chain_stall`, `chain_stale_stamp` | buffers as the host gives | buffers as the host gives (none posts a back-end job) |
| `stream_lend` (host; its stand-in allocator is the memfd one, whatever the host has) | the same | the same |
| `be_device` (pisp driver; a lend mock, no buffers) | the same | the same |
| driver test `a_lent_buffer_the_block_cannot_register_is_refused_bad_config_and_nothing_stays_lent` | the same | the same (the mock refuses the registration as the kernel does) |
| `camera-sim` `a_lent_file_that_is_not_a_dma_buf_is_refused_and_nothing_is_registered` | the same | the same |

Both modes were run on the development machine: the camera-proof crate (55 tests in each mode), and the
workspace in each mode (see the PR body). The memfd mode is `LEMNOS_TEST_NO_DMA_HEAP=1 cargo test`.

## Is the lent chain covered on CI?

Not with real dma-bufs. The CI gate runs the workspace on a host without a dma-heap, so the chain tests take
the copy path there, and the lent chain (a back-end job reading a front-end dma-buf lent through the host)
does not run. The QEMU job runs the kernel's own lend of a CMA dma-buf (`lemnos_lend_check`, real module,
real CMA), and that covers the kernel side only. The userspace lent chain runs on a machine with a dma-heap
(a development machine, as here) and on the board run above.

> Historical note. The C check named above is now `testing/crates/lend-check (lemnos-lend-check)` (the Rust port).
