# E8 board run: the rkcif receiver

Status: untested on board. The routing rules and the driver have passed their tests against graphs
written by hand in the shape the vendor kernel builds them (`drivers/rkcif/src/tests.rs`). No graph
from a real Rockchip board has been read by this code. Every name the rules depend on was read from
the vendor kernel's source (rockchip-linux/kernel `develop-6.1`,
`drivers/media/platform/rockchip/{cif,isp}`), not from a running board.

Run in a local session after this PR merges, on a Rockchip board running the vendor kernel with
`rkcif` and `rkisp` bound and a camera whose kernel sensor driver probes (the vendor path still
needs one). An RK3588 board with one MIPI camera is the first target; an RK3568 or RK3566 board the
second. Build on NVMe or SSD, never on the Github HDD. Module loads, unbinds and rebinds are allowed;
report each.

## Checks

1. **The graphs match the rules.** `media-ctl -p -d <dev>` for every `/dev/media*`. Pass:
   - The receiver's media device reports a model (e.g. `rkcif-mipi-lvds2`) and has
     `stream_cif_mipi_id0` to `_id3`, each fed from pad `n + 1` of the CSI-2 host entity.
   - An ISP's media device (driver name e.g. `rkisp-vir0`) has `rkisp-isp-subdev` with pad 0 fed by
     an entity named exactly the receiver's model, of function `PROC_VIDEO_COMPOSER`. If the name or
     function differs (for example a `-sditf` suffix), record it: `route::feeds` must change.

2. **`feeds` answers which ISP.** A small program binds `Rkcif` with `device = <the model>` and
   prints `feeds()`. Pass: the ISP whose sink link to that entity `media-ctl` shows `[ENABLED]` is
   the one with `enabled: true`, and every other ISP wired to it shows `enabled: false`. On a board
   with two cameras, each receiver names its own ISP.

3. **Routing.** With the channel's link turned off by hand (`media-ctl -l '"<host>":1->"stream_cif_mipi_id0":0[0]'`),
   `configure` RAW10 on virtual channel 0, then `start`. Pass: the link reads `[ENABLED]` again, any
   other enabled link into `stream_cif_mipi_id0` is off, other channels are unchanged.

4. **Frames still flow to the ISP.** After `start`, stream the ISP's main path with the vendor
   tools or E9's driver. Pass: frames arrive; this shows the route this driver keeps is the one the
   ISP reads through. If frames arrive with the capture link off as well, record it: the link is not
   on the ISP's path and `start` should leave it alone.

5. **Recovery.** While routed, turn the channel's link off by hand. Pass: within about a second
   health reads degraded, then the link is back on and health is `Ok`. Unbind and rebind the
   receiver's platform device while routed. Pass: the driver keeps retrying, every 8 s at most, and
   routes again once the device is back; no attempt allocates in the 1 s check (`perf` or the
   counting allocator in a debug build).

6. **Compact layout.** Capture one raw frame from `stream_cif_mipi_id0` with `v4l2-ctl` at the
   configured size and compare `bytesperline` and `sizeimage` with `configure`'s `stride` and `size`
   (1280x800 RAW10: 1792 and 1,433,600). Pass: equal.

## Not tested here, and known not to be

`frame_stream` and `counters` (not served), `Unpacked16` (refused), HDR modes (the channel is not
the virtual channel there), DVP inputs, and the ISP's own links (left to the ISP's driver).
