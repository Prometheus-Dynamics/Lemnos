# F2f2 board check: a client that goes away leaves the sensor stopped

Status: NOT RUN on the board. Host check only so far: `drivers/ov9782` test
`a_caller_going_away_stops_the_sensor_it_started` (the owner's caller_gone writes standby; another caller's does not).

## Steps for the board session

1. Start lemnosd with the chain board file (`pisp-camera-chain.toml` as in the F2d record), sensor `cam0-sensor`.
2. Start a client that selects a mode, starts the sensor and streams. Note its PID (started by us; recorded in a pid file).
3. Kill that client by its PID while it is streaming (never by name). Then read the sensor's state through lemnos-ctl.
   Expected: the sensor is stopped (not "running") within the daemon's next caller-gone pass. Record the time.
4. Run `select_mode` from a fresh client on the same daemon. Expected: accepted (before F2f2 it returned -16 EBUSY).
5. Repeat 5 times. Record every result, the PIDs and the timings.
6. Stop the daemon by its PID. Leave the board as found.

Not run. Reason: the board is held by the chain run (see testing/board-runs/L1-chain.md).

## Interim: clearing the sensor by hand (until F2f2 is on the board's lemnosd)

A client stopped with SIGTERM while streaming left the sensor started, and the next `select_mode` returned
-16 (EBUSY). It cleared without unloading the module, by the contract stops in this order:

    lemnos-ctl --socket <sock> call cam0-sensor stop
    lemnos-ctl --socket <sock> call cam0-receiver stop

Then the front end, if it was started: `lemnos-ctl --socket <sock> call cam0-fe stop` (name per the board file).
These run under the board lock, against the daemon's own socket. Record the output of each command.

With F2f2 in lemnosd, the daemon stops the sensor, the receiver and the front end itself when the client that
started them goes away. The host visits devices in slot (board file) order; each stop is independent of the
others, so the order does not change the outcome.
