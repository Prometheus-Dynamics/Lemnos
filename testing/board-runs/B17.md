# B17 board run: status light on the CM5

Status: untested on board. The ring map, animator, layers and priorities, the built-in status looks,
the golden frames and the driver's tick, write and retry paths are covered by tests over a fake
`pixels/1` device on the cloud host. No frame has reached a real ring.

Run in a local session after this PR merges. Take the board lock named in `AGENTS.md`
(`/run/lock/board-gpu.lock`) before starting, use the CM5 only, and build on NVMe or SSD, never on the
Github HDD. Report CM5 timings only.

The board file binds a `ws2812` ring as in B16 (the bus as B16 gives it, `count = 16`), and a
`status-light` that uses it:

```toml
[[devices]]
id = "ring"
driver = "status-light"
uses = { pixels = "ring-pixels" }
config = { count = 16, look_brightness = 1.0, fade_ms = 250 }
```

The `ring-pixels` device is the `ws2812` from B16. Looks are sent through `light/1` (`show` on a
layer at a priority, `clear`, `clear_all`, `set_brightness`). A status look is the one-byte
`status.*` look. A comet or a fill is given in full (see `drivers/status-light/src/wire.rs`).

1. Bind and health. Start the service with the board above.
   Pass: the `ring` light is running, its health is ok, and the `ring-pixels` device is ok.
2. Default look. Send no look and wait 300 ms.
   Pass: every LED is green at 178 of 255 (the `status.ok` fill), and the ring is not dark.
3. Layers. Show `status.error` on layer 0 at priority 10, then a blue fill on layer 1 at priority 50.
   Clear layer 1.
   Pass: while layer 1 holds the fill every LED is blue; after the clear, the ring shows `status.error`
   again, which blinks red (on for half of each second) because the board's `error_effect` is `blink`.
4. Animation. Show a comet on layer 0 at priority 60 with a period of 1200 ms and a tail of 5 LEDs.
   Pass: the bright head goes once round the ring in 1200 ms, and the ring is written about every
   20 ms while it moves (CM5 timings only: median write interval within 2 ms of 20 ms).
5. Idle cost. Clear every layer, wait for the fade to finish, then leave the ring alone for 60 s.
   Pass: no `ws2812` SPI transaction is made in those 60 s, and the `lemnosd` process uses no CPU
   while the ring is steady (CM5 CPU time over the minute is under 0.1 s).
6. Runtime brightness. Send `set_brightness` at 128, then show a full red fill.
   Pass: the red is about half as bright as at 255 on the CM5 meter, with no colour cast.
7. Restart. Stop and start the service.
   Pass: the ring's brightness is back at the board's `look_brightness` (1.0), and no look survives
   the restart, which is the design: nothing is kept across a restart.
8. Failure path. Not tested on board. The retry schedule (100 ms doubling to a cap of 8 s, and no
   give-up) is covered on the fake bus. Forcing an SPI error on the CM5 needs the bus taken out from
   under the driver, which is not a safe board action; leave it to a later board run.
