# D8 board run: the ov9782 sensor driver

Status: untested on board. The register sequences, limits, group hold bracketing, the refusal of
`0x3D80` and the recovery backoff are covered by the mocked-bus tests in `drivers/ov9782`. No
register has been written to a real OV9782 by this driver, and no frame has been seen.

Run in a local session after this PR merges, on the CM5 (Raze #2) with an OV9782 connected, using
`rp1-csi2` (or the stock receiver as a pixel source) and the board file's `ov9782` device. Take the
board lock named in `AGENTS.md` (`/run/lock/board-gpu.lock`). Build on NVMe or SSD, never on the
Github HDD. Report CM5 timings only. Compare against dev's lemnosd on the same scene where a dev
reference exists.

The driver needs the sensor already powered, with its 24 MHz clock running and reset released. The
board or image owns that.

Modes (`mode(index)`): 0 and 1 are 1280x800 RAW10 and RAW8; 2 and 3 are 1280x720; 4 and 5 are the
2x2-binned 640x400.

## Checks

1. **Bring-up.** Bind the driver, `select_mode(0)`, configure the receiver from `mode(0).link`,
   `start`. Pass: frames arrive at the expected size. Repeat for each mode index. Record whether the
   chip id read back is `0x9782` or `0x9281` (the driver accepts both).

2. **OTP stays untouched.** Trace the bus (logic analyser or an instrumented backend) through a
   start, `set_controls`, `post_values`, flips and every test pattern. Pass: `0x3D80` never appears.

3. **Pixel rates.** With modes 0 and 1 at the minimum frame length, measure the frame rate and the
   size of each frame on the link. Compare with `Mode.max_fps_milli`, `line_length`, and
   `link.pixel_rate_hz` (160 MHz RAW10, 200 MHz RAW8). Pass: the frame rate follows the 80 MHz (RAW10)
   and 96 MHz (RAW8) system clocks within 1 %. Note that `0x030D = 0x60` runs the system clock above
   the 80 MHz limit given in the chip's PLL limits table; report any instability seen at RAW8.

4. **Line time.** From one measured frame period at a known frame length, compute the line time.
   Pass: it matches `Mode.line_time_ps` within 1 % (RAW10 gated clock 9.5625 µs, RAW10 continuous
   clock 9.1 µs, RAW8 gated clock 7.96875 µs, RAW8 continuous clock 7.5833 µs). If RAW8 disagrees,
   the driver's 96 MHz arithmetic is wrong and `Mode.line_time_ps` must be fixed with the measured
   clock.

5. **Blanking.** With `continuous_clock` false and true in the board config, check the receiver has
   no line or frame errors at the minimum frame length in each mode, and record whether the minimum
   line length (register 728 continuous, 765 gated) needs more than this.

6. **VTS+1.** At a fixed mode and exposure, measure the frame period at frame lengths `v` and `v + 1`
   for several `v`, including the mode's `frame_length_min` and a length near its
   `frame_length_max`. Pass: the difference between the two periods is one line time. Record the
   constant offset between the programmed frame length and the measured lines per frame (for
   example, whether the sensor outputs VTS or VTS+1 lines).

7. **Exposure margin 25.** At a fixed frame length `v`, set exposure to `(v - 25) * 16` and to
   `(v - 25) * 16 + 1` (the driver must refuse the second with `INVALID_ARGUMENT`). Pass: at the
   accepted limit, frames are not corrupted or short, and exposure and brightness scale linearly up
   to it. A shorter margin, or one the sensor needs longer, is a defect in `chip::EXPOSURE_MARGIN`.

8. **Fractional exposure.** At a low gain on a stable scene, step exposure by single sixteenths from
   16 to 32 and in the upper part of the range. Pass: mean pixel value increases monotonically
   with no large jumps at line boundaries (whole sixteenths per line).

9. **Latch frames.** Using `post_values` with the receiver's frame identity on a scene where the
   exposure step is visible:
   - Post a new exposure and gain with a new identity; find which delivered frame first shows the
     change. Pass: it matches `Mode.exposure_delay` and `gain_delay` (table values 2; set them from
     this measurement if not) and the two change on the same frame (group hold).
   - Post a new `frame_length`; find the first frame whose period reflects it. Set
     `frame_length_delay` (table value 2) from this.
   - Pass only if the group hold brackets every multi-register change and no frame shows a torn
     exposure while posting at the full frame rate for at least 600 frames. Check that group 0
     launch (`0x3208` = `0xA0`, the chip's documented sequence) latches; the frozen `dev` driver used
     a different register (`0x3308`) that the register map does not list, so this has no dev reference.

10. **First frame after start (0x4242).** Start the sensor with a known exposure repeatedly. Pass: the
    first delivered frame has that exposure and looks like a real frame, and frames continue after it
    (the sensor keeps streaming and does not mask every frame). If the masking behaves otherwise
    (no masking, or the stream stays masked), `Mode.drop_frames` must be set instead of
    `chip::FIRST_FRAMES_MASKED`. Also read `0x4244` (frame counter) to see whether the first frame
    was counted.

11. **Black level 64.** Cap the lens or use a dark scene. Pass: the mean pixel level in RAW10 is about
    64 codes in each mode, and in RAW8 about 16. The binned mode must match (the driver now writes
    the black target `0x4003 = 0x40` in every mode; dev's 640x400 table left it at its reset value).

12. **Flips and Bayer.** For each of the four flip settings, check the rotation of the image against
    the setting and check the colour order with a Macbeth chart or the colour bars. Pass: the image
    mirrors and flips as asked, and the Bayer order is what `set_flips` answers. The driver answers
    BGGR for all four (from `0x5e10` defaulting to keeping the first pixel in place). Dev's defaults
    were both flips on and reported SBGGR; check that holds. If a flip changes the order, the table in
    `chip::BAYER` has to be per flip.

13. **Binning (2x2).** With modes 4 and 5, check the image is correct and colour is right against
    modes 0 and 1 scaled down: no missing rows, no colour shifts. This mode differs from the dev
    640x400 table on purpose (row increment `0x31`, vertical binning, digital binning control), so
    there is no dev reference and a failure here is a defect in the table row.

14. **Array crop.** Compare mode 2 with mode 0 on a chart. Pass: the 720-line output is the top 720
    active lines (rows 8 to 727), matching `Mode.crop`. Compare modes 4 and 5 with mode 0: full field
    of view.

15. **Test patterns.** Run codes 1 to 7 and check each pattern looks like its name (standard bars,
    the three darkening bars, random data, squares, black).

16. **Recovery.** Interrupt the sensor's bus or power while streaming and `post_values` at frame rate.
    Pass: the call that sees the failure reports `IO`, later calls return `BUSY`, health is degraded,
    retries are at most 8 s apart, and the stream comes back with no action when the bus returns
    (with the sensor powered). The sensor is not switched off and the driver does not give up.

17. **Allocations.** On the steady path (start, then `post_values` at the frame rate for a few
    seconds), confirm no allocations from the driver with `engine/measure`.
