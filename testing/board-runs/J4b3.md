# J4b3: embedded data in the receivers (board checks, not run)

Untested on board. No board run has been made for this change. The checks below are the ones the
CM5 (Raze #2) session should run after the PR merges, under `/run/lock/board-gpu.lock`.

## What was run here

- QEMU harness (`testing/qemu/run.sh`), kernel module with its fake receiver: the embedded channel
  on data type 0x12 and the image's virtual channel; no request, no channel; the three frames:
  a line with sequence 0, a frame with no line (sequence 1 absent), a line with sequence 2 in
  buffer 1; the request's refusals (length, reserved word, streaming). The log ends in
  `lemnos-qemu: passed (0 failed)`.
- `cargo test` for `lemnos-driver-rp1-csi2-sys`, `lemnos-driver-rp1-csi2` (the embedded stream
  is named only when declared, given its memory before START, publishes on its own stream with
  the frame's sequence, refuses a length the channel can't take) and
  `lemnos-driver-v4l2-capture` (the metadata line pump: copied with its sequence, a bad or empty
  line not published, a line with no free buffer dropped, the node buffer always given back).

## Checks for the board

1. CSI-2 data type 0x12 on the image's virtual channel: a sensor that sends embedded lines (none
   in the tree does) with the `embedded` stream declared. Each frame's line arrives with that
   frame's sequence. Line length: the `embedded_bytes` the board names.
2. The line count on channel 1 reads 1 per line (the stock meta node's frame height). If a
   sensor's line is longer than one line in the channel's terms, the line is published empty
   and the sequence gap shows it. Record which.
3. With no `embedded` stream declared: channel 1's control register stays 0 and nothing moves
   on the embedded path.
4. Frame start counts (`frame_starts`) unchanged by the embedded channel.
5. Stop and close with an embedded stream attached: both DMA channels stop before any buffer is
   given back (the wait is on both channels' line counters).

## Not done on board, and why

- No sensor on a board in the tree emits embedded data, so no real line has been seen.
- rkcif: lines from a metadata node named in its config; the vendor kernel has none, so it answers empty there. sunxi-vin answers empty.
