# D17 board run: the back end takes its input and configuration from its client

Status: untested on board.

What changed since D15: the PiSP back end driver's input image and configuration are the client's.
Jobs are posted on the `config` stream, whose buffers hold a `pisp_be_tiles_config`; the driver
reads the one a job names once into its own memory, checks it, and writes that copy to the
module's configuration slot that goes with the job's place on the ring. The input is an `input`
stream buffer (`memory = "dma-buf"`), registered with the module for the job exactly as output 0
is. Output 1 does the same on an `output1` stream when the board has one. The module's pool is one
page per job, and the driver no longer allocates an input or output 1 region. The host test
(`drivers/pisp/tests/be_frames.rs`) proves this against a stand-in for the block; nothing here has
run on the block.

The stream names changed: `jobs` is now `config` and `frames` is now `output0`. Board files from
D15 need renaming.

## Setup

1. Take the board lock, `/run/lock/board-gpu.lock`, as AGENTS.md says. CM5 (Raze #2).
2. Board file: the back end device with
   - `[devices.streams.config]`: `buffers = 2`, `buffer_bytes = 16720`, `job_slots = 8`,
     `job_bytes = 128` (plain memory is fine);
   - `[devices.streams.input]`: `memory = "dma-buf"`, `heap = "linux,cma"`, `buffer_bytes` at
     least the input's `stride * height` (RAW16 at 1280x800 is 2048000);
   - `[devices.streams.output0]`: `memory = "dma-buf"`, `heap = "linux,cma"`, `buffer_bytes` at
     least the `size` `set_output(0, ...)` answers;
   - optionally `[devices.streams.output1]` the same way.
   Builds on NVMe or SSD.

## Checks

1. **Content from the client's input.** Attach a `lemnos-client` to `config`, `input` and
   `output0`. Write a `simple_bayer` configuration (1280x800 RAW16 in, NV12 out) into config buffer
   0 and a flat grey RAW16 frame into input buffer 0, both through the client's mappings. Post one
   job per output buffer. Pass: every frame's Y plane is a constant near the grey level, not zero.
   Repeat with a horizontal ramp in the input: the Y plane must ramp the same way.
2. **The configuration is the client's.** Post two jobs naming the same input with different white
   balance gains in config buffers 0 and 1. Pass: the outputs' chroma differ as the gains say.
3. **A configuration changed after posting.** Post a job, and right after the post rewrite the
   config buffer with all-zero gains. Pass: the frame looks like the first configuration; the
   module's `refused` count stays 0.
4. **A configuration naming addresses is never run.** Write a non-zero byte into the first 112
   bytes of the config buffer and post. Pass: the driver's `dropped` goes up by one and the
   module's `refused` (`LEMNOS_PISP_BE_IOC_STATUS`) does not.
5. **Registration is released.** After 1000 jobs, the stream is open, `refused` is 0, and a further
   job still registers its input and output (no `ENOSPC`).
6. **Input still on the block.** Post two jobs naming the same input buffer in one go. Pass: one
   frame, `dropped` up by one.
7. **Ring full.** With `job_slots = 2` and `buffers = 8`, post 8 jobs at once. Pass: no stream
   error; jobs past what the ring holds are counted as dropped, never refused by the module.
8. **Output 1.** With an `output1` stream and a configuration enabling output 1 at the same size,
   post jobs naming both. Pass: both frames have content; every region is released.
9. **Cache.** Record whether the client needs `DMA_BUF_IOCTL_SYNC` around writing the input and
   around reading an output on the CM5.

## Not tested here

- The block itself: everything above is the stand-in's.
- Temporal denoise averages are still the driver's own memory (they are the block's state between
  frames), and stitch input/output stay off: the driver gives them no memory, so a configuration
  enabling them is dropped.
