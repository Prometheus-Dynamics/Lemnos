# B8 board run: bmi088 on a CM5

Status: untested on board. The driver is covered by unit tests on the simulated bus
(`drivers/bmi088`, `backends/sim`), including the batch, stamp and clamp checks. No transfer has
reached a real BMI088 through this driver.

Setup: one BMI088 wired to a CM5 I2C bus, accelerometer at 0x18 and gyroscope at 0x68 (SDO pins
low). Use a board file device such as:

```toml
[[devices]]
id = "imu"
driver = "bmi088"
bus = "i2c-N"
config = { accel_rate = 200, gyro_rate = 200, fifo = true }
```

With `fifo = true` the host must call the device's `tick` (the host does this after every method
call and at the time `tick` returns), and samples are taken with `read_batch`. The capture tool
for the checks below calls `read_batch` on the accelerometer every 50 ms with a 4 KiB buffer, and
records each record's stamp (`at_ns`) and value. The tool is not part of this PR: the board session
writes it, and this file says what it must record.

Run it under the board lock named in `AGENTS.md`, with the build on NVMe or SSD, never the HDD.
Timings are CM5 only.

1. Bind with the chip present, then read the accelerometer until it returns a sample. The
   power-up is one step a read, so the first reads return `AGAIN`.
   Pass: a sample arrives within 10 reads. Once the gyroscope has a sample too, health is `Ok`.
   If health stays `Degraded("accelerometer: transfer failed")`, the configuration readback did
   not match: record the register values with `i2cget` and stop here.
   Record how many reads failed during bring-up and with what status. The gyroscope's reset takes
   about 30 ms, which at 200 Hz spans several reads. A read that lands inside it can fail, and the
   driver reports that failure and retries on the next read.

2. Check the settings the chip holds, with `i2cget` after the device is up.
   Pass: accelerometer 0x40 has 0x9 in its low nibble (0xa9 expected), 0x41 is 0x01 (6 g). Gyroscope
   0x0f is 0x00 (2000 degrees per second) and 0x10 is 0x04 (200 Hz). With `fifo = true`,
   accelerometer 0x48 is 0x02 and 0x49 is 0x50, and gyroscope 0x3e is 0x80.

3. Stationary batch capture at 200 Hz for 45 s, through `read_batch` on the accelerometer, with
   the host ticking the device.
   Pass: every record the chip took is delivered. Consecutive stamps are one sample period apart
   (the period is the average over the capture), and the stamps span the host's elapsed time for
   the capture to within 1 ms. No batch read returns `FIFO overflowed` or `batch missed samples`
   in health. Record the number of records, the number of batch reads that returned none, and the
   largest number of records one read returned.
   Dev's earlier run delivered 9000 of 9000 samples through its own read path. This check counts
   the chip's samples through their stamps, not against 9000, since the die's own rate is not
   exactly 200 Hz.

4. Misses. Watch health through the same capture, and the stamps.
   Pass: health never reports a FIFO overflow or a batch miss. The largest gap between two
   consecutive stamps is no more than 1.5 sample periods (7.5 ms at 200 Hz). The largest gap
   between two `read_batch` calls is no more than 10 ms. Record both, and dev's earlier largest
   read gap of 5.1 to 5.2 ms for comparison.

5. Read time. Time 1000 `read` calls with `fifo = true`, 1000 `read_batch` calls with
   `fifo = true`, and 1000 `read` calls with `fifo = false`, and record the median and worst case of
   each. Dev's earlier 200 Hz run recorded 555 to 576 µs per read.
   Pass: every call completes, and the timings are recorded here.

6. CPU. Run the same 200 Hz capture on dev's service and on this driver's build, with the same
   tool, and compare the CPU of the reading process. Dev's earlier figure at 200 Hz was 3.1 to
   3.2 %. The drain now runs once per half FIFO on the tick (every 365 ms at 200 Hz), not on each
   read, so it should be no higher.
   Pass: this driver's CPU is no higher than dev's on the same run. Record both.

7. Alignment. This driver does not align the gyroscope to the accelerometer in time. Each batch
   record is stamped on its own die's grid from the host clock, and the two dies are not paired.
   Alignment needs the host clock at the start and end of each bus transaction, which the driver
   model does not give yet (the driver gets one time per call).
   Pass: on dev, run the same 200 Hz capture with the timed alignment on and off, and record the time
   gap it closes between the two dies here. On this driver, record the spread of the offset
   between each gyroscope record's stamp and the nearest accelerometer record's stamp, over the
   same capture. This check stays open until a clock-based alignment lands in `next`.

8. Disconnect the accelerometer's I2C wiring during reads, then reconnect it.
   Pass: reads fail with `IO` while it is off, and health is `Degraded` naming the accelerometer.
   After reconnecting, reads resume with no restart. The soft-reset register (0x7e) is written
   again, and the power-up steps run once more. A batch read that fails leaves its samples in the
   ring, and the next batch read after power-up returns them.

9. Take the gyroscope off the bus (or point `gyro_address` at an address nothing answers, such as
   0x69 when the chip is at 0x68).
   Pass: bind succeeds. Gyroscope reads fail with `IO`, health names the gyroscope, and accelerometer
   reads keep returning samples. Retry pacing is the host's, and it stays within the 8 s cap.

10. Point `accel_address` at the gyroscope's address (0x68) so the accelerometer reads a chip with
    the wrong ID.
    Pass: accelerometer reads fail with `NOT_SUPPORTED`, health is `Degraded("accelerometer: wrong
    chip id")`, and 0x7e on that address is never written.

11. Bind with `accel_range = 5`.
    Pass: bind fails with `INVALID_ARGUMENT`.

12. Bind with `fifo = false` and call `read_batch` on the accelerometer.
    Pass: the call fails with `NOT_SUPPORTED`, and `read` still returns samples.
