# R1: the USB gadget's network and console functions, and the privileged root phase

Status: untested on board. The configfs tree, the mount options and the chown are tested against
a stand-in tree, a fake mount and the kernel source (`fs/configfs/inode.c` `configfs_setattr`, which
keeps a per-entry uid and gid; `drivers/usb/gadget/function/f_fs.c` mount options `uid=`, `gid=`,
`rmode=`, `fmode=`; `drivers/usb/gadget/configfs.c` `UDC` store; `f_ncm.c` attributes `host_addr`
and `dev_addr`; `u_serial.c` `gserial_alloc_line`, the first ACM is `ttyGS0`). Nothing here has run
on a board, a real configfs, a FunctionFS mount or a controller.

What only a board can show:

- that `functions/ncm.usb0` and `functions/acm.GS0` link into `configs/c.1` with `ffs.NAME` in the
  order the board file lists them, and that the host enumerates the NCM interface, a CDC ACM
  device as `/dev/ttyGS0`, and the FunctionFS vendor interface, with the `interface` name from the
  board file;
- that after the root phase the UDC attribute is owned by the daemon's user and mode 0600, and that
  the daemon, after dropping to `lemnos`, can open it and write the controller's name (chown on a
  configfs attribute is kept by `configfs_setattr`; the write checks permission only at open);
- that `ep0` and the endpoint files of the FunctionFS mount, made with `uid=` and `gid=` of
  `lemnos`, open for the daemon after the drop (`fmode=0600` on ep0; the endpoint files take the
  same mode, the default for `fmode`);
- that the `ReadWritePaths=-/sys/kernel/config/usb_gadget` line in `packaging/systemd/lemnosd.service`
  keeps the UDC attribute writable under `ProtectKernelTunables=yes` and `ProtectSystem=strict`.
  Until a board shows it, that line is the thing to check first if the gadget does not bind;
- that the NCM link comes up with the MAC addresses the board file gives (`host=`, `device=`).

Before running: take `/run/lock/board-gpu.lock` as `AGENTS.md` says, use the CM5, and build on NVMe
or SSD. Set the board file's gadget section as `docs/boards.md` shows. Start the daemon as root for
the root phase, and check with `ls -l /sys/kernel/config/usb_gadget/lemnos-*/UDC` that the owner is
`lemnos`. Then `lsusb -v` on the host computer, and `ls -l /dev/ttyGS0` there.

## Endpoint hand-off (R1b)

Status: untested on board. The hand-off is tested on the simulated board's function with socket
pairs standing in for the endpoint files (`service/lemnosd/tests/usb_endpoints.rs`, `drivers/usb-gadget`
unit tests). What only a board can show:

- that `ep02` and `ep81` of the FunctionFS mount, lent over the socket, read and write the host's
  bytes on a real controller, in both directions, with the Orion bridge's `LinkOffer` taken by the
  comm core as the `[read, write]` pair;
- that a host unplug and replug (a bus reset, a suspend) leaves the held descriptors working with no
  new hand-off, and that a transfer under way at the unplug fails with `ESHUTDOWN` rather than hanging;
- that the gadget going down (a controller let go) leaves the daemon's hold standing (it keeps ep0 and the
  endpoint files open, so the bind writes `UDC` only), and that the bridge, which gives its own hold up when the
  function's `up` goes false, offers again once the gadget is up. The re-offer is new duplicates of the same
  endpoint files. It works because the comm core ends its old stream and closes its old copies when the new offer
  arrives (an offer for a link that has a handle replaces it): the comm core's reader on the old copies sees the
  function go (`ESHUTDOWN`) and must not take the host's first bytes of the new stream. The QEMU check
  (`testing/crates/orion-link-check`) does this with the pinned comm core over the emulated bus; check it on the
  board with its real controller and a real host;
- that the BUSY answer is seen by a second client while the bridge holds the pair.
- that the Orion bridge and a real comm core on the board carry frames both ways: the simulated
  check is `service/orion/tests/usb_link.rs` (a comm core from the Orion revision the bridge pins,
  its USB link over socket pairs), and the board version is the same bridge with `LEMNOS_ORION_LINKS`
  set on a real gadget.

Before running: the same lock, CM5 and NVMe rules as above.
