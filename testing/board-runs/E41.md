# E41: the K230 video codec block as `codec.block/1` (`drivers/k230-vpu`)

Status: untested on board. `lemnos-driver-k230-vpu` gained `VpuBlock`, the block served through
the shared job server (`lemnos-driver-codec-jobs`) with one session owned across jobs, and the
driver `k230-vpu` that binds it from a board file. What has run on the PC
(`cargo test -p lemnos-driver-k230-vpu`, 34 tests): setup, sources and destinations completing
out of order on a played-back `mvx` node, the stream's buffers lent as handles (pipes and memfds
standing in for the stream's dma-bufs), every refused job never reaching the node, controls and
the private requests `lemnos-driver-k230-vpu-sys` allows, a decoder adopting destinations after a
source change, a session whose dequeue fails being closed with its jobs failed, a consumer that
goes closing the session, and the steady state allocating nothing. No test opened a codec node,
so nothing below has been seen to happen. The checks in `E21.md` (the node, the layouts, a frame
through JPEG and back, confinement, recovery) come first; these build on them.

Run it in a local session on a K230 board running the SDK kernel named in `E21.md` with the codec
driver loaded. Take the board lock named in `AGENTS.md`. Builds go on NVMe or SSD, never on the
Github HDD. Module loads and unbinds are allowed; report each.

```toml
[[devices]]
id = "vpu"
driver = "k230-vpu"
config = { device = "/dev/video0" }   # the node E21 check 1 found

[devices.streams.jobs]
memory = "dma-buf"
buffers = 32
buffer_bytes = 4194304
job_slots = 16
job_bytes = 20
```

## Checks

1. **It binds and opens nothing.** Start lemnosd. Expect the device `Running` and healthy, and
   the node not open (`ls -l /proc/$(pidof lemnosd)/fd`). Call `block`: `mvx`; `info`: 3
   references, 17 items, 32 buffers. With `memory = "plain"` instead, expect the bind to fail
   with `NOT_SUPPORTED`.
2. **A JPEG encode through the contract.** Post a setup job: direction 1, source NV12 640x480
   two planes, destination JPEG one plane, 4 and 4 buffers. Expect `Done`, the node open, and
   the read-back to hold the formats and buffer counts the kernel kept (the same the E21 test
   prints). Post one destination job, then one source job whose two references are the luma and
   chroma buffers filled with the E21 ramp. Expect the source to finish, then the destination
   with bytes starting `ff d8` and ending `ff d9` in the plane count its read-back gives.
   Record the order the two completions came in and the time.
3. **Out of order.** Post four destinations and then four sources, each with its own stamp.
   Expect every job to finish once, each destination's read-back carrying the stamp of the
   source it came from, and `dmesg` clean.
4. **A JPEG decode with a source change.** Set up direction 0 with the JPEG as source and no
   destination buffers. Post the encoded frame as a source. Post an events job until its flags
   say a resolution change; then an adopt job with 4. Expect the read-back to give the NV12
   format the kernel chose, then post destinations: the decoded luma's first row rises in steps
   of 4 within JPEG's error. Post a drain: the last destination comes back flagged `LAST`.
5. **What the block refuses never reaches the node.** Under `strace -f -e ioctl -p
   $(pidof lemnosd)`, post a source with `offset` 1, one with `length` past its buffer, one with
   a buffer smaller than the plane size the setup answered, a destination whose buffer is still
   pending, and a private request outside the allowed list. Expect each `Refused` and no
   `VIDIOC_QBUF` or private request for any of them.
6. **Controls and a private request.** On an encode session, set the bitrate control in the
   setup and alone; the read-back holds what the kernel kept. Issue an allowed private request
   (for example the ROI regions with one region). Expect `Done` and the structure back.
7. **A consumer that goes.** Close the caller's stream with jobs pending. Expect the node
   closed (`ls -l /proc/$(pidof lemnosd)/fd`), `dmesg` clean, and the next consumer's setup to
   open it again.
8. **Recovery.** Unload the module (or unbind the device; report which) with a session open.
   Expect the pending jobs `Failed`, health saying the session failed and was closed, and
   setups failing with health saying the node did not open a session, tried no faster than the
   backoff doubling from 250 ms to 8 s. Load it again: the next setup opens a session and
   check 2 passes again. Nothing panics and the driver never stops trying.

Record each result here.
