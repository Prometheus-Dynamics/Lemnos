# C6: power, clocks, resets and events, on a board

Run on the board 2026-11-11: clocks, thermal and events passed; the reset pulse was not run.

On Raze #2, with a block bound through `driver_override` whose device tree node has `clocks`, `resets` or `*-supply`:

1. `LEMNOS_IOC_POWER`: read the clock rate; compare with `/sys/kernel/debug/clk/clk_summary`. Enable and disable; the enable count there follows.
2. A reset pulse, on a block where that is safe: the block still works afterwards.
3. Thermal: `LEMNOS_IOC_THERMAL_READ` on `cpu-thermal` matches `/sys/class/thermal/*/temp`. A watch across the current temperature fires on a load step.
4. Bind and unbind produce the two block events. Record any supply fault seen under a real load.

## Result, 2026-11-11

Run 2026-11-11 on the CM5 (Raspberry Pi Compute Module 5 Rev 1.0, Raze #2), kernel `7.2.9-v8-16k`,
with `lemnos.ko`, `lemnosd` and the tools from PR F2a, built on NVMe and copied to
`/tmp/lemnos-run/` on the board. Raw logs are kept off the repository.

`kernel/test/lemnos_board_check.c` on the PiSP back end bound to the module (`confined=`), with the
clock and thermal readings compared against debugfs and sysfs by the run script.

1. The block's clock: 500000000 Hz, as `clk_summary` says for `fw-clk-isp`. Enable took its enable
   count from 2 to 3 there, disable back. The node's clock is looked up unnamed: the device tree
   spells the property `clocks-names`, so a lookup by the name `isp_be` fails with `ENOENT`.
2. Reset pulse: not run; no block on this board where a reset is known to be safe.
3. `cpu-thermal` read 38600 m°C, the same as `/sys/class/thermal/thermal_zone0/temp`; a watch
   across the current temperature fired.
4. Bind and unbind each produced their event. No supply fault was seen.
