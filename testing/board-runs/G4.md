# G4: a block's registers, interrupts, clocks and resets through the Linux backend

Status: untested on board. `LinuxBoard` now provides the `registers`, `interrupt`, `clocks` and
`reset` needs for a block bound to `lemnos.ko`, by board-file names in the style of `dma:<block>`:
`regs:<block>/<n>`, `irq:<block>/<n>`, `clocks:<block>/<name>,...` and `resets:<block>/<name>,...`.
Each comes from the module alone and is held under a module claim. Registers are mapped only when
`LEMNOS_IOC_INFO` reports `LEMNOS_INFO_MMIO_MAPPABLE`; interrupts are read from the module's one
event stream and filed per interrupt.

What has run on the PC: unit tests (name parsing, the mappable rule, region bounds, filing events
per interrupt with counts and wrap, an unbound block, no allocation while filing and waiting, the
`kernel/lemnos.h` layouts and request numbers) and the QEMU harness on x86 with the real module and
its test block, module loaded with `test_map_unconfined=1 test_irq_inject=1`. There the test
block's page was mapped and its marker word read, writes read back through a second mapping,
injected interrupts were delivered, stayed masked until enabled and went to the interrupt they were
for, the test clock's rate read 25 MHz and it turned on and off, the test reset asserted and
released and read back, a block not owned gave `NO_DEVICE`, no module gave `NOT_SUPPORTED`, and
none of the steady-state calls allocated. Over two harness runs under KVM, a register read took
50 to 80 ns median and an interrupt round trip (enable, inject, wait) 6.1 to 8.4 us median; these
are a virtual machine's numbers, not a board's. No real block's registers, interrupt, clock
or reset has been touched.

Before running: take `/run/lock/board-gpu.lock`. Builds go on NVMe or SSD, never on the Github
HDD. Module loads, binds, unbinds and reboots are allowed; report each.

## 1. A real block, confined

Pick a block whose DMA its IOMMU confines, list it in both `owned=` and `confined=`, and bind it
(see `kernel/README.md`, "Claiming a block"). Then, with a small program doing what
`check_registers`, `check_interrupts` and `check_power` in `testing/crates/module-check` do, with
the names pointed at that block:

- `regs:<block>`: `size()` is the region's size from the device tree, and word 0 reads the block's
  documented reset value (an ID or version register).
- `irq:<block>`: with the block made to raise its interrupt (its own test or software trigger
  register, if it has one), `wait` returns an event, the next does not arrive until the cause is
  cleared and `enable` is called, and `count` stays 1 per event.
- `clocks:<block>/<name>` with a name from the device tree's `clock-names`: `rate_hz` matches
  `/sys/kernel/debug/clk/<clock>/clk_rate`, and `enable`/`disable` move its enable count there.
- `resets:<block>/<name>` from `reset-names`: assert, then the block's registers read their reset
  values after deassert.

Pass: each of the above, nothing in `dmesg` but the module's own bind line, and the block unbinds
cleanly once the program exits.

## 2. A block not confined

The same block with the module loaded without it in `confined=` or `unconfined=`. Pass: `regs:<block>` is refused with `ACCESS`, and `irq:`, `clocks:` and
`resets:` still open.

## 3. Unbind while held

Hold `irq:<block>` and `regs:<block>`, then unbind the block. Pass: `wait` reports the interrupt
unavailable (the module's unbound event), and the program is not touching the registers when the
module removes their pages. Report what happens if it does: the module documents that a mapping
faults once the block is unbound.
