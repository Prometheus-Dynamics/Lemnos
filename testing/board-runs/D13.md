# D13: Coral firmware load

Status: untested on board. The DFU sequence, chunking at `wTransferSize`, block-number wrap, every
retry path and the failure rule are covered by unit tests over a mock USB device that runs the DFU
state machine. No block has reached a real device through this driver.

**Superseded in part by `testing/board-runs/A22.md`:** `UsbDevice` gained a reset in A22 and the
driver now issues it, so the paragraph below, step 2 and the last line describe the driver as it
was when D13 merged. Run A22's check 1 in their place. Steps 1, 3 and 4 stand.

**Re-enumeration needs a reset this driver cannot issue.** The brief's check, "Coral re-enumerates
on both boards", cannot pass on this PR. A DFU download ends in a USB bus reset, and `UsbDevice` in
`engine/hal` has no reset. The driver takes the device as far as `MANIFEST_WAIT_RESET` (or the
equivalent) and then reports that a reset is needed. The check stays open until `UsbDevice` gains
a reset through an A-series PR and the driver issues it.

Before running: the driver is not in lemnosd's built-ins. A maintainer runs
`scripts/generate-builtins.py` after merging. Take the board lock named in `AGENTS.md`. Give the
device's board entry `driver = "coral-loader"`, the `usb` need pointing at the accelerator in its
boot-ROM state (the identity it has before any firmware), and `config = { firmware = "<absolute
path to the firmware image>" }`.

What can be checked with this PR, on both boards:

1. The device binds and starts. The accelerator is on the USB port, in its boot-ROM state, and the
   driver's description shows `state: downloading`.
2. The download reaches its end. Expect the health to become `Degraded` with the message
   `firmware downloaded and manifested: the device needs a USB reset, which this driver cannot
   issue`, and the description to show `state: manifested, needs a USB reset this driver cannot
   issue`. If the device stops answering while it manifests, expect the `unconfirmed` message and
   `state: ended unconfirmed, needs a USB reset this driver cannot issue`. Either way no block is
   sent again. With no reset the device is expected to keep its boot-ROM identity; if it
   re-enumerates on its own, record that, since it would mean the driver's report is wrong for it.
3. The block size used matches the device's own `wTransferSize`. Check with `usbmon` on the bus:
   each DNLOAD carries that many bytes (or fewer for the last) and the block numbers count up from
   0.
4. Failure rule: unplug the accelerator partway through a download. Expect `Failed` with a
   `retrying` message, retries spaced at most 8 s apart, and no change in the rest of the host.
   Plug it back, restart the device, and expect the download to reach step 2 again. The driver
   never switches itself off.

boards.
