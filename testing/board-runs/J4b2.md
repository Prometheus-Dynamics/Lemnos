# J4b2 board run: the rp1-csi2 frame-start count on the reference board

Status: untested on board. Nothing here was run on hardware. The count is checked in the kernel
QEMU harness (`kernel/test/lemnos_rp1_csi2_check.c`, `test_frame_starts` and the frame-start
checks in `test_jobs`) and in the driver's tests (`drivers/rp1-csi2`, with the integration
stand-in in `tests/frames.rs`).

Run in a local session after this PR merges, on the CM5 (Raze #2), with an OV9782 on the board
linked to the CSI-2 receiver (`rp1-csi2`) in the board file. Take the board lock named in
`AGENTS.md`, `/run/lock/board-gpu.lock`. Build on NVMe or SSD, never on the Github HDD. Report CM5
timings only.

## What the count is, and what the board has to confirm

`frames` counts the frame-start interrupts the channel raised since START. Measured earlier on
this block (`testing/board-runs/D5.md`, "Nothing armed, nothing seen"): a channel with no buffer
address raises no interrupt and its debug counter does not move. So a frame start while no buffer
has ever been armed since START is in no count, and the first published frame can then carry a
sequence above zero only if the count moved before it. A start while an address is still set
but no buffer is free is counted as a drop. The sensor's landing rule (`post_values_at`, F =
`after.count - 1`) needs every frame start counted, so check 1 decides whether the count can be
used as the sensor's frame number on this block.

## Checks

1. **The count matches the sensor.** Start the receiver and the sensor, keep the `frames` stream
   drained, and read `camera.receiver` `frame_starts` once a second for 60 s. Pass: `count` rises
   by the sensor's frame rate (60 at the full frame, 120 at 1280x400 RAW10 on the 120 fps mode),
   and the published frames' sequence numbers run from `count - 1` at each read with no gaps.
   Fail: a gap in the sequence, or `count` rising slower than the sensor's frames. Record the
   result as it is; a gap is the case above and is a finding, not a fix to make in this PR.
2. **A stopped receiver has no count.** `frame_starts` answers `None` before START and after STOP,
   and the kernel's `valid` is zero then (the raw ioctl reads zeros). Pass on both.
3. **The latest time is a frame start.** `latest_ns` is a CLOCK_MONOTONIC time within one frame
   period of the read, in the same clock as `Frame::timestamp_ns` (`backends/linux-sys`
   `monotonic_stamps_land_between_the_boot_clock_readings`). Pass: the difference from a read of
   `clock_gettime(CLOCK_MONOTONIC)` taken just after is under 1000/fps milliseconds.
4. **Dropped starts.** With the consumer holding every buffer, the `dropped` counter rises by one
   per frame start, and `frame_starts.count` rises by the same amount, the drops being the starts
   the channel showed (check 1 decides whether any were missed). Pass on the counts agreeing.
5. **A restart begins the count again.** Stop the block the module reports as failed (or unbind
   and rebind it); the next read after the restart is lower than the last read before it, and
   `valid` is set again. Pass on both.
6. **An older module.** On a kernel without `LEMNOS_RP1_CSI2_IOC_FRAME_STARTS` the driver answers
   `NOT_SUPPORTED` (`ENOTTY` from the node), which the posting caller reads as "this receiver
   cannot count". Pass: `post_values_at` answers `NOT_SUPPORTED` and writes nothing.

The checks use the OV9782 only; no other sensor is on the board.
