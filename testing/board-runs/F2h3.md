# F2h3: the frame period with the global line, as measured on a board

Run on Raze #2 (serial a317bcbee5226d57), 2026-11-14, by the BR1 session: mode 1 (1280x800 RAW8, 96 MHz system
clock), 5000 frames per run, `lemnos-rate-proof --measure-only`, the mean interval being (last - first) / 4999 from
the frame timestamps. The step is the one in `F2h.md`; this file is its result. Untested on board for everything not
listed here: the 10-bit modes (80 MHz clock), the 720 and 400 windows, and the other boards' sensors.

## The three models

N is the frame length in lines, HTS the line length in system clocks, G the value of registers 0x382C/D.

| model | period | |
|---|---|---|
| M0 | `N x HTS` | what the contract stated before |
| A | `(N + 1) x HTS` | one extra line |
| B1 | `(N - 1) x HTS + G`, G = 1456 (the reset value) | the global line |

## What the board showed

Gated clock (HTS 765), runs at 1100, 2082, 2091, 2092, 2093, 2102 and 4300 lines: least-squares slope +7.4 ppm
(+-0.2) of the nominal line, which is the crystal; intercept 7205.1 ns (+-3.9). B1's term, (1456 - 765) / 96 MHz, is
7197.9 ns (residual +7.2 ns); A (one extra line, 7968.75 ns) is 764 ns away and M0 (no term) 7205 ns away.

A write of 0x382C/D from 1456 to 1536 (80 system clocks) moved the mean period at 2092 lines from 16 677 958 ns to
16 678 790 ns, +832 ns; B1 predicts 80 / 96 MHz = +833.3 ns.

Continuous clock (HTS 728): there G = 1456 = 2 x HTS, so A and B1 are the same period, `(N + 1) x HTS`. The runs sit
+8.1 ppm over it.

Register 0x382E reads 0x01 on the board, so its bit 2 reads 0, while 0x382C/D (0x05B0) is used once per frame
all the same. The driver therefore does not gate the term on that bit. 0x382C/D read 0x05 0xB0 before the write.

Every absolute period sits +7.5 to +8.1 ppm over B1: the crystal, not modelled.

## What changed

`camera.sensor/1` `Mode` gains the last field `frame_offset_ps` (`#[added]`): the frame period is
`N x line_time_ps + frame_offset_ps`, that is `(N - 1) x HTS + G` with the offset `G - HTS` in picoseconds. The
driver reports 7 197 916 ps gated and 7 583 333 ps continuous at 96 MHz, 8 637 500 and 9 100 000 at 80 MHz.
`max_fps_milli` is the rate at the shortest frame on that period (RAW10 gated 114 917 -> 114 804, continuous
120 758 -> 120 626). The rate functions take the offset, and the rate proof's expected value is the mode's period.
For 60.000 fps gated the frame length is 2091 lines (59 989 milli-fps), where 2092 (59 986) was asked before and
now gives 59 960.

## The rate proof on these runs

The tool's check compares the rate from the timestamps with the nominal rate, both in whole milli-fps, limit 200
ppm. On `lines x line time` every one of these runs failed (205 to 823 ppm). On the mode's period all twelve pass:

| run | rate from timestamps (milli-fps) | was (ppm) | now (ppm) |
|---|---|---|---|
| gated 2082 | 60 247 | 431 | 0 |
| gated 2091 | 59 988 | 433 | 0 |
| gated 2092 | 59 959 | 433 | 0 |
| gated 2093 | 59 930 | 450 | 16 |
| gated 2102 | 59 674 | 435 | 0 |
| gated 1100 | 113 987 | 823 | 8 |
| gated 4300 | 29 177 | 205 | 0 |
| continuous 2188 | 60 240 | 464 | 16 |
| continuous 2197 | 59 994 | 449 | 0 |
| continuous 2198 | 59 966 | 466 | 16 |
| continuous 2199 | 59 939 | 466 | 16 |
| continuous 2208 | 59 695 | 452 | 0 |

The steps of 16 and 8 ppm are the whole-milli-fps rounding. The `measurement:` line, in nanoseconds on the mean,
reads +7 to +8 ppm in each case (for 2092 gated, +134 ns). The run after the write (G = 1536, which the tool is not
told) reads 50 ppm over, as it should: the period is 833 ns longer than the model for G = 1456.

## Not established here

The 10-bit modes and the 720 and 400 windows are not measured on a board. Any other value of G than 1456 and 1536 are taken from the same
arithmetic (the global line counted in the mode's own system clock) and have not been run on a board.
