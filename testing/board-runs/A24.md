# A24: lemnosd streams of dma-bufs

Status: untested on board. A stream declared `memory = "dma-buf"` is covered in lemnosd over the
real socket with sealed memfds standing in for the dma-bufs, and, on the build machine only (an
x86 PC, 4 KiB pages, no camera or image block), with real dma-bufs from `/dev/dma_heap/system`:
allocation by heap name, the CPU mapping with the sync calls around `write` and `read`, the
handle lent to the producer, all the descriptors to the client in one message, the client's
check that each is a dma-buf, and its mapping. No hardware has been given one of these handles.

What only a board can show:

- that the heaps a board has are found by the names its board file uses, and that lemnosd's user
  may open them (the node is `root:video 0660` on the build machine);
- that a heap which rounds to 16 KiB pages gives buffers the client maps the same way;
- which heap a block's driver can take buffers from (`system` pages are not contiguous; a block
  without an IOMMU wants `linux,cma` or a vendor heap);
- that what hardware wrote into a buffer is what the consumer reads through its own mapping,
  with no cache trouble between them. The consumer does not bracket its reads with
  `DMA_BUF_IOCTL_SYNC` in this change; lemnosd brackets `write` and `read`. If stale or torn
  bytes are seen at the consumer on a block whose DMA is not cache-coherent, that is the finding
  that the consumer needs the bracket too.

Before running: take the board lock named in `AGENTS.md`. Builds go on NVMe or SSD.

## 1. The service's stream path on each of the board's heaps

For each heap under `/dev/dma_heap/`:

```sh
LEMNOS_TEST_DMA_HEAP=/dev/dma_heap/<heap> \
  cargo test --release -p lemnosd --test stream_dma -- --nocapture the_same_on_dma_bufs
LEMNOS_TEST_DMA_HEAP=/dev/dma_heap/<heap> \
  cargo test --release -p lemnos-linux-sys -p lemnos-linux-stream when_a_heap_is_named
```

Pass: the tests pass and the first prints `ran on dma-bufs from /dev/dma_heap/<heap>`. Record
which heaps pass, the page size (`getconf PAGESIZE`), and the size the heap gave a 5000-byte
buffer (the test asserts only that it is at least 5000).

## 2. A board file with a dma-buf stream, on the installed service

1. Add to a device in the board file:

   ```toml
   [devices.streams.frames]
   buffers = 8
   buffer_bytes = 1228800
   memory = "dma-buf"
   heap = "system"
   ```

   Start lemnosd as the user it runs as in the image. Expect it to start: an unknown `memory` or
   a `heap` that is not one file name stops it with the key named.
2. Open the stream from a client built from this tree. Expect it to open, and
   `ls -l /proc/<lemnosd pid>/fd | grep -c dmabuf` to be 8 while it is open and 0 after the
   client exits.
3. Set `heap = "nothing"` and restart. Expect the service to start, and opening the stream to be
   refused with status -2 and the text `can't get dma-bufs for the stream`; expect every other
   stream on the board to open as before.
4. Open the stream from a client built from `next` before this change (or send StreamOpen, kind
   17, by hand). Expect Refusal -95 and the connection to stay up.

## 3. A buffer through hardware

Needs one of the follow-ups that hands a handle to a block: a receiver queueing the handle to
V4L2 as DMABUF, or the g2d driver registered (`testing/board-runs/A23.md`, check 2, which this
change makes runnable through lemnosd). Record for each block and heap: whether the block took
the handle, and whether 1000 consecutive frames read at the consumer match what the block was
asked to write.
