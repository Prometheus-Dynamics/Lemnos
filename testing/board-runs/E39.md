# E39: capture straight into the stream's buffers

Status: untested on board. The pump is run through a real `Host` with sealed memfds standing
in for the stream's dma-bufs and a stand-in node that, like the kernel, keeps its own hold on
each dma-buf it is queued and fills a frame by writing through that hold. No test opens a
video node, so nothing below has been seen to happen.

What only a board can show:

- that each vendor capture driver takes `VIDIOC_REQBUFS` with `V4L2_MEMORY_DMABUF`, starts
  streaming with nothing queued, and takes the stream's dma-heap buffers at `VIDIOC_QBUF`;
- that queueing a slot on another dma-buf (a new consumer's) makes the kernel let go of the
  old one;
- the frame rate and CPU use against the copy path.

Before running: take the board lock named in `AGENTS.md`. Builds go on NVMe or SSD.

## 1. `sunxi-vin` (A733 board)

The board entry of `testing/board-runs/E12.md`, with the stream as dma-bufs:

```toml
[devices.streams.frames]
memory = "dma-buf"
buffers = 4
buffer_bytes = FRAME_BYTES
```

1. Start the camera chain and open the `frames` stream. Expect frames, each `FRAME_BYTES`
   long, with the node's sequence numbers in order.
2. `strace -e ioctl` on lemnosd: expect `VIDIOC_REQBUFS` with memory 4 (DMABUF) once, and a
   `VIDIOC_QBUF`/`VIDIOC_DQBUF` pair per frame; no `mmap` of the video node.
3. Compare 100 frames with the same scene captured by copy (the same entry without `memory`).
   They should match to sensor noise. Record the frame rate and lemnosd's CPU both ways.
4. Close the consumer and open another. Expect frames again within a few ticks, `dropped`
   up by the frames in flight, and `/proc/PID/fdinfo` of lemnosd to show the old dma-bufs
   gone once each slot has been queued again.
5. Give the stream `buffer_bytes` smaller than a frame. Expect no frame, `errors` equal to the
   buffer count, and no `VIDIOC_QBUF`.
6. If `VIDIOC_REQBUFS` with DMABUF is refused, expect the driver to open the node again and
   run by copy: record that the driver takes no dma-bufs.

## 2. `rkcif` raw frames (RK3588 board, vendor kernel)

```toml
[[devices]]
id = "cif"
driver = "rkcif"
config = { capture = "stream_cif_mipi_id0", order = "bggr" }

[devices.streams.frames]
memory = "dma-buf"
buffers = 4
buffer_bytes = FRAME_BYTES
```

(`capture` is the routed channel's video node by its media entity name: read it from
`media-ctl -p` on the receiver's media device; `order` is the sensor's.)

1. Configure the link, start, open `frames`. Expect `frame_stream` to answer `frames`,
   frames in the compact layout `configure` answered (`stride` a multiple of 256), and
   `counters` counting them.
2. Check the pixel format the node kept is the one asked for: a start that fails with
   `NOT_SUPPORTED` means the vendor driver names its raw formats otherwise for this sensor;
   record `v4l2-ctl --list-formats` of the node.
3. Steps 2 to 6 of section 1.
4. With the ISP also streaming from the receiver, record whether both paths run at once.

Record anything else.
