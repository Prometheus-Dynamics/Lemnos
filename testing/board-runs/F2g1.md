# F2g1 board run: the resample readout, and the chain proof's checks

Not run on a board: untested on board. The board check for the camera chain needs the receiver node
to allow a second open (the kernel change another worker is writing) and the sensor's latch to run
with the chain linked. Run on the reference board after that change is on the board:

1. Copy the built `lemnos-chain-proof`, `lemnos-sensor-proof` and `lemnos-isp-proof` (same directory,
   the chain proof starts the latch from its own directory) and the board file `pisp-camera-chain.toml`.
2. Start a fresh daemon: `lemnosd --board pisp-camera-chain.toml --socket chain.sock`, wait for the
   sensor to report running (see F2g2's check for the start time).
3. `lemnos-chain-proof --socket chain.sock --frames 9000 --frame-length 910 --pattern 1 --fps <rate of the mode>
   --reference <one packed RAW10 frame of the same scene> --latch-trials 20`
   Exit 0 and the line `chain proof: pass` are the result. Any line `... not checked ...` is a failure.
4. Dark scene: the same run with `--allow-skip lit-scene` skips only the mean-luma and latch checks,
   and prints that it did.
5. `lemnos-isp-proof --input <a frame> --socket chain.sock --isp cam0-be --sensor cam0-sensor --jobs 1
   --resample 640x400 --sharpen 1`: the luma eighths must be the scene's (not 0), and the sharpen line
   must show a non-zero mean luma difference.

What is measured, and what is not:
- Frame rate from the front end's timestamps against the mode's rate (within 2 %).
- Sequence gaps, timestamp steps that do not increase, and timestamps that are in the future or older
  than one second (CLOCK_MONOTONIC from the frame start).
- Dropped and errored jobs on the front end, back end and receiver; the receiver's counters are read
  while the chain is linked.
- The first frame's lines equal to the reference, and the back end's mean luma on a lit scene.
- The sensor's latch, run beside the chain.
- Not measured: colour, exposure beyond the latch.

Before the board run, on the host only (sim tests): the isp proof's luma readout reads the luma plane
at 640x400 (a test fails with the old 40-pixel margin, which read zero at 640 wide), the zero-gain
configuration passes the driver's check, and the chain proof's checks (rate tolerance, timestamp
age, the not-checked failures) are unit tests.

Since M25 the chain proof also runs end to end on a PC in CI (`testing/crates/camera-proof/tests/chain_end_to_end.rs`):
the real service and the real sensor, power switch, front end and back end drivers over simulated
blocks (`testing/crates/camera-sim`), the proof started as a process on the service's socket, the
latch beside it. What that run cannot show, and the board run must:

- the real blocks' timing, DMA and statistics, and the module's checks of a job (the simulated blocks
  apply the front end's job checks only);
- the module's per-address I2C claims and the receiver node's claims, so the receiver's counters
  read while the front end streams (the simulated receiver never refuses them);
- a CMA heap's limits and a real dma-buf's cache behaviour (a PC run uses the host's system heap
  where it can be opened, and sealed memfds otherwise);
- the sensor's real frame period (the model takes the system clock from the PLL register: 80 MHz for
  RAW10, so 1832 lines is 59.95 fps), its real exposure latch (the model latches a group launched
  in frame F into the picture of frame F + 2), and a lit scene;
- a frame start with no job queued (the simulated front end waits for a job, where the silicon
  drops the frame and counts it);
- per-frame relay latency and the wake source of the drivers: the proof prints the back end's
  frame timestamp to client time, and no wake source.
