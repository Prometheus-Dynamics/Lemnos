# E3 board run: vglite

Status: untested on board. The kernel request layouts are pinned against the C compiler's sizes
and offsets for the vendor header (`kendryte/k230_linux_sdk` at `fc6cc21`,
`buildroot-overlay/package/vg_lite/VGLiteKernel/vg_lite_kernel.h` and
`VGLiteKernel/linux/vg_lite_ioctl.h`), and every command stream the driver builds is compared word
for word with the vendor library's own output for small fixtures (recorded on a host by the dev
branch's oracle). No stream has reached a GPU, on dev or here.

Run in a local session after this PR merges, on a K230D board running the K230 SDK's kernel with
the `vg_lite` module loaded and `/dev/vg_lite` present. The CM5 has no VGLite. Build on NVMe or
SSD, never on the Github HDD. Module loads and unbinds are allowed; report each.

## Checks

1. **The node answers.** `ls -l /dev/vg_lite /dev/dma_heap/`; `dmesg | grep -i vg_lite`. Record
   the kernel version, the heaps present, and the chip id and revision the driver reads
   (`VG_LITE_CHECK`: the driver takes chip id 0x265, revision 0x1003, customer 0x417, and
   refuses anything else as `Unsupported`).
2. **Every operation.** As root (or with access to the node and the heap):

   ```sh
   LEMNOS_VGLITE_NODE=/dev/vg_lite LEMNOS_VGLITE_HEAP=/dev/dma_heap/system \
     cargo test --release -p lemnos-driver-vglite --test board -- --ignored --nocapture
   ```

   Pass: every test passes: a crop, a horizontal flip, a half turn and a quarter turn equal to a
   CPU remap byte for byte; a part fill that leaves the rest alone and an A8 fill; a palette
   expansion equal to the table lookup; an opaque SRC_OVER equal to its foreground; a flat source
   staying flat under bilinear and area resize; a 1-pixel horizontal line on exactly pixels 1 to 6
   of row 3 and a 2-wide butt stroke on exactly rows 1 and 2, columns 1 to 6; an L8 line refused
   as `Unsupported`; dma-bufs from the heap staged both ways with `staged_bytes` equal to twice the
   frame. Run it three times. If the heap is not `system`, try `linux,cma` and record which.
3. **Lines against Bresenham.** `cargo test --release -p lemnos-driver-vglite --test lines --
   --ignored --nocapture`. Record the count of pixels that differ from the reference for each
   slope it prints. A line is a width-1 square-capped stroke; it is not claimed equal to
   Bresenham, so a difference is a record, not a failure, and decides whether the RGA caps table
   may list `FixedOp::Line` for this route.
4. **What the sources did not state.** Through checks 2 and 3, record whether the outputs match.
   Each of these is inferred, not read from a source that states it, and a mismatch in check 2
   points at one of them:
   - the register meanings marked unverified in `lemnos-driver-vglite-sys` (`stream.rs`);
   - the RISC-V cache clean and invalidate encoding (`0x0275000b`, the T-Head `dcache.civa`);
   - whether the GPU clips path coverage to the tessellation window and the target, or only to
     the window: a stroke running past the target's edge (draw one from (-4, 4) to (12, 4) on an
     8x8 target) must change nothing outside the target's 256 bytes, read back through a
     staging buffer one row larger than the target (a few lines over the board test);
   - float rounding of the stroke port (FMA contraction may differ from the vendor's build).
5. **The kernel stays clean.** Record what `dmesg` says through checks 2 to 4: it must be clean of
   vg_lite errors, GPU hangs and bus faults.
6. **Recovery.** While operations run in a loop (a small program over `Vglite`), unload the
   `vg_lite` module or unbind the device (report which), wait 20 s, and load or bind it again.
   Pass: calls answer `Device` and then `BackingOff`, with delays of 250 ms doubling to 8 s and
   holding there; once it is back, the next due call reopens and operations pass again. Nothing
   panics and the driver never stops trying. If a wait fails, the staging memory and the context
   are leaked on purpose (the GPU may still use them): record the process's mapped size before
   and after.

Record each result here.
