# E38: deinterlace and JPEG blocks for a caller

Status: untested on board. The A733 deinterlacer's request builders are checked against
sealed memfds, its contract driver is run through a real `Host` on a device that records the
requests it was given, and its unsafe layer is tested on plain files (which answer `ENOTTY`).
The JPEG session's move onto the shared service layer is tested by layouts and by what it
refuses. No test opens `/dev/deinterlace` or `/dev/mpp_service`.

## 1. `a733-di` (A733 board, vendor kernel)

```toml
[[devices]]
id = "di"
driver = "a733-di"

[devices.streams.jobs]
memory = "dma-buf"
buffers = 8
buffer_bytes = 4194304
job_slots = 8
job_bytes = 20
```

1. Start lemnosd. Expect the device `Running`, and `/dev/deinterlace` not open until a job.
2. Post a bob job (`TAG_CONFIG` with mode 1, a `TAG_FRAME` each for an NV12 input and
   output, two references). Expect `Done` with a one-byte read-back, `DI_IOC_GET_VERSION` once
   at open, then the five settings requests, `DI_IOC_CHECK_PARA` and `DI_IOC_PROCESS_FB`
   (`strace -e ioctl`), and no `mmap` of the node. Compare the output with the input's field
   interpolated by hand: this settles which `base_field` value is the top field (E20 left
   it open). Record the job's time.
3. Post the same job again. Expect one `DI_IOC_PROCESS_FB` and no settings request.
4. Post a motion-adaptive job with noise reduction (two inputs, two planar outputs). Expect
   `Done`.
5. Post a job whose chroma plane ends one byte past its buffer. Expect `Refused` and no
   request. The same with a chroma offset of 0.
6. On a kernel built with `CONFIG_SUNXI_DI_SINGEL_FILE`, expect the open to fail (the version
   request answers `ENOTTY`), every job `Failed`, and health `the deinterlacer failed`.
7. Kill the caller mid-job and attach another. Expect its first job to run.

## 2. JPEG through `rk-mpp` (RK3588 board, vendor kernel)

```toml
[[devices]]
id = "jpegd"
driver = "rk-mpp"
config = { block = "jpeg-decoder" }
```

with the job stream of `testing/board-runs/E37.md`.

1. Call `block`: `rk-mpp:jpeg-decoder`.
2. With a caller that builds the decoder's register file for one picture (the address
   registers are the ones `lemnos-driver-rk-jpeg`'s `regs` names), decode it: a `TAG_WRITE` of
   the file, a reference for the stream and one for the picture, a `TAG_READ` of the status
   register. Expect `Done`, the status `lemnos_driver_rk_jpeg::status` reads as finished, and
   the picture to match a software decoder's.
3. From a test binary, `lemnos_driver_rk_jpeg::open("/dev/mpp_service")` and a `Jpeg` session
   on it: expect `hw_id` to answer the block's id, and `release_buffers` to succeed.
