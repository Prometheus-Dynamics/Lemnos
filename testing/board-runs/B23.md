# B23: Linux boards provide DMA memory

Status: untested on board. `LinuxBoard` now provides the `dma` need for a board-file name
`dma:<block>`, where `<block>` is the device name of a platform block bound to `lemnos.ko`. Each
buffer is the module's `LEMNOS_IOC_ALLOC` for that block: a dma-buf, mapped for the CPU, with the
device address the module reported. Covered in unit tests (name parsing, refusals, the checks on
what the module answers, CPU access bounds, no allocation on read and write) and in the QEMU harness
on x86 with the real module and its test block: the address equals what the module reports when it
maps the same dma-buf on the block again, the CPU reads back what it wrote, a block not bound to the
module gives `NO_DEVICE`, no module gives `NOT_SUPPORTED`, and every dma-buf is closed on release and
on drop (the block's unbind, which waits for every buffer, then returns). No hardware block has been
given one of these addresses.

What only a board can show:

- that the module, built for the board's kernel, binds the block the memory is for, and reports a
  sensible `dma_bits` for it;
- that a block programmed with the address writes into the memory the CPU then reads, with no cache
  trouble (the module's memory is `dma_alloc_coherent`, and `sync_for_device`/`sync_for_cpu` bracket
  it with `DMA_BUF_IOCTL_SYNC` all the same);
- on the K230 capture path (`drivers/k230-capture`, E30): which block to name. The ISP there is
  bound to the vendor's `vvcam-isp` driver, so `lemnos.ko` cannot own it, and the address the module
  gives is valid for the DMA setup of the block it does own. That is the same address the ISP sees
  only if both blocks have the same view of memory (no IOMMU, the same `dma-ranges`). This run is
  where that is checked; if it can't be shown, the memory must not be handed to the ISP.

Before running: take the board lock named in `AGENTS.md`. Builds go on NVMe or SSD. Module loads,
binds, unbinds and reboots are allowed; report each.

## 1. The memory of a block bound to the module

Load the module owning one block of the board and bind it (see `kernel/README.md`, "Claiming a
block"). Then, with the module test harness's backend check built for the board:

```sh
lemnos-module-check module stock <gpio chip> <dir>   # or a small program doing what check_dma does
```

with `DMA_NAME` set to `dma:<that block's device name>`. Pass: every `dma` line `ok`, the printed
device address below `2^dma_bits` from `LEMNOS_IOC_INFO`, and `the address is the one the module
reports for the block` (on a block behind an IOMMU the import may be a second mapping, in which case
record both addresses rather than fail).

Then unbind the block: pass when the unbind returns at once (no buffer is left held).

## 2. The K230 capture path (only if 1 passes on that board)

1. Find a block on the same interconnect as the ISP whose device-tree node has no `iommus` and the
   same `dma-ranges` (or none) as the ISP's. Record both nodes. If there is none, stop: the capture
   driver cannot be given memory safely on this board.
2. Load `lemnos.ko` owning that block, bind it, and in the board file give `K230Capture`
   `dma = "dma:<that block>"`.
3. Run E30's checks (`testing/board-runs/E30.md`) with `lemnosd` instead of the test program it
   describes. Pass: the driver binds, frames arrive, and a frame's bytes are the sensor's (a test
   pattern from the sensor, if it has one, checked byte for byte).

Report the board, kernel, the block named, `dma_bits`, the addresses printed, and the results.
