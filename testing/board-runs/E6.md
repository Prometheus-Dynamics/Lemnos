# E6 board run: nonai2d, OSD and border

Status: untested on board. What landed is `drivers/nonai2d`'s `overlay` module (the OSD and border
controls of the SDK's `nonai-2d` driver, built from checked regions and borders, their layouts
pinned by tests and by `layout-check/run.sh` against clang for host and riscv64 and gcc) and
`Device::draw`, which sets them and runs the engine once in place on a frame. All of it passes its
tests against a played-back node. No control from this code has reached a `nonai-2d` node.

Run in a local session after this PR merges, on a K230 board running the K230 Linux SDK kernel
(`kendryte/k230_linux_sdk` at `fc6cc21`, the tree the driver was read from) with the `nonai2d`
package's module loaded, after `testing/board-runs/E5.md` check 1 passes. Nothing else may have
the node open (see check 6). Build on NVMe or SSD, never on the Github HDD. Module loads and unbinds
are allowed; report each.

## Checks

1. **The controls are there.** `v4l2-ctl -d <node> --list-ctrls-menus`. Pass: controls
   `0x00981b00` (mode, integer 0..3), `0x00981b03` (OSD attr, u8 array of 320) and `0x00981b04`
   (border attr, u8 array of 16) exist. If the arrays have other lengths, stop: the attribute
   layouts differ from the header this was written from.

2. **The engine stays inside the frame.** This is the one place the design relies on the
   hardware: that the engine writes only the frame, at the frame's stride, and draws regions and
   borders only where they lie. Allocate one dma-buf from the CMA heap three frames long, fill it
   with `0xA5`, and build an ARGB32 1920x1080 frame on its middle third (a dma-buf per plane is
   needed, so use a frame-sized dma-buf and two frame-sized guard dma-bufs allocated right before
   and after it; record their bus addresses from `dmesg` with the driver's info logging, and that
   they touch). Draw, in turn: one region at each corner flush with the edges (`x + width ==
   1920`, `y + height == 1080`), eight regions, a border with line width 8 at the largest
   rectangle the checks allow, 32 borders. Pass: every guard byte still reads `0xA5` after each,
   and the frame shows each region and border where asked. Repeat with an NV12 frame (guards
   around both planes). If any guard byte changed, the drawing path is not sound on this kernel:
   record it and do not use `Device::draw`.

3. **The engine runs once per draw.** With the kernel's info logging on
   (`nonai_2d_info`), draw 10 times. Pass: 10 `device_run` lines, and no `nonai_2d_config_job`
   from a capture queue (the frame is queued for capture in conversion mode, where the kernel
   starts nothing). Draw a region with `osd_alpha` 0x80 over a frame of one colour. Pass: the
   region's pixels are blended once (half way), not twice.

4. **Line placement.** Draw a border of line width 4 at (100, 100), 200x100 on a black frame.
   Record whether the line lies inside, across or outside the rectangle. The checks keep a
   margin of the line width on every side whichever it is; record it so the margin can be
   tightened if it is inside.

5. **Back to conversion.** After a draw, run `E5.md`'s conversion test on the same open device.
   Pass: it passes. Then draw with 3 borders, then ask for 2. Pass: refused with
   `InvalidInput`; after reopening, 2 is drawn and only 2 appear.

6. **Another opener.** With a draw loop running, open the node from a second process and close
   it. Record what happens (the kernel shares one channel among opens: the second open resets
   the mode and regions, its close frees the OSD images). Expected: the loop's next draws
   misbehave or fail. This is a kernel fault the driver cannot prevent; record it for the
   kernel's owners.

7. **OSD formats.** One region per `OsdFormat` over a grey frame, with a test image whose
   colours are known. Pass: each shows the right colours. Record any format whose channels come
   out swapped.

Record the results here, with the kernel version.
