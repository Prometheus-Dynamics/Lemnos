# Board run: I5i8 (payload bays, the boot partition's cut safety)

Status: **untested on board.** Nothing here has run on a board. Every check is written as the question the
firmware or U-Boot must answer, with the expected answer from the code and the PC tests that assume it.
These checks are NOT a condition of merging I5i8 (AGENTS.md: a PR is not held back for a board run).

Run on a board only in a local session that takes `/run/lock/board-gpu.lock` and uses the CM5 (Raze #2).
Builds go on NVMe or SSD, never on the Github HDD. Report each result as a row below with the command, the
PC time, and the board's own output; a check that is not run stays `untested`.

## Pi firmware family (tryboot), the boot partition written by `lemnos-ctl boot-partition`

| # | Check | Expected (from the code) | Why it matters | Result |
|---|---|---|---|---|
| P1 | The firmware reads `os_prefix=slots/bayN/` (a directory a set) and loads `kernel8.img`, `initramfs.cpio`, `board.dtb`, `cmdline.txt` and `overlays/lemnos-board.dtbo` from it. | Yes, for every set 0 to 2. The overlay is read only with `overlays/README` present (generated, 162 bytes). | Every bay boot depends on it. | untested |
| P2 | The pointer file is two sectors, each a whole `os_prefix` line with a `#lemnos-crc32=` line and `#` padding. The firmware reads the LAST whole `os_prefix` line. Test: write the second sector only with a new line; boot. | The new line is read (commit = the second sector). | The commit point of a trial or a default switch. | untested |
| P3 | First pointer sector garbage (including NUL bytes), second sector a valid line. | The firmware reads the second sector's line (the boot goes to the named set). | A cut during the first of the two writes. | untested |
| P4 | The reverse: the second sector garbage (including NUL), the first a valid line. | The firmware reads the first sector's line. | A cut during the second write (the commit was not reached: the old line remains in the other sector). | untested |
| P5 | Both sectors whole, with DIFFERENT set names. Which `os_prefix` wins? | The LAST whole line in the file, which is the second sector's. Expected from the design; the firmware's own rule is not read from its source. | Decides which set boots after a cut between the two writes of a pointer. | untested |
| P6 | A sector read error on the pointer file (a bad sector in the test image). | The firmware falls back to `config.txt`'s default `os_prefix` (none): the fixed text has no `os_prefix`, so the boot takes the root files. | What boots when no pointer can be read. | untested |
| P7 | No whole pointer in either sector (a state no cut produces: the second sector is written first, so one sector is whole at every cut; made on purpose on the test image). | The firmware finds no `os_prefix` and no kernel at the partition's root (the image has none: no copy is kept there), so it does not boot. Record what it prints. | Confirms that the write order, not a fallback copy, is what keeps the default reachable. | untested |
| P8 | Trailing `#` padding after the `cmdline.txt` payload (cmdline is padded with spaces, the other payloads with zeros) and the zero padding after the kernel, initramfs and dtb in their bays. | The Pi loaders read the stored length from the file and ignore the padding; `cmdline.txt` padding is spaces. | The bays are fixed size; the payload is shorter. | untested |
| P9 | The bay record `bayinfo.rec` (two sectors, a CRC per copy) is not read by the firmware. It is read only by slot-init and the installer. | The firmware never opens it. | Its presence in the set directory must not change the boot. | untested |
| P10 | The `lemnos,overlay-sha256` marker and the `.dtbo` in a bay: the stored bytes hash to the manifest's `boot.overlay`. | Yes (the every-boot check hashes the stored bytes). | The overlay is verified byte for byte. | untested |

## U-Boot on block storage (the environment and `extlinux.conf` per set)

| # | Check | Expected (from the code and the U-Boot source at v2026.10) | Result |
|---|---|---|---|
| U1 | With the environment U-Boot saved on its first start (`lemnos_env` set), the driver's default switch writes `previous_bay`, `default` and `default_bay` in one write of the inactive copy; `printenv` shows all three after a restart, and U-Boot's own variables are unchanged. | Yes, with `CONFIG_ENV_REDUNDANT=y` and `CONFIG_ENV_SIZE` as the board file says (`--uboot-config`). | untested |
| U2 | A trial arm writes `trial`, `trial_bay` and `trial_attempts` in one write; the script's `saveenv` after taking an attempt keeps `trial_bay`. | Yes: the script reads `trial_bay` after the attempt is saved. | untested |
| U3 | `sysboot ... /slots/bayN/extlinux/extlinux.conf` loads the composed `extlinux.conf` and the kernel from `../kernel8.img` (relative to the extlinux directory), with no `fdt` line (the script has loaded `slots/bayN/board.dtb` and named the boot source in it). | Yes; the composed text names the set's files relatively. | untested |
| U5 | The download-mode loop (`fastboot usb`) is entered when neither `slots/${trial_bay}/` nor `slots/${default_bay}/` starts, and the next pass tries the bays again. | Yes: the loop's steps are `trial default` and nothing else (no root copy). | untested |
| U4 | A gzip kernel on the U-Boot form is refused by the tool by name (I5i8), so no board run is needed for it; the uncompressed kernel boots. | The tool refuses; `booti` needs `kernel_comp_addr_r` and `kernel_comp_size`. | untested |
| U6 | The default's files unreadable (`/slots/${default_bay}/board.dtb` will not load) with `previous_bay` set by a default switch: the board starts the previous bay as a trial, and `/chosen` carries `lemnos,default-failed = "files"` (I5i10: the step reads only `previous_bay`, `default_bay` and `trial_bay`; no variable `previous`). | Yes: `printenv` shows no `previous`, the previous bay's kernel starts, slot-init records the default's failure. | untested |

## NAND (UBI): not built in I5i8

The NAND family's bays are parked, not implemented: the `ubi` record refuses an install and a free by name
("payload bays on raw NAND (UBI) are parked"). A board check for them is written when that code exists.

## Known gaps the checks above do not cover

- The real-size power-cut sweep was run on the PC (debug build, sampled), not on the board's storage: a
  board's sector writes may reorder or tear differently from the image file.
- Raw NAND (UBI) bays are parked; the `ubi` record refuses an install by name.
