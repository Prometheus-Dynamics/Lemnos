# D5 board run: the rp1-csi2 receiver

Status: untested on board. The receiver's checks (`kernel/test/lemnos_rp1_csi2_check.c` in QEMU
against a fake receiver with memory for registers) and the driver's mock tests have passed. No frame
has been received from real hardware by this code, and every board fact below is still only as
measured on dev (`kernel-modules/lemnos/rp1-csi2.md`, Board #1, 2026-11-06).

Run in a local session after this PR merges, on the CM5 (Raze #2) with an OV9782 on `cam0` (i2c-10,
1280x800 RAW10 over 2 lanes at 800 Mbit/s, the same sensor setup as the dev measurement, from a
register file kept outside the repository). Take `/run/lock/board-gpu.lock`. Module loads, unbinds and
rebinds are allowed; report each. Build on NVMe or SSD, never on the Github HDD. Report CM5 timings
only.

## Getting the block

`lemnos.ko` built for the board's kernel (`make KDIR=<the image's kernel build> ARCH=arm64
CROSS_COMPILE=...`), then:

```sh
D=1f00128000.csi     # or whichever device the camera is on
echo $D > /sys/bus/platform/drivers/rp1-cfe/unbind
insmod lemnos.ko owned=raspberrypi,rp1-cfe
echo lemnos-rp1-csi2 > /sys/bus/platform/devices/$D/driver_override
echo $D > /sys/bus/platform/drivers/lemnos-rp1-csi2/bind
```

Sensor kernel driver and regulator unbinding as in `rp1-csi2.md` on dev. Afterwards, restore
(`echo > driver_override`, rebind `rp1-cfe`) and confirm `rp1-cfe` registers its nodes again.

The camera proof tool (D9) drives this end to end; before it exists, drive the node directly: a
small program opens `/dev/lemnos-rp1-csi2-$D`, makes a stream with
`LEMNOS_RP1_CSI2_IOC_STREAM_CREATE` on a CMA heap dma-buf, maps the ring and pool, and starts with
`LEMNOS_RP1_CSI2_IOC_START`. The module's `lemnos_rp1_csi2_check` shows the shape of it (fake
hardware stubbed).

## Checks

1. **RAW10 at 60 fps, as measured before.** VTS 1822 (60.28 fps), 3600 frames, 8 CMA buffers of
   1,280,000 bytes, stride 1600. Pass: 3600 published, 0 `dropped`, 0 `errors`, and sampled rows as
   the dev run: the colour bars exact, rows of the same parity identical. Report the frame rate and
   frame start to frame end time; dev measured 60.28 fps and a median of 7465 µs.

2. **120 fps.** VTS 910 (120.63 fps), 9000 frames, the same buffers. Pass: 0 `dropped`, 0 `errors`,
   as dev measured at this rate. Then again under 4 busy loops, one per core.

3. **DMA address in the region register.** Mid-stream, read the channel's `ADDR0`/`ADDR1` over a
   debug path (`/sys/kernel/debug/...` of `rp1-cfe` isn't available with it unbound; use the kernel
   module's dmesg or a one-shot `devmem`, not a path a normal build keeps) and confirm it is a pool
   buffer address given by `lemnos_stream_create.pool_addr + n * pool stride`. Pass: every value seen
   is one.

4. **Stop waits for the DMA, with the sensor still streaming.** This is the check the design depends
   on most. Stop the receiver while the sensor keeps streaming, and watch the node's INFO:
   - `STOP` returns in a time well under a frame, with `LEMNOS_RP1_CSI2_INFO_WEDGED` clear.
   - If `WEDGED` is set here, the channel's `CSI2_CH_DEBUG` line counter keeps moving with the channel
     disabled, and the evidence in `lrc_dma_stopped` doesn't work on this block. Then buffers would
     stay pinned until reboot on every stop. Report it: the fix is either stopping the sensor first or
     a different "channel is idle" signal, not a relaxed wait.

5. **Stop with a frame in flight, every way.** Repeat check 4 with a frame known to be in flight, for
   each of: `STOP`; closing the stream's descriptor; closing the node; unbinding the block with the
   stream still open. Pass: none hangs, no kernel warning, none wedges, and the pool's memory shows
   no change after the stop returns (write a pattern into the pool after the stop and read it back
   for 2 s, to catch a channel still writing).

6. **Restart.** After each stop, start again. Pass: frames arrive, sensor and link undisturbed.

7. **Cache coherence.** Confirm the pool's mapping shows frame data at full speed without an explicit
   sync; if it needs one, record which, for the consumer in D9 to do (`DMA_BUF_IOCTL_SYNC`).

8. **Second receiver.** With a second camera, bind both and confirm the node names differ
   (`/dev/lemnos-rp1-csi2-<device>`) and neither disturbs the other.

## Not tested here, and known not to be

Virtual channels other than 0, data types other than RAW8/10/12/14, 1 lane, link rates other than
800 Mbit/s, the D-PHY polarities (read from the device tree, no board has swapped lanes), a missing
frame end from the real channel.
