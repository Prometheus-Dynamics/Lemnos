# D5 board run: the rp1-csi2 receiver

Run on the board 2026-11-11 through `lemnosd`: checks 1, 2, 4 (as stop, client kill and unbind while
streaming) and 6 passed after three fixes; checks 3, 5 (every way), 7 and 8 were not run.

Run in a local session after this PR merges, on the CM5 (Raze #2) with an OV9782 on `cam0` (i2c-10,
1280x800 RAW10 over 2 lanes at 800 Mbit/s, the same sensor setup as the dev measurement, from a
register file kept outside the repository). Take `/run/lock/board-gpu.lock`. Module loads, unbinds and
rebinds are allowed; report each. Build on NVMe or SSD, never on the Github HDD. Report CM5 timings
only.

## Getting the block

`lemnos.ko` built for the board's kernel (`make KDIR=<the image's kernel build> ARCH=arm64
CROSS_COMPILE=...`), then:

```sh
D=1f00128000.csi     # or whichever device the camera is on
echo $D > /sys/bus/platform/drivers/rp1-cfe/unbind
insmod lemnos.ko owned=raspberrypi,rp1-cfe
echo lemnos-rp1-csi2 > /sys/bus/platform/devices/$D/driver_override
echo $D > /sys/bus/platform/drivers/lemnos-rp1-csi2/bind
```

Sensor kernel driver and regulator unbinding as in `rp1-csi2.md` on dev. Afterwards, restore
(`echo > driver_override`, rebind `rp1-cfe`) and confirm `rp1-cfe` registers its nodes again.

The camera proof tool (D9) drives this end to end; before it exists, drive the node directly: a
small program opens `/dev/lemnos-rp1-csi2-$D`, makes a stream with
`LEMNOS_RP1_CSI2_IOC_STREAM_CREATE` on a CMA heap dma-buf, maps the ring and pool, and starts with
`LEMNOS_RP1_CSI2_IOC_START`. The module's `lemnos_rp1_csi2_check` shows the shape of it (fake
hardware stubbed).

## Checks

1. **RAW10 at 60 fps, as measured before.** VTS 1822 (60.28 fps), 3600 frames, 8 CMA buffers of
   1,280,000 bytes, stride 1600. Pass: 3600 published, 0 `dropped`, 0 `errors`, and sampled rows as
   the dev run: the colour bars exact, rows of the same parity identical. Report the frame rate and
   frame start to frame end time; dev measured 60.28 fps and a median of 7465 µs.

2. **120 fps.** VTS 910 (120.63 fps), 9000 frames, the same buffers. Pass: 0 `dropped`, 0 `errors`,
   as dev measured at this rate. Then again under 4 busy loops, one per core.

3. **DMA address in the region register.** Mid-stream, read the channel's `ADDR0`/`ADDR1` over a
   debug path (`/sys/kernel/debug/...` of `rp1-cfe` isn't available with it unbound; use the kernel
   module's dmesg or a one-shot `devmem`, not a path a normal build keeps) and confirm it is a pool
   buffer address given by `lemnos_stream_create.pool_addr + n * pool stride`. Pass: every value seen
   is one.

4. **Stop waits for the DMA, with the sensor still streaming.** This is the check the design depends
   on most. Stop the receiver while the sensor keeps streaming, and watch the node's INFO:
   - `STOP` returns in a time well under a frame, with `LEMNOS_RP1_CSI2_INFO_WEDGED` clear.
   - If `WEDGED` is set here, the channel's `CSI2_CH_DEBUG` line counter keeps moving with the channel
     disabled, and the evidence in `lrc_dma_stopped` doesn't work on this block. Then buffers would
     stay pinned until reboot on every stop. Report it: the fix is either stopping the sensor first or
     a different "channel is idle" signal, not a relaxed wait.

5. **Stop with a frame in flight, every way.** Repeat check 4 with a frame known to be in flight, for
   each of: `STOP`; closing the stream's descriptor; closing the node; unbinding the block with the
   stream still open. Pass: none hangs, no kernel warning, none wedges, and the pool's memory shows
   no change after the stop returns (write a pattern into the pool after the stop and read it back
   for 2 s, to catch a channel still writing).

6. **Restart.** After each stop, start again. Pass: frames arrive, sensor and link undisturbed.

7. **Cache coherence.** Confirm the pool's mapping shows frame data at full speed without an explicit
   sync; if it needs one, record which, for the consumer in D9 to do (`DMA_BUF_IOCTL_SYNC`).

8. **Second receiver.** With a second camera, bind both and confirm the node names differ
   (`/dev/lemnos-rp1-csi2-<device>`) and neither disturbs the other.

## Not tested here, and known not to be

Virtual channels other than 0, data types other than RAW8/10/12/14, 1 lane, link rates other than
800 Mbit/s, the D-PHY polarities (read from the device tree, no board has swapped lanes), a missing
frame end from the real channel.

## Result, 2026-11-11

Run 2026-11-11 on the CM5 (Raspberry Pi Compute Module 5 Rev 1.0, Raze #2), kernel `7.2.9-v8-16k`,
with `lemnos.ko`, `lemnosd` and the tools from PR F2a, built on NVMe and copied to
`/tmp/lemnos-run/` on the board. Raw logs are kept off the repository.

The camera path was taken from the product: its camera service stopped, `rp1-cfe`, the
sensor's kernel driver, the sensor's fixed regulator (`cam0_reg`, RP1 GPIO34) and `pispbe` unbound,
`insmod lemnos.ko owned=raspberrypi,rp1-cfe,raspberrypi,pispbe pisp_be=raspberrypi,pispbe`, the
receiver bound to `lemnos-rp1-csi2` and the back end to `lemnos` through `driver_override`.
`lemnosd` ran a board file with `gpio-power-switch` on `gpiochip15:34` (default on), `ov9782` on
`i2c-10` and `rp1-csi2` on `1f00110000.csi`, 8 buffers of 1280000 bytes, `memory = "dma-buf"`,
`heap = "linux,cma"`. The client was `lemnos-camera-proof` over the daemon's socket. Afterwards
everything was put back and the product's camera produced its 478 receiver interrupts a second
again, as before the run.

Mode 0 on this sensor is 1822 lines of 9.5625 µs by default (57.37 fps) and 910 at the shortest
(114.8 fps): the 60 and 120 fps of the checks are this board's 57 and 115.

1. Colour bars (`--pattern 1`), 3600 frames: 57.366 fps from the timestamps, 0 sequence gaps,
   receiver counters `frames 3600, dropped 0, errors 0`, every frame identical, rows equal by
   parity, all 8 buffers used. The scene (`--pattern 0`), 600 frames: every frame differs from the
   one before, 0 dropped. Start took 43 ms. Frame start to the client holding the frame: median
   8.4 ms, p99 8.9 ms (the frame itself takes 7.84 ms to arrive). The proof frame was checked on
   the PC: the even pixels of a row alternate 1023 and 0 in eight runs starting at columns 0, 154,
   316, 478, 640, 802, 964 and 1126.
2. Frame length 910, 9000 frames: 114.802 fps, 0 gaps, 0 dropped, 0 errors; frame start to client
   median 8.5 ms, p99 9.0 ms. With four busy loops (one per core) the client falls behind (p99 66
   ms against 8 buffers): 9000 frames, 0 errors, and 89 frame starts with nothing armed, which the
   hardware never reports (see below), counted from the frame intervals.
3. Not run (no register read over the node in this run).
4. Stop while streaming took 3.9 to 4.1 ms every time (7.9 ms once under load), with the sensor
   still streaming. A client SIGKILLed mid-stream is gone at once and `dmesg` stays clean; the
   camera drivers keep streaming for the next client, which stops and starts it. Unbinding the
   receiver under `lemnosd` while streaming returned in 0.010 s and its 8 attachments went to 0;
   after the rebind the driver was healthy within 2 s and the next run was normal.
5. Not run every way.
6. Every stop above was followed by a start with frames.
7, 8. Not run (no second camera; coherence not measured separately).

What the run found, each fixed with a test that fails without the fix:

- **Nothing armed, nothing seen.** The channel makes no frame start while it has no address, and
  its debug frame counter does not move: frames that start then are invisible, as with the stock
  driver. The module armed the channel only at start and on frame start and end, so a stream
  started with no consumer, or whose consumer gave buffers back late, never armed again and
  delivered nothing. Fix: when arming finds no buffer, the module tries again 1 ms later from a
  high-priority work item (`kernel/lemnos_rp1_csi2.c`, also `lemnos_pisp_fe.c`); QEMU checks for
  both. On the board: attach 1 s after start, then reattach ten times: the first frame 27 to 30 ms
  after each attach, 10 of 10 frames with content each time.
- **A short frame published.** After a quick stop and start, the first interrupt carried frame
  start and end together with one line written, and an all-zero frame was published. Fix: at frame
  end the module compares the lines the channel counted with the frame's height, and a frame that
  is short is an error, not a frame. Board: 10 rounds of kill and restart, 0 all-zero frames, 3
  counted as errors; 9000 frames at 115 fps, 0 errors.
- **The receiver driver kept a dead node** after an unbind and answered `EIO` for ever. Fix: it
  drops a node that answers `ENODEV` and opens the path again (`drivers/rp1-csi2/src/hw.rs`).
- The driver's lost-frame count carried from one start to the next; it now starts at 0.
