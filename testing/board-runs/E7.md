# E7 board run: the rkvpss offline scaler

Status: untested on board. The checks that keep a job inside its dma-bufs, the layouts (matched
against `gcc` on the vendor header) and the scaler's reopen and backoff have passed their tests
(`drivers/rkvpss-sys/src/tests.rs`, `drivers/rkvpss/src/tests.rs`). No job has gone through this
code on a real block. Everything the code depends on was read from the vendor kernel's source
(rockchip-linux/kernel `develop-6.1`: `include/uapi/linux/rk-vpss-config.h`,
`drivers/media/platform/rockchip/vpss/{common.h,vpss_offline_v20.c,vpss_offline_v10.c,stream_v20.c}`),
not from a running board. Dev's code, which this ports, was never run on a board either.

Run in a local session after this PR merges, on an RV1126B board running the vendor kernel with
the `rkvpss` driver bound (an RK3576 board, whose block takes the same structures through
`vpss_offline_v10.c`, second). Build on NVMe or SSD, never on the Github HDD. Module loads, unbinds
and rebinds are allowed; report each.

## Getting the node

```sh
for v in /sys/class/video4linux/video*; do echo "$v $(cat $v/name)"; done   # rkvpss-offline
ls /dev/dma_heap/
```

Find which output channels the camera path uses on this image (its `rkvpss` main and scale paths
streaming, or not). Selecting a channel for offline mode takes it from the camera path, and the
driver refuses the selection while that path runs. Use a channel the camera path does not.

## Checks

1. **Frames come out right.** As root:

   ```sh
   LEMNOS_RKVPSS_CHANNEL=<n> cargo test --release -p lemnos-driver-rkvpss --test board -- --ignored --nocapture
   ```

   Pass: the test passes (1920x1080 NV12 to 640x360 NV12, as it is and flipped, rows within 6 of
   the ramp, chroma grey) and prints a median and slowest job time. Run it three times, and once
   more on channel 1 and on one of channels 2 to 5. Record the times. A failure from the flipped
   frame means the flip writes elsewhere than the code assumes: record the rows it got.
2. **No allocation on the job path.** Check 1 asserts 0 allocations over 100 jobs on an open node.
   Pass: it does not fail there.
3. **Output stride.** The code refuses an output stride that is not a multiple of 16, because the
   vendor driver then hands the block a stride of 0. Write a 36x36 GREY output with stride 48 (a
   small program over `Job` and `Scaler`), into a buffer of exactly 48 x 36 bytes followed by a
   guard page filled with `0xa5`. Pass: the output is right and the guard is untouched. Then, with
   the check commented out locally (never committed), stride 36 into a 36 x 36 buffer with a guard:
   record what the block wrote and whether it touched the guard. This says whether the rule can be
   relaxed.
4. **Flip stays inside.** For each output format CH1 writes (RGB565, RGB24, BGR24, XRGB32, XBGR32)
   and for NV12 on CH0, a flipped 640x360 output into a buffer of exactly its frame size plus a
   `0xa5` guard page before and after it. Pass: both guards untouched, and the first output row is
   the last input row. `RGB24` and `BGR24` matter most: the vendor driver gives the block their
   flipped picture size in bytes, the 16- and 32-bit formats in pixels.
5. **Limits.** Pass or record each:
   - CH0 at 1:32 down and up (the driver's check allows it; the header's comment gives 1:8 across
     and 1:6 down for CH0).
   - 4096x3072 NV12 in, unscaled, out on CH1, in one pass.
   - A scaled output larger than 1920x1080 on CH2 is refused here; record whether the block
     would have taken it (with the check off locally).
6. **Recovery.** While jobs run in a loop (a small program over `open_at` with the monotonic
   clock), unbind the platform device behind the node, wait 20 s, and bind it again. Report the
   unbind and bind. Pass: `run` returns `Device`, then `BackingOff`, with delays of 250 ms doubling
   to 8 s and holding there; after the bind the next due call opens the node again (it may have a
   new number: pass `find()` inside the open function), selects the channel again and the jobs
   run, with the backoff cleared.
7. **Buffers are let go.** Run 50 jobs each with a new pair of dma-heap buffers, dropping each
   pair after its job, then `release_buffers`. Pass: the heap's use (`/sys/kernel/debug/dma_buf/bufinfo`)
   is back to where it started after `release_buffers`, and not before it.

## The driver (`Rkvpss`, E4b)

Added after the library: the `#[driver]` type `rkvpss` providing `image.scaler/1` over `Jobs` on
one configured channel, its jobs on the device's `jobs` stream. Untested on board: it is tested
on the host's real frame stream with sealed memfds for the dma-bufs and a played node
(`drivers/rkvpss/tests/driver.rs`). It needs `lemnosd` to list it (`scripts/generate-builtins.py`,
a maintainer step) before these checks can run.

8. **Through the daemon.** A board file with the device (`channel` set to one the camera path
   does not use) and its stream (`memory = "dma-buf"`), as the crate docs show. Attach a consumer,
   write the ramp of check 1 into buffer 0, post a 1920x1080 to 640x360 NV12 job with
   `Filter::Bilinear` into buffer 1. Pass: one completion on buffer 1 with the job's identity and
   345600 bytes, rows within 6 of the ramp; `counters` 1 job, 0 errors; health `Ok`. A job with
   `Filter::Area` completes with 0 bytes.
9. **The refusal.** The stream's `memory` left out. Pass: after a consumer attaches, health is
   `Failed` with the text naming `memory = "dma-buf"`.
10. **A frame that does not finish.** The driver holds back the output of a request that failed
    after the node was open (the vendor driver's 500 ms timeout leaves the block running), until a
    later frame ends. To provoke one: unbind the platform device while a job runs (report it).
    Pass: no completion for that job until the bind; health says the output is held back; after
    the bind, within one backoff, the driver's own 32x32 frame runs, the held-back job's
    completion arrives with 0 bytes, and jobs run again. Record `dmesg` (IOMMU faults or
    "working timeout"). Record also whether the block, after a real timeout, finishes the next
    frame normally: the hold-back rests on the block running one frame at a time and on a later
    frame end meaning the earlier one is over, which is read from the source, not seen.
11. **Attachments are let go.** Attach, run 10 jobs, detach, attach again, run one job. Pass: the
    heap's use returns to its level before the first consumer once the second consumer's job has
    run (the driver calls `release_buffers` after a consumer change when nothing is held back).
