# I5i3: the count-based fallback on the Pi firmware family

Untested on board. Nothing here has run. The firmware points below come from the vendor
documentation (copies: `config_txt_boot.adoc`, `conditional.adoc`, `rn2712.md`), and each one must
be shown on a real board before the fallback is trusted.

## Points to be run on a board

| # | Point | Where it is written | Check |
|---|---|---|---|
| 1 | `[boot_count&4]` in config.txt selects `previous.txt` when bit 2 is set | `conditional.adoc` (`boot_count`, expression filter) | At the 2025-12-08 bootloader build: write a count of 4 with `vcmailbox 0x0003808d`, boot, and read which pointer the board runs. Then count 0, 3, 8. |
| 2 | `kernel_watchdog_timeout=15` hands the watchdog to the OS and resets the board when it is not serviced | `config_txt_boot.adoc` (`kernel_watchdog_timeout`) | At that build: `/proc/device-tree` shows the timeout; stop the service, time the reset. |
| 3 | A panicking kernel that restarts itself increments `boot_count` and is not caught by the watchdog partition | inferred from `bcm2835_wdt.c` (not documentation) | Force a panic at boot, count the resets, read the count after each. |
| 4 | A brown-out reset clears `boot_count` like a full power loss | not in the documentation | Brown the supply out during boot; read `chosen/bootloader/count` and `chosen/bootloader/rsts`. |
| 5 | Which `rsts` bits each cause leaves. Observed so far (coordinator's reads, 2026-11-13): `0x1000` after a power-on; `0x20` after a software restart (twice, one on a tryboot trial boot); `0x1020` on a tryboot boot. Not yet observed: a watchdog expiry, a brown-out, a panic restart, and a plain reboot. The rule in `drivers/slot-store/src/fallback.rs` (`cause`) reads the FULL value, no bit masked: `0x1000` is power; `0x20` and `0x1020` are restart (an episode); any other value is `Unknown`, which counts no episode and is kept in the boot history with its raw value and reported by name. A partition-field value beside these bits is therefore `Unknown` until the board run shows it occurs; the run decides whether the rule changes. Bit 6 (`0x40`) is the watchdog's `HADWRH` in the sources read, and partition bit 3: a reading with it is `Unknown` and is recorded as read. The run reads `rsts` before and after the watchdog driver's probe (which clears the field with `PM_RSTS_PARTITION_CLR`, clearing bit 6 too) and records whether bit 6 changes. To run: after each cause, boot, then `od -An -tx1 /proc/device-tree/chosen/bootloader/rsts` (four bytes, big-endian) and `od -An -tx1 /proc/device-tree/chosen/bootloader/count`, and record both in the run log. Causes: (a) watchdog expiry (open `/dev/watchdog` on a test boot and stop feeding it); (b) brown-out (the supply cut short during boot); (c) panic restart (`echo c > /proc/sysrq-trigger` on a test boot); (d) plain reboot after `systemctl reboot`. A reading the rule calls `Unknown` is recorded as read, not forced into a class.
| 6 | The firmware's behaviour with `previous.txt` missing or invalid | not in the documentation | Remove or corrupt it; boot. |

## What a run does

For each point: the step, the expected value, and the value read, with the firmware version from
`vcgencmd version`. A point that fails stops the fallback until its design is revised; the board
reports the failure, not the workaround.

## Pass criterion

- Point 1: the pointer the board runs matches the bit, for counts 0 to 15.
- Point 2: the reset happens after the configured time without service.
- Points 3 to 5: recorded as they are; the classification is changed only from these values.
- Point 6: the board reaches its default or previous; if it does not, the open item is recorded.

## Source of the bit meanings (read here, not on a board)

Read from the Raspberry Pi kernel (`raspberrypi/linux` at `rpi-7.2.y`, fetched read-only): `drivers/watchdog/bcm2835_wdt.c` defines the `rsts` register at offset `0x20`, the `PM_RSTS_HADWRH_SET` bit (`0x40`), the partition field (bits 0, 2, 4, 6, 8, 10; `PM_RSTS_PARTITION_CLR` = `0xfffffaaa`, applied at probe) and the halt partition `0x555`. `__bcm2835_restart` writes the partition and keeps every other bit. The names `HADPOR`, `HADWRF`, `HADDRF` and `HADWRQ` do not occur in that tree, nor in `drivers/pmdomain/bcm/bcm2835-power.c` or `drivers/mfd/bcm2835-pm.c`: the power-on bit (`0x1000`) and the warm-reset bit (`0x20`) are named nowhere in the sources read. Their meaning here is the board observations above, not the sources.
