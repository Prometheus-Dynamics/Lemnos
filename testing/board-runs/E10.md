# E10 board run: the Rockchip AI-ISP (rkaiisp)

Status: untested on board. The layouts (generated from `gcc` on the vendor headers and asserted at
compile time in `drivers/rkaiisp/src/layout.rs`), the parameter checks and the ring's reopen and
backoff have passed their tests (`drivers/rkaiisp/src/tests.rs`). Nothing in the crate reaches the
block: no Linux `Device` exists, and the pool and queue requests are left out because how far the
block's data channels reach cannot yet be bounded (see the crate documentation). Every fact was read
from rockchip-linux/kernel `develop-6.1` at `77168c8d5ab82399f65a80e9f807b50ba37cf483`:
`include/uapi/linux/rk-aiisp-config.h`, `include/uapi/linux/rk-isp2-config.h`,
`drivers/media/platform/rockchip/aiisp/{aiisp.c,aiisp.h}`.

Run in a local session on an RV1126B board running the vendor kernel with `rkaiisp` bound
(`dmesg | grep -i aiisp`, a video node named `rkaiisp` in `v4l2-ctl --list-devices`). Take
`/run/lock/board-gpu.lock`. Build on NVMe or SSD, never on the Github HDD. Module loads, unbinds and
rebinds are allowed; report each. The checks below need a local, never committed `Device` over the
node (V4L2 meta output, memory-mapped buffers, the private requests in `uapi`).

## What the code assumes and the board must confirm

1. **Layouts on the target.** Run `layout-check/run.sh` with `CC=aarch64-linux-gnu-gcc` against the
   board kernel's own `include/uapi/linux` (with a sysroot). Pass: "layout.rs matches the headers".
2. **The node's order.** `SET_PARAM_INFO` (para_size 16384, max_runcnt 8), `SET_MEMORY_MODE`,
   `REQBUFS` of 4 memory-mapped meta-output buffers. Pass: `VIDIOC_G_FMT` reports `RK1P` with
   `buffersize` 2752 + 16384 * 8 = 133824, and `QUERYBUF` gives that length.
3. **The weight read stops where the check says.** With the vendor camera pipeline running the
   AI denoise (the pool set up by its own user space, not Lemnos), queue one parameter buffer whose
   last run's weights end exactly at `kwt_offet + 4 * ceil(kwt_size / 4)` = the buffer's used bytes,
   with `kwt_size` not a multiple of 4, and fill the rest of the kernel buffer with `0xa5`. Then the
   same with the weights moved to the buffer's last bytes. Pass: no IOMMU fault (`dmesg`), and the
   output matches the run with the weights in the middle of the buffer.
4. **The checks the kernel lacks.** Queue a buffer the crate refuses (`sw_aiisp_level_num` 0, then
   a channel reading `AIISP_LAST_OUT` with `model_runcnt` 8) through the local `Device` with the
   check bypassed. Record what the kernel does (an oops, a garbage read, nothing). This is evidence
   only; never leave the board in that state, reboot after.
5. **For the missing bound.** For each channel source and channel mode the vendor user space uses,
   record the read base, stride and height registers (`rkaiisp_showreg=1`, `dmesg`) next to the
   pool's buffer sizes, and with each pool buffer followed by a guard page of `0xa5`, whether any
   guard is touched. This is what a later PR needs to land the pool and queue paths.
