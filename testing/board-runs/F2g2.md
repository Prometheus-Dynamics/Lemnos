# F2g2 board check: the camera sensor's first start

Not run. untested on board.

## What the change claims

The sensor's first chip-ID read is no longer made in the start call. The driver answers the start at
once, and the first read is made at the first tick at least 10 ms later (`POWER_UP_NS`). Before this,
the first read was made inside the start, a few milliseconds after the board's power switch was started.
The datasheet's power-up timing (at least 1 ms from the supplies to the reset line, at least 5 ms from the
reset line to system ready, and 8192 XVCLK cycles before the first SCCB transaction) puts the first safe
read after about 6 ms. A failed first read is retried with the existing backoff (250 ms, doubling, capped
at 8 s, never giving up).

The hypothesis that this fixes the board's delay is NOT confirmed. The board showed the first binds
failing with NO_DEVICE (-19) and the sensor running (degraded) after about 7 s (7.1 s once). The current
retry schedule is 0.25, 0.5, 1, 2, 4 s, so a success at about 7.75 s means four retries failed before it,
which a delay of a few milliseconds at the first read does not explain on its own. The board run below
decides it.

## What the board run must measure

Use the chain board file (`testing/boards/pisp-camera-chain.toml`) with the daemon as the product runs it.
Do not change the board's power, clock or reset lines.

1. Ten daemon starts. For each, the time from the daemon's start to the sensor's first `running` state
   (`lemnos-ctl --socket <socket> list`, polled every 50 ms), and whether the sensor was ever `degraded`
   before it ran. Record each as a row.
2. The same ten starts with the sensor's first start done by hand (`lemnos-ctl`'s start action) at a
   known time after the daemon starts. The first chip-ID read is the first bus transaction on
   `/dev/i2c-10` after the start; time it with `strace -e trace=ioctl -tt` on the daemon if available, or
   from the driver's health change.
3. The time from the power switch's line change (`gpio:pinctrl-rp1:34`, the camera regulator) to the first
   successful chip-ID read, if a scope or a logic probe is on the line; say "not measured" otherwise.
4. With the chip answering at its first attempt, the sensor must be `running` with no `degraded` at any
   poll. A first attempt that fails is a failure of this change, whatever it then recovers to.
5. The failure rule still holds: a sensor left unplugged (the bus has no device at 0x60) is retried
   with the backoff, its interval never more than 8 s, and it never gives up. Record the intervals from
   the health changes for a 30 s window.

## Pass

- Item 4: the first attempt succeeds on all ten starts.
- Item 1: the first `running` is within about 100 ms of the daemon's start on all ten, against about 7 s
  before.
- Item 5: the intervals are 0.25, 0.5, 1, 2, 4, 8 s, then 8 s.
