# E36: a caller serves the gadget (`usb.function/1`)

Status: untested on board. The contract, the driver's job handling and its checks are covered
against the mock function and the mock stream; the whole path (board file, host, stream,
contract calls) through a real `Host` on the simulated board; and the service's socket, the
client, the shared stream memory and the `lemnos-usb-echo` tool against a running service on
the simulated board. The Linux backend's per-endpoint transfer queues are tested on files and
pipes, which finish every transfer before `io_submit` returns. No test goes near a real
controller, FunctionFS mount or USB device, so nothing below has been seen to happen.

What only a board can show:

- that a FunctionFS endpoint file takes a native AIO read and write that stay under way after
  `io_submit` returns, completes them when the host moves the bytes, and that `io_getevents`
  with a zero timeout finds the completion (`backends/linux-sys/src/aio.rs`, `Queue`);
- that a read left under way loses nothing: bytes the host sends between two ticks are there
  for the next one, in order, with transfer ends where the host put them;
- that `io_cancel` on such a transfer ends it (the path taken when the host configures the
  device again, and when the driver goes);
- what a write of 0 bytes does (a zero-length packet is expected);
- the rates the driver reaches at its 1 ms tick.

Before running: take the board lock named in `AGENTS.md`. Builds go on NVMe or SSD. Set the
board up as `testing/board-runs/E25.md` section 0 says, with a host computer on the other end
of the cable that can send control and bulk transfers (pyusb or libusb's examples).

The board entry (the controller is named under `uses`, not as `bus`):

```toml
[[devices]]
id = "gadget"
driver = "usb-gadget"
uses = { function = "udc:NAME" }
config = { vendor = 0x1209, product = 0x0001, manufacturer = "Lemnos", product_name = "E36 check", serial = "E36-0001", interfaces = "interface 0xff 0 0 check\nendpoint in bulk\nendpoint out bulk\n" }

[devices.streams.data]
buffers = 8
buffer_bytes = 69632
job_slots = 16
job_bytes = 18
```

Build the tool: `cargo build --release -p lemnos-usb-echo`. It serves the device through the
service: it answers a vendor IN request with `lemnos`, accepts a vendor OUT request, stalls
anything else, and sends back on the IN endpoint what arrives on the OUT endpoint.

## 1. Nobody serving: the device refuses

1. Start lemnosd, plug the cable in. Expect the device to enumerate as in E25 section 1.
2. From the host, send a vendor request (`bmRequestType` 0xc0, `bRequest` 1, `wLength` 8).
   Expect a stall. `lemnos-ctl` (or a call of `counters`) shows `requests_unanswered` 1.

## 2. A caller answers control requests

1. Run `lemnos-usb-echo SOCKET` on the board. Expect it to print the two endpoints, the
   stream's name and `event Configured` (or nothing more, if the host configured the device
   before it started: `state` told it).
2. Send the vendor IN request again. Expect the host to read `6c 65 6d 6e 6f 73` (`lemnos`),
   and the tool to print the request with `Ok(6)`.
3. Send it with `wLength` 3. Expect `6c 65 6d`.
4. Send a vendor OUT request (0x40) with 4 bytes. Expect the tool to print them.
5. Send a class request (0x21). Expect a stall.
6. Stop the tool with a request outstanding (send one from a host program that waits, and
   kill the tool before it answers: pause it with `SIGSTOP` first). Expect the stall within a
   tick of the tool's connection closing, and `requests_unanswered` up by one.
7. With the tool stopped by `SIGSTOP`, send a request and wait. Expect a stall after
   `control_timeout_ms` (1 s). Record the time the host measured.

## 3. Bytes both ways

1. From the host, write 5 bytes to the OUT endpoint and read the IN endpoint. Expect the same
   5 bytes. Repeat with 512, 513, 4096 and 65536 bytes.
2. Write a zero-length packet and read. Record what the host reads (a zero-length packet is
   expected).
3. Write 64 MiB in 64 KiB transfers while reading it back, and compare. Any difference, or a
   byte out of order, is a finding against the transfer queues. Record the rate, and lemnosd's
   CPU use meanwhile.
4. The same with the host reading slowly (1 ms sleep between reads). Expect no loss: the send
   waits for the endpoint, and the receive behind it for its buffer.
5. `strace -f -e io_submit,io_getevents,io_cancel` on lemnosd for a few transfers. Expect one
   `io_submit` per transfer and `io_getevents` calls that return 0 between them. An
   `io_submit` that blocks is a finding.

## 4. The host comes and goes

1. Pull the cable while the echo runs. Expect the tool to print `event Deconfigured` and
   `job 2 ended NotConfigured`; health stays `Ok`.
2. Plug it back in. Expect `event Configured`, and the echo to work again with no restart.
   Bytes sent just before the pull may be lost; nothing sent after the replug may be.
3. Reset the device from the host during a transfer. Expect the same as a replug, and no
   stale bytes of the transfer that was cut in what the host reads afterwards.
4. Halt the OUT endpoint through the contract (`set_halt`), write to it from the host and
   expect a stall; clear it from the host (`CLEAR_FEATURE`) and expect the echo to carry on.
5. Stop lemnosd while the echo runs. Expect the tool to end, the gadget to go from the host,
   and no process left waiting in `io_destroy` (`ps`: lemnosd gone within a second).

Record anything else.
