# E36: a caller serves the gadget (`usb.function/1`)

Status: untested on board. The contract, the driver's job handling and its checks are covered
against the mock function and the mock stream; the whole path (board file, host, stream,
contract calls) through a real `Host` on the simulated board; and the service's socket, the
client, the shared stream memory and the `lemnos-usb-echo` tool against a running service on
the simulated board. The Linux backend's per-endpoint transfer queues are tested on files and
pipes, which finish every transfer before `io_submit` returns. No test goes near a real
controller, FunctionFS mount or USB device, so nothing below has been seen to happen.

What only a board can show:

- that a FunctionFS endpoint file takes a native AIO read and write that stay under way after
  `io_submit` returns, completes them when the host moves the bytes, and that `io_getevents`
  with a zero timeout finds the completion (`backends/linux-sys/src/aio.rs`, `Queue`);
- that a read left under way loses nothing: bytes the host sends between two ticks are there
  for the next one, in order, with transfer ends where the host put them;
- that `io_cancel` on such a transfer ends it (the path taken when the host configures the
  device again, and when the driver goes);
- what a write of 0 bytes does (a zero-length packet is expected);
- the rates the driver reaches at its 1 ms tick.

Before running: take the board lock named in `AGENTS.md`. Builds go on NVMe or SSD. Set the
board up as `testing/board-runs/E25.md` section 0 says, with a host computer on the other end
of the cable that can send control and bulk transfers (pyusb or libusb's examples).

The board entry (the controller is named under `uses`, not as `bus`):

```toml
[[devices]]
id = "gadget"
driver = "usb-gadget"
uses = { function = "udc:NAME" }
config = { vendor = 0x1209, product = 0x0001, manufacturer = "Lemnos", product_name = "E36 check", serial = "E36-0001", interfaces = "interface 0xff 0 0 check\nendpoint in bulk\nendpoint out bulk\n" }

[devices.streams.data]
buffers = 8
buffer_bytes = 69632
job_slots = 16
job_bytes = 18
```

Build the tool: `cargo build --release -p lemnos-usb-echo`. It serves the device through the
service: it answers a vendor IN request with `lemnos`, accepts a vendor OUT request, stalls
anything else, and sends back on the IN endpoint what arrives on the OUT endpoint.

## 1. Nobody serving: the device refuses

1. Start lemnosd, plug the cable in. Expect the device to enumerate as in E25 section 1.
2. From the host, send a vendor request (`bmRequestType` 0xc0, `bRequest` 1, `wLength` 8).
   Expect a stall. `lemnos-ctl` (or a call of `counters`) shows `requests_unanswered` 1.

## 2. A caller answers control requests

1. Run `lemnos-usb-echo SOCKET` on the board. Expect it to print the two endpoints, the
   stream's name and `event Configured` (or nothing more, if the host configured the device
   before it started: `state` told it).
2. Send the vendor IN request again. Expect the host to read `6c 65 6d 6e 6f 73` (`lemnos`),
   and the tool to print the request with `Ok(6)`.
3. Send it with `wLength` 3. Expect `6c 65 6d`.
4. Send a vendor OUT request (0x40) with 4 bytes. Expect the tool to print them.
5. Send a class request (0x21). Expect a stall.
6. Stop the tool with a request outstanding (send one from a host program that waits, and
   kill the tool before it answers: pause it with `SIGSTOP` first). Expect the stall within a
   tick of the tool's connection closing, and `requests_unanswered` up by one.
7. With the tool stopped by `SIGSTOP`, send a request and wait. Expect a stall after
   `control_timeout_ms` (1 s). Record the time the host measured.

## 3. Bytes both ways

1. From the host, write 5 bytes to the OUT endpoint and read the IN endpoint. Expect the same
   5 bytes. Repeat with 512, 513, 4096 and 65536 bytes.
2. Write a zero-length packet and read. Record what the host reads (a zero-length packet is
   expected).
3. Write 64 MiB in 64 KiB transfers while reading it back, and compare. Any difference, or a
   byte out of order, is a finding against the transfer queues. Record the rate, and lemnosd's
   CPU use meanwhile.
4. The same with the host reading slowly (1 ms sleep between reads). Expect no loss: the send
   waits for the endpoint, and the receive behind it for its buffer.
5. `strace -f -e io_submit,io_getevents,io_cancel` on lemnosd for a few transfers. Expect one
   `io_submit` per transfer and `io_getevents` calls that return 0 between them. An
   `io_submit` that blocks is a finding.

## 4. The host comes and goes

1. Pull the cable while the echo runs. Expect the tool to print `event Deconfigured` and
   `job 2 ended NotConfigured`; health stays `Ok`.
2. Plug it back in. Expect `event Configured`, and the echo to work again with no restart.
   Bytes sent just before the pull may be lost; nothing sent after the replug may be.
3. Reset the device from the host during a transfer. Expect the same as a replug, and no
   stale bytes of the transfer that was cut in what the host reads afterwards.
4. Halt the OUT endpoint through the contract (`set_halt`), write to it from the host and
   expect a stall; clear it from the host (`CLEAR_FEATURE`) and expect the echo to carry on.
5. Stop lemnosd while the echo runs. Expect the tool to end, the gadget to go from the host,
   and no process left waiting in `io_destroy` (`ps`: lemnosd gone within a second).

Record anything else.

## Detached form (image where lemnosd owns the USB link)

On that image the board's one device-mode port carries the image's own gadget (the link the bridge
hands to the comm core, NCM, ACM), served by lemnosd and the bridge. E36 needs its own gadget entry
and a caller (`lemnos-usb-echo`) on its function, so the image's link is gone for the whole run,
not only for 4.5: the PC is the USB host of the E36 device and has no login meanwhile. The run is
therefore one detached script, `scripts/checks/E36.sh`:

1. `ALT_BOARD`: the image's `/etc/lemnos/board.toml` with its `usb-gadget` device replaced by the
   entry above (serial `E36-0001`). The check refuses a file without a `hw-watchdog` device (lemnosd
   on it would not feed, and the board would reset one period later) or without `E36-0001`, and one
   `lemnos-ctl validate` rejects. It is copied into the run directory.
2. lemnosd is restarted on that file through a runtime drop-in
   (`/run/systemd/system/lemnosd.service.d/90-lemnos-check-E36.conf`, an `ExecStart=` override; gone
   at the next boot, removed by the check or the restore). One lemnosd down window, 5 s restore.
3. The echo tool runs on the board (`ECHO_BIN`, built for the board), its output stamped into
   `echo.out`. The PC runs sections 1 to 4.4 as the host, inside `WINDOW_S`, and ends the window
   with a vendor OUT request carrying the 4 bytes `DONE` (the tool prints
   `request data [44, 4f, 4e, 45]`). The host side keeps its own record of those sections.
4. 4.5: `systemctl stop --no-block lemnosd` while the echo runs; 20 ms samples for 2 s: when
   lemnosd's process is gone (want within 1 s), when the tool ends, and at 1 s the wait channel of
   every `lemnosd`, `lemnosd-gsuper`, `lemnosd-gadget` and `lemnos-usb-echo` process (`io_destroy`
   is the finding). Then the drop-in is removed and lemnosd started on the image's own file. One
   lemnosd down window, 5 s restore.
5. A `session` restore armed first, at `WINDOW_S` + 120 s, puts the image's settings and link back
   if anything above dies.

Running it (shared by every detached form; `scripts/lemnos-check.sh`'s header has the details):

1. Upload `scripts/lemnos-check.sh`, `scripts/detached-lib.sh` and `scripts/checks/` to
   `/data/board/checks/bin/` over the session (not `/tmp`: the session's `/tmp` may be private to the
   comm core's unit, and the transient units would not see it).
2. Hold no board lock in the session: the check takes `/run/lock/raze-gpu.lock` and
   `/run/lock/board-gpu.lock` itself (10 s wait) and refuses, stopping nothing, if either is held.
3. As root: `bash /data/board/checks/bin/lemnos-check.sh start E36 ALT_BOARD=<file> ECHO_BIN=<lemnos-usb-echo> [WINDOW_S=900]`. It copies the
   scripts into `/data/board/checks/E36/<UTC stamp>/bin/`, starts the check in the transient unit
   `lemnos-check-E36` and returns. The link then goes; nothing on the board depends on the session.
4. The check logs its hypothesis, a baseline and every step (CLOCK_REALTIME stamp and seconds since
   boot) to `log` in the run directory, verdicts to `result`. Before each stop it arms a timed
   restore in its own transient unit (`lemnos-restore-E36-NAME`) and sees it running; at the bound,
   uncancelled, the restore kills the check's unit, undoes what the check changed, starts lemnosd
   and the comm core (`COMM_UNIT`, default `orion-comm.service`) with backoff 1, 2, 4, 8, 8 ... s, never giving up, and checks the end state.
   The end state, checked by the check or the restore: lemnosd active, the `hw-watchdog` device
   `running ok`, the comm core and the bridge as before, the gadget bound to the same controller, no
   drop-in of ours, the link's addresses back, the same boot id. The address on `lemnos0` is
   systemd-networkd's (a runtime `.network` file written at boot, applied again when the interface
   comes back): the end check waits 30 s for it. One still missing then is added back by hand so
   the board stays reachable, and the run is FAILED: a recovery never lets a run pass. Nothing touches config.txt, the default slot,
   `mem=`, `.reboot-ok` or the watchdog.
5. Reconnect after WINDOW_S + 2 min and run `bash /data/board/checks/bin/lemnos-check.sh collect E36`: the
   log, the restore logs, the results, whether each restore was cancelled or fired, and whether the
   board reset since the baseline (`THE BOARD RESET`, from the boot id). Its first and last lines
   are the run's verdict: `RUN PASSED`; `RUN INCOMPLETE` when a step was not run; `RUN FAILED` with
   the reasons when a step failed, the board was not as found (an address re-added by hand
   included), the board reset, or a restore had to finish the check. Paste it here.

The watchdog: once slot-init has exec'd away, lemnosd's `hw-watchdog` driver is the only feeder of
`/dev/watchdog`. It feeds every half period and never writes the magic close. When lemnosd stops or
dies the kernel pings once on the close and logs `watchdog did not stop!`
(`drivers/watchdog/watchdog_dev.c`, `watchdog_release`); the board resets one period (15 s) after
that unless a new lemnosd feeds. A stop that hangs before it drops the driver leaves only what was
left of the last feed: half a period (7.5 s) at worst. Every lemnosd down window is therefore bounded
by its timed restore at `DOWN_BOUND_S` = 5 s, plus 2 s for lemnosd's start, under that 7.5 s; the
check refuses to start if the device's own `timeout` makes this false. The log says for each window
whether the close ping was seen and how long lemnosd was down. A lemnosd that cannot be started
inside the period (the backoff running past it) resets the board: expected, recorded by `collect`.

Status of the detached form: untested on board. Rehearsed on the PC against the stand-in board
(`scripts/rehearse/rehearse.sh ID CASE`: fake systemd with `Restart=always` and starts that fail
like a failed start job, the kernel's close ping, a 15 s watchdog that resets the stand-in): the
normal run; the check killed right after it stops lemnosd (the stand-in's `systemctl stop` freezes
the check at that exact point); the check frozen there; two failed starts (the restore retries 1
and 2 s apart and the board stays up); five failed starts (the backoff passes the period and the
stand-in resets, which `collect` reports as RUN FAILED); the link's address put back by networkd
(RUN PASSED) and not put back (re-added by hand, RUN FAILED). Three failed starts are the most a
restore survives inside one period.
