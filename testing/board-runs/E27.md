# E27 board run: driver packages on a CM5

Status: untested on board.

Everything below ran on the build machine (x86-64), against the simulated board and the mocks.
Not yet run anywhere: a package on aarch64, and a package's driver on real hardware of any kind
(a real I2C bus, SPI device, GPIO line, PWM channel, UART, register window, interrupt, DMA
memory, clock, reset, USB device, USB function or frame stream with real dma-bufs).

## A package loads and runs

1. Build lemnosd and `engine/package/tests/fixture` (`cargo build --release` in that directory)
   for aarch64, on the board or cross-compiled with the same toolchain and the same Lemnos tree.
2. Put `liblemnos_package_fixture.so` in a directory on the board. Start lemnosd with
   `--packages <dir> --package-mode open` and a board file with one device,
   `driver = "package-fixture"`, `uses = { bus = "<an I2C bus the board file names>" }`.
   Expect on its error output `package <path>: driver "package-fixture"`, and the device `running`
   in `lemnos-ctl list`.
3. `lemnos-ctl packages` shows `packages open: any package in the directory runs` and the file
   as `loaded   package-fixture`.
4. `lemnos-ctl call <device> add 40 2` answers 42. `lemnos-ctl call <device> register <address>
   <register>` reads a register of a chip known to be on that bus (an identity register), and a
   read of an address with no chip fails without taking the device down.
5. `lemnos-ctl call <device> crash`: the call fails, the device shows `retrying (the driver
   panicked)`, and is `running` again about a second later. Other devices on the board are
   unaffected throughout.
6. Signed mode: make a key and sign the file as `docs/writing-a-driver.md` shows, start lemnosd
   with `--package-keys <file>` and no `--package-mode`, and expect the package to load. Append a
   byte to the `.so`, restart, and expect `refused: bad signature`, on the error output and in
   `lemnos-ctl packages`.
7. A package built for x86-64 put in the directory is refused with `not a driver package: built
   for another kind of machine`, and nothing else changes.

## A merged driver as a package, on its real hardware

8. Build `engine/package/tests/ws2812-package` for aarch64. Take `ws2812` out of the service's
   built-in drivers for this run (a package with a built-in driver's name is refused), or give
   the wrapper's driver another name. With a strip on an SPI bus the board file names, and the
   device's board entry unchanged from the built-in run, expect the strip to show what
   `lemnos-ctl call <device> set` and `show` send, the same as with the driver built in.

## Every other kind of resource, on real hardware

The fixture's `exercise KIND STEP DATA` method makes one call on one resource; its kinds and
steps are listed in `engine/package/tests/fixture/src/exercise.rs`. For each kind the board has,
name the resource in the fixture device's `uses` and run the steps, checking the result against
the hardware:

9. GPIO line (`line`, kind 3): step 0 drives the pin (measure it), step 1 then 2 reads an input,
   and step 4 reports an edge after the pin is toggled, with a timestamp from the kernel.
10. PWM (`pwm`, kind 4): step 0 with a period and duty, measured on a scope; step 1 reads them
    back.
11. UART (`uart`, kind 5): step 1 sends bytes seen on the wire; step 2 reads bytes sent to it.
12. Registers, interrupt, clocks, reset, DMA (kinds 8 to 12): on a block the board file gives a
    window to, read an identity register, enable its clock, release its reset, wait for one
    interrupt, and allocate, write, sync and read back one DMA buffer.
13. Stream (`stream`, kind 13) on a stream the board file declares as dma-bufs, with a client
    attached: steps 1, 6 and 4. Step 6 must answer present, and the bytes read through the
    descriptor must be the buffer's. This is the one place a real dma-buf descriptor crosses to
    a package.
14. USB device (`usb`, kind 6) on a device plugged into the board: step 0 reads its
    configuration descriptor; steps 4, 1 claim an interface; step 5 resets it.
15. USB function (`function`, kind 7) with the board's device controller: step 0 with a
    descriptor set, then step 2 until a host that is plugged in configures it.

## A statically linked service

16. Build lemnosd for `aarch64-unknown-linux-musl` and start it with `--packages <dir>
    --package-mode open`. Expect one line on its error output saying it is statically linked and
    packages need a dynamically linked build, the same line in `lemnos-ctl packages`, no file
    looked at, and every built-in driver running as without `--packages`.
