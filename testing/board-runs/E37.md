# E37: a caller uses the codec blocks (`codec.block/1`)

Status: untested on board. The contract and its work format, the shared job server, and each
block's checks are covered by unit tests; `rk-mpp` runs jobs on a played kernel that does what
`mpp_common.c` does with each message; the V4L2 stateless block runs requests on a played-back
node; the A733 engine on a device that records its requests; and each driver is bound from a
board file and served through a real `Host` with sealed memfds standing in for the stream's
dma-bufs. No test opens a codec node, so nothing below has been seen to happen.

What only a board can show:

- that each kernel takes the stream's dma-heap buffers where a test gave it memfds (the
  service node's translation, `V4L2_MEMORY_DMABUF` on both queues of a stateless decoder);
- that a job's registers or controls, built by a caller who knows the codec, decode or encode
  a picture;
- that a descriptor number over 1023 (the service node keeps 10 bits) is refused cleanly in a
  daemon with many files open;
- how long a job holds the driver's tick (a job runs to its end inside it).

Before running: take the board lock named in `AGENTS.md`. Builds go on NVMe or SSD. Each
check needs a caller that builds the work for its block. Lemnos parses no bitstream: the HEVC
headers and controls for the stateless decoder come from Styx's `styx-block` (Styx `next` at
65865a99, `crates/codec/block`), and nothing in the tree builds register sets.

Every entry needs a job stream of dma-bufs (except the A733 engine's, which can be plain):

```toml
[devices.streams.jobs]
memory = "dma-buf"
buffers = 16
buffer_bytes = 4194304
job_slots = 16
job_bytes = 20
```

## 1. `rk-mpp` (RK3588 board, vendor kernel)

```toml
[[devices]]
id = "vdpu2"
driver = "rk-mpp"
config = { block = "vdpu2" }
```

1. Start lemnosd. Expect the device `Running` and healthy, and `/dev/mpp_service` not open
   (`ls -l /proc/$(pidof lemnosd)/fd`).
2. Call `block`: `rk-mpp:vdpu2`. Call `info`: 64 references, 2 items, 32 buffers.
3. Post a job whose `TAG_WRITE` item is register 0 with one value and no reference. Expect
   `Refused` (a job with no address leaves the kernel's own translation table in force): the
   claim is taken, and no task is queued.
4. Post a job with a reference in a register the block translates and a `TAG_READ` of the
   block's first registers. Expect `Done`, the node open, the read-back to hold the buffer's
   device address in that register, and `dmesg` clean. Record how long the tick took.
5. Post the same with an offset equal to the buffer's size. Expect `Refused`.
6. Close the caller's stream. Expect one `MPP_CMD_RESET_SESSION` (`strace -e ioctl`) and the
   node closed; attach again and expect a new open on the first job.
7. On a board whose block has no `iommu_group`, expect `Failed` and health
   `the block is not behind an IOMMU`.
8. With a caller that builds real register sets for one frame, decode it and compare the
   picture with a software decoder's.

## 2. `v4l2-stateless` (a board with a stateless decoder: hantro, rkvdec or cedrus)

```toml
[[devices]]
id = "decoder"
driver = "v4l2-stateless"
config = { device = "/dev/videoN" }
```

1. Post one IDR frame's job, built by Styx's `styx-block` from its fixture
   `crates/codec/block/src/hevc/fixtures/idr320.h265` (one 320x240 IDR): `TAG_SETUP` for `S265`,
   the picture's size and `NV12`, the controls the block takes as items, the slice in a stream
   buffer as the source, another stream buffer as the picture. Expect `Done`, the read-back to be
   the picture's bytes, and the picture to match the reference: that fixture decoded to linear
   NV12 (115,200 bytes) on another machine, for example
   `ffmpeg -i idr320.h265 -pix_fmt nv12 -f rawvideo idr320.nv12`. Record which decoder made it.
   Styx's own live test runs this job on the simulated block only, so this is the first run of
   it on a real decoder.
2. Expect `VIDIOC_QBUF` with `V4L2_MEMORY_DMABUF` on both queues to be accepted. A driver that
   refuses dma-bufs on its source queue is a finding: record it (the block then needs a copy
   path for the bitstream).
3. Decode a P frame that references the first picture by its stamp. Expect `Done`: the kernel
   found the reference by timestamp in the capture buffer the first job used.
4. Post a job whose source `length` runs one byte past its buffer. Expect `Refused` and no
   `VIDIOC_QBUF`.
5. Unplug nothing; stop the caller mid-stream and attach another. Expect the node closed and
   opened again, and the second caller's first job to decode.
6. Recovery, with frames running in a loop of jobs: unbind the decoder through its driver's
   `unbind` file, wait 20 s, and bind it again. Expect the jobs that run while it is unbound to
   be `Failed`, the wait between reopen attempts to go 250 ms, 500 ms, 1 s and so on, holding at
   8 s, and health to read the reopening message while the device is closed. After the bind the
   next due job opens the node again (its number may change) and its picture matches again.
   Nothing panics and the block never stops trying. Record the kernel version, the node and
   media paths, the unbind and bind, and `dmesg` (no errors from the decoder's driver).
7. A decoded picture allocates nothing from the second job on, under the counting allocator
   (the unit test `decoding_allocates_nothing_once_the_session_is_open` shows it on the mock).

## 3. `a733-video` (A733 board, vendor kernel)

```toml
[[devices]]
id = "ve2"
driver = "a733-video"
```

1. Post a job with a `TAG_READ` of 4 registers at the engine's top-register offset (0x800).
   Expect `Done` and four values; record them. `strace -e ioctl` shows `0x206`, `0x310`,
   `0x311`, `0x207` in that order and no other request.
2. Post a read of one register at offset 0x1000. Expect `Refused` and no request.
3. Kill lemnosd during a burst of jobs and check the engine's clocks are off afterwards
   (`cat /sys/kernel/debug/clk/clk_summary | grep ve`). A use count left behind is a finding.
4. Post any item with another tag. Expect `Refused`: no register is ever written.

## 4. `k230-vpu` private requests (K230 board)

Not reachable through the contract yet. From a test binary over
`lemnos_driver_k230_vpu::Claim`:

1. On an encoder session, `private(VIDIOC_S_MVX_RATE_CONTROL, ..)` with a constant bitrate.
   Expect success and the encoded stream's bitrate to follow.
2. `private(VIDIOC_G_MVX_COLORDESC, ..)` on a decoder after its first frame. Expect the
   stream's colour description.
3. `private(VIDIOC_S_MVX_ROI_REGIONS, ..)` with `num_roi` 16. Expect success. With 17, expect
   `InvalidInput` and no ioctl in `strace`.
4. `private(VIDIOC_S_MVX_OSD_INFO, ..)`. Expect `InvalidInput` and no ioctl.

Record anything else.
