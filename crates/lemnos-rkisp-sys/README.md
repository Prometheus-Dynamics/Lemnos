# lemnos-rkisp-sys

The Rockchip ISP21 (RK3566, RK3568), ISP30 (RK3588, RK3588S) and ISP32 (RV1106, RV1103, and the
ISP32-lite of RK3562) uAPI layouts of the vendor kernel's `rkisp` driver: the parameter and
statistics buffers, the module bits, and the compile-time checks of their sizes and offsets. It is
the `-sys` crate of `lemnos-drivers-rkisp`, which re-exports it as `uapi`. It is `no_std`, with no
allocation and no C libraries.

## What is here, and what is not

- Layouts only: `#[repr(C)]` structures and constants, generated by bindgen from the headers in
  `headers/` (`scripts/rkisp-bindgen.sh` regenerates them), plus `isp32_layout.rs`, which holds
  the hand-written impls and the C compiler's sizes and offsets.
- No device code, no tuning, no statistics math. Those are in `lemnos-drivers-rkisp` (the nodes,
  on `lemnos-v4l2`) and in the camera stack.

## Why its unsafe code lives here

The workspace forbids unsafe code, and this crate is the one place the rkisp layouts need it. Two
kinds of unsafe code are needed, and both are confined to this crate:

- The ISP32 bitfields. Bindgen generates their accessors (`raw_get`, `raw_set`, `raw_get_const`)
  as `unsafe` functions, by its design. `isp32.rs` is that generated output. Its module header says
  so, and its lint allows for `undocumented_unsafe_blocks` and `multiple_unsafe_ops_per_block` are
  set there with their reason. The generated module allows nothing else.
- The `bytemuck::Pod` and `Zeroable` impls for the generic bitfield unit (`isp32_layout.rs`). Derive
  refuses a generic structure, so the impls are written by hand, each with a SAFETY comment. The
  other structures derive `Pod` and `Zeroable`, which needs no unsafe code here.

The generated modules `isp21` and `isp3x` allow `missing_docs`, because bindgen runs with
`--no-doc-comments`. Their header says so.

## Licences

The headers are `(GPL-2.0+ WITH Linux-syscall-note) OR MIT`, from the Rockchip kernel
`develop-5.10` (`rk-isp2`, `rk-isp21`, `rk-isp3`, `rk-isp32`). The crate uses them under MIT, as
the generated files say, and their SPDX lines are kept. The rest of the crate is `MIT OR Apache-2.0`.

## Board status

Untested on board. The layouts are checked against the C compiler's sizes and offsets, not against
a running driver.
